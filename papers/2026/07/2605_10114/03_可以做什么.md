# 可以做什么

基于 SkillRAE 的核心逻辑（**离线拆解子单元 + 在线混合检索 + 救援式编译**），以下是可直接落地的行动指南。核心思想是：**不要直接把“技能文档”扔给 Agent，而是把“技能”编译成“针对当前任务的执行剧本”。**

## 可迁移到的场景（≥4）

1.  **企业级低代码/无代码平台（Low-Code/No-Code）**
    *   **痛点**：用户搜索“生成报表”，系统返回了包含“数据清洗”、“图表绘制”、“邮件发送”等几十个组件的庞大文档，Agent 容易混淆参数。
    *   **应用**：将组件文档拆解为“输入约束”、“输出格式”、“依赖库”等**子单元**。当用户任务复杂时，从非首选组件中“抢救”出特定的“日期格式校验”规则，编译进主组件的执行指令中，减少 Agent 的参数幻觉。

2.  **复杂软件开发的 Copilot（如 VS Code 插件）**
    *   **痛点**：在大型单体项目中，修改一个函数往往需要遵循跨文件的隐式规范（如命名约定、日志格式），直接检索相关函数代码往往遗漏这些“潜规则”。
    *   **应用**：构建代码库的**多级技能图**（文件 -> 函数 -> 规范片段）。当开发者请求“重构登录模块”时，系统不仅检索登录函数，还从“全局配置模块”中抢救出“异常处理规范”子单元，编译成一段 `README` 风格的上下文，指导 LLM 生成符合项目规范的代码。

3.  **自动化运维与故障排查 Agent（AIOps）**
    *   **痛点**：故障排查需要结合“当前报错日志”和“历史运维手册”。手册通常很长，包含大量无关的旧版本操作，直接检索会导致 Agent 执行过时指令。
    *   **应用**：将运维手册拆解为**原子操作单元**（如“重启服务”、“检查端口”、“清理缓存”）。当遇到特定报错时，系统从“旧版本手册”中抢救出“特定端口冲突的临时规避方案”，将其附着到当前版本的“重启服务”指令上，形成紧凑的**应急操作手册**。

4.  **多智能体协作系统（Multi-Agent Orchestration）**
    *   **痛点**：主 Agent 调用子 Agent 时，往往传递了过长的背景信息，导致子 Agent 注意力分散，执行效率低。
    *   **应用**：在主 Agent 和子 Agent 之间加入**编译层**。主 Agent 检索所有相关子 Agent 的能力描述，编译层提取出子 Agent 所需的**最小必要上下文**（如特定的输入格式、超时限制），并生成一段“任务简报（Briefing）”传给子 Agent，而非原始能力文档。

## 可立刻试的小实验（≥3，含输入/步骤/期望输出）

### 实验 1：模拟“救援机制”验证细粒度约束的增益
*   **输入**：
    *   任务：`"用 Python 写一个脚本，读取 CSV 并导出为 PDF，必须使用 A4 纸张，且页眉包含文件名。"`
    *   技能库 A（主技能）：`"Python CSV 转 PDF 通用脚本"`（包含完整代码，但未提及 A4 和页眉）。
    *   技能库 B（非首选技能）：`"LaTeX 文档排版规范"`（整体不相关，但包含"A4 纸张设置”和“页眉自定义”的子单元）。
*   **步骤**：
    1.  **基线**：直接将技能库 A 的全文 + 任务描述输入 LLM。
    2.  **SkillRAE 模拟**：
        *   检索：选中 A，忽略 B。
        *   救援：从 B 中提取“设置 A4 纸张”和“页眉包含文件名”两个子单元。
        *   编译：生成一段 Prompt：`[主技能代码] + [约束：必须使用 A4 纸张] + [约束：页眉动态插入文件名]`。
    3.  将编译后的 Prompt 输入 LLM。
*   **期望输出**：
    *   基线：生成的 PDF 可能是默认尺寸，页眉缺失或错误。
    *   SkillRAE 模拟：生成的代码明确包含 `page_size='A4'` 和 `header_text=filename` 逻辑，且代码结构紧凑，无冗余。

### 实验 2：构建简单的“子单元提取器”
*   **输入**：一份 2000 字的复杂 API 文档（包含安装、配置、示例、FAQ、版本历史）。
*   **步骤**：
    1.  使用 LLM 将文档拆解为 JSON 格式的子单元列表：
        ```json
        [
          {"type": "constraint", "content": "API Key 必须包含 32 位字符"},
          {"type": "snippet", "content": "import requests; ..."},
          {"type": "error_handling", "content": "401 错误需重试 3 次"}
        ]
        ```
    2.  构建一个向量索引（Embedding）存储这些子单元。
    3.  输入任务：`"调用该 API 获取数据，处理 401 错误"`。
    4.  检索 Top-1 子单元（401 错误处理），并找到其所属的父技能（整个 API 文档）。
*   **期望输出**：
    *   成功定位到"401 错误需重试 3 次”这一细粒度信息，即使它在文档的 FAQ 部分，而非核心代码块中。

### 实验 3：上下文压缩率与执行成功率对比
*   **输入**：5 个复杂的 Agent 任务（如“配置 Kubernetes 集群并设置网络策略”）。
*   **步骤**：
    1.  **组 A（Vanilla）**：检索 Top-3 相关技能文档，直接拼接（Token 数约 2000）。
    2.  **组 B（Compiled）**：检索 Top-3 技能，提取关键子单元，过滤冗余代码，生成紧凑上下文（Token 数约 800）。
    3.  分别让同一个 LLM（如 GPT-4o-mini）执行任务，记录成功率。
*   **期望输出**：
    *   组 B 的 Token 消耗降低 60% 以上。
    *   组 B 的执行成功率（通过验证器）不低于组 A，甚至在复杂约束任务上更高（因为干扰信息少）。

## 产品 / Agent 灵感

1.  **"Agent 编译器”中间件插件**
    *   做一个独立的服务层，夹在 RAG 检索器和执行 LLM 之间。
    *   **功能**：接收检索到的原始技能列表，输出优化后的 `System Prompt` 或 `Context File`。
    *   **卖点**：宣称“让 Agent 执行成功率提升 15%，Token 成本降低 40%"。

2.  **动态技能知识库（Dynamic Skill KB）**
    *   不是静态存储文档，而是存储“技能图”。
    *   当用户新增一个技能时，系统自动运行“子单元提取器”，将其拆解并挂载到现有图谱中。
    *   支持“跨技能引用”，例如在“支付技能”中自动关联“风控技能”中的“黑名单校验”子单元。

3.  **执行前“预演”模式**
    *   在 Agent 真正执行代码前，先运行一次“编译 - 模拟”流程。
    *   生成一份 `READ_FIRST.md` 给人类或另一个 LLM 审查：“这是为你编译的执行手册，确认无误后执行”。
    *   适用于金融、医疗等高风险场景。

## 跟现有系统怎么接

*   **接入 LangChain / LlamaIndex**：
    *   不要直接用 `Retriever` 返回文档。
    *   自定义一个 `ContextCompiler` 类，继承自 `BaseRetriever`。
    *   `invoke` 方法逻辑：先调用标准检索器 -> 获取 Top-K 文档 -> 调用内部 LLM 进行“子单元提取”和“救援逻辑” -> 返回编译后的字符串。
*   **接入 RAG 向量数据库**：
    *   **Schema 改造**：在向量库中增加 `subunit_id`, `parent_skill_id`, `community_id` 字段。
    *   **索引策略**：对子单元（Subunit）和完整技能（Skill）分别建立索引，或者使用混合索引（Hybrid Search）。
*   **接入现有 Agent 框架（如 AutoGen, CrewAI）**：
    *   将 SkillRAE 编译后的输出作为 `System Message` 的一部分注入到 Agent 的 `Conversation` 中。
    *   修改 `UserProxyAgent` 或 `AssistantAgent` 的 `prompt` 模板，使其适应“编译后上下文”的格式（如包含 `## Guidance` 和 `## Attached Constraints` 区块）。

## 风险与坑

1.  **子单元提取的准确性（Garbage In, Garbage Out）**
    *   如果技能文档本身写得乱七八糟，LLM 提取出的“子单元”可能是错误的或断章取义的。
    *   **对策**：在离线阶段引入“人工校验”或“确定性规则（正则）”作为兜底，不要完全依赖 LLM 提取。
2.  **编译延迟（Latency）**
    *   在线编译涉及多次 LLM 调用（检索、提取、附着、生成指导语），会显著增加首字延迟（TTFT）。
    *   **对策**：对高频技能进行**预编译**（Pre-compilation），或者使用小参数模型（如 7B）专门负责编译任务，大模型负责执行。
3.  **过度裁剪导致上下文缺失**
    *   为了“紧凑”，可能误删了某些看似无关但实际关键的“隐性依赖”。
    *   **对策**：设置“安全阈值”，保留一定比例的原始技能代码作为“参考区”，仅将核心约束放入“执行区”。
4.  **维护成本**
    *   技能库更新后，需要重新构建图、重新提取子单元。
    *   **对策**：设计增量更新机制，只处理变更的技能节点。

## 跟进清单

- [ ] **数据准备**：收集 50+ 个真实世界的技能文档（代码、API 文档、SOP），格式需包含“约束”、“示例”、“依赖”等结构化信息。
- [ ] **原型开发**：编写 Python 脚本实现“离线子单元提取器”和“在线救援逻辑”的简化版（Hardcode 规则优先，LLM 辅助）。
- [ ] **基准测试**：在本地搭建一个简单的 Agent 环境，对比 `Vanilla RAG` vs `SkillRAE 模拟` 在 10 个复杂任务上的成功率。
- [ ] **指标定义**：定义“上下文压缩率”、“救援命中率”、“执行成功率”三个核心指标。
- [ ] **工具链调研**：确认 LangChain/LlamaIndex 中是否有现成的组件可改造，或需从头编写 `Retriever`。
- [ ] **文档化**：编写一份《技能库构建规范》，指导如何编写能被 SkillRAE 高效编译的技能文档（例如：强制要求包含 `## Constraints` 章节）。
