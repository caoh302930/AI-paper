# Agent-as-a-Router: Agentic Model Routing for Coding Tasks

**Authors:** Pengfei Zhou, Zhiwei Tang, Yixing Ma, Jiasheng Tang, Yizeng Han, Zhenglin Wan, Fanqing Meng, Wei Wang, Bohan Zhuang, Wangbo Zhao, Yang You
**Venue:** arXiv preprint (2026)
**Organization(s):** National University of Singapore (NUS), DAMO Academy (Alibaba), Hupan Lab, Zhejiang University, UC Berkeley, HKUST
**arXiv:** [2606.22902](https://arxiv.org/abs/2606.22902)
**Code:** [https://github.com/LanceZPF/agent-as-a-router](https://github.com/LanceZPF/agent-as-a-router)
**Project page:** [https://omnisource.cn/agent-as-a-router](https://omnisource.cn/agent-as-a-router)

## TL;DR and contributions
这篇论文提出了一种名为 **Agent-as-a-Router** 的新框架，旨在解决多模型环境下的代码任务路由问题。它不再将路由视为一次性的静态分类，而是将其构建为一个持续运行的 **Context-Action-Feedback (C-A-F)** 循环，让路由器在执行过程中不断积累“实战经验”，从而越用越准。

**Main contributions:**
- 提出 **Agent-as-a-Router** 框架，将路由形式化为 C-A-F 循环，核心在于通过执行反馈（Execution-grounded Feedback）填补信息缺口。
- 构建了 **CodeRouterBench**，包含约 10,000 个任务实例和 8 个前沿大模型的执行验证数据，支持基于累积遗憾（Cumulative Regret）的流式评估。
- 实现了 **ACRouter** 系统，包含编排器（Orchestrator）、验证器（Verifier）和记忆模块（Memory），在分布内（ID）和分布外（OOD）任务上均实现了最低的累积遗憾。
- 诊断出当前 LLM 路由器的瓶颈是**信息缺失（Information Deficit）**而非推理能力不足，提供维度级性能统计即可带来 15.3% 的相对提升。

**Compared against:** DimensionBest (启发式), RouteLLM, LinUCB/LinTS (上下文多臂老虎机), 静态微调分类器 (LogReg, MLP), 单模型基线 (Always-Opus 等)。
**On datasets:** CodeRouterBench (10 个编码维度，含 9 个分布内任务 + 1 个分布外智能体编程任务)。
**Headline improvements:** 在分布内任务上，ACRouter 的平均性能（AvgPerf）达到 **49.98%**，优于次优基线 DimensionBest (47.50%)；累积遗憾（CumReg）降至 **205.5**，显著低于其他方法（约 280-310）。在分布外（OOD）任务上，ACRouter 性能为 **62.50%**，远超静态基线（<22%）甚至优于最强单模型 Always-Opus (57.14%)。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** **C-A-F 循环**（上下文→动作→反馈→更新上下文）是本文的灵魂。理解为什么“执行后的验证反馈”比“静态的先验知识”更重要，以及路由器如何通过记忆模块（Memory）将过去的成功/失败转化为未来的决策依据。
- **🔧 Useful in practice:** **ACRouter 的架构设计**（Orchestrator + Verifier + Memory）以及 **CodeRouterBench 的构建方法**。特别是如何利用 kNN 检索历史相似任务来增强当前决策，这对构建自适应系统极具参考价值。

## Context and prerequisites

要理解这篇论文，首先需要打破一个直觉误区：很多人认为路由器的核心难点在于“推理”，即让路由器像专家一样思考哪个模型适合当前任务。然而，本文指出，真正的瓶颈在于**信息缺口（Information Deficit）**。现有的路由器往往只有静态的模型能力描述（例如“模型 A 擅长数学”），缺乏针对具体任务实例的动态反馈。这就好比一个老中医只背了药典（静态知识），却没见过病人实际服药后的反应（动态反馈）。

其次，需要理解**上下文多臂老虎机（Contextual Multi-Armed Bandit）**的概念。在路由问题中，每个模型是一个“臂（Arm）”，每个任务是一个“上下文（Context）”。传统的 Bandit 算法（如 LinUCB）虽然能在线更新，但它们通常假设奖励函数是线性的，或者仅依赖简单的特征向量，难以捕捉代码任务中复杂的语义相似性。本文的 C-A-F 循环本质上是一个更灵活的 Bandit 变体，它利用 LLM 强大的语义理解能力来处理 Context，利用 Verifier 获取真实的 Feedback，并利用 Memory 存储非线性的历史经验。

最后，**累积遗憾（Cumulative Regret）**是评估流式路由的核心指标。它衡量的是：在任务流中，你的路由器做出的选择与“上帝视角”（即知道每个任务最佳模型的 Oracle）之间的总差距。这个指标比单纯的准确率更能反映路由策略在长期运行中的效率，因为它惩罚了那些“虽然做对了但没选最优”或“选错了”的决策。

## Method

### The big picture (layman version)

想象你在管理一个由 8 位不同特长的程序员（大模型）组成的团队。以前，你（路由器）只能根据简历（静态模型描述）来分配任务，结果经常派错人，导致返工。这篇论文提出的方法，相当于给你的管理助手装上了一个**“实时反馈与记忆系统”**。

当一个新的编程任务进来时，助手不仅看任务描述，还会去翻“历史档案库”（Memory），看看以前类似的任务是谁做成功的，谁搞砸了。然后，它做出一个决定（Action），调用某位程序员。任务完成后，系统会立即运行测试代码（Verifier），给出一个真实的分数和成本（Feedback）。这个结果会被立刻记入档案库，更新到“历史记忆”中。当下一个类似任务出现时，助手就能基于这次真实的“实战经验”做出更精准的判断。

这个过程不断循环：看上下文 -> 做决定 -> 执行并验证 -> 更新记忆。通过这种方式，路由器不再依赖死板的规则或静态的统计，而是像一位经验丰富的老项目经理一样，在实战中越用越聪明，最终能自动适应各种新类型的任务，甚至在没有见过的新任务类型（OOD）上也能表现优异。

### The walkthrough

让我们深入拆解 **ACRouter** 是如何实现这个 C-A-F 循环的。

**1. 形式化定义：C-A-F 循环**
我们将路由过程定义为一个序列决策问题。对于任务流 $\mathcal{T} = (t_1, \dots, t_N)$ 和模型池 $\mathcal{M} = \{m_1, \dots, m_M\}$：
- **Context ($c_i$)**：在第 $i$ 个任务时，路由器的观察包括任务提示 $p_i$、元数据 $d_i$（如难度、语言），以及**历史记忆** $\mathcal{H}_{<i}$。
- **Action ($a_i$)**：路由器选择一个模型 $m_{a_i}$ 来执行任务。
- **Feedback ($f_i$)**：执行后，验证器返回真实分数 $\hat{s}_i$ 和成本 $\hat{\kappa}_i$。
- **更新**：$c_{i+1}$ 包含了 $f_i$，即 $c_{i+1} = (p_{i+1}, d_{i+1}, \mathcal{H}_{<i} \cup \{(a_i, f_i)\})$。

这本质上是一个上下文多臂老虎机问题，但关键在于**记忆 $\mathcal{H}$ 的构建方式**。

**2. 核心组件详解**

*   **Orchestrator（编排器）：决策的大脑**
    它负责综合所有信息做出选择。输入包括：
    - **DimensionBest Prior**：基于预实验的维度级最佳模型先验（例如：算法题选 GLM-5）。
    - **kNN Retrieval**：从 Memory 中检索与当前任务最相似的 Top-10 历史任务。这里使用了代码专用 Embedding（如 voyage-code-3）计算余弦相似度。
    - **策略模型**：一个经过微调的轻量级 LLM（Qwen3.5-0.8B），结合启发式规则进行加权投票。
    *为什么这样设计？* 单纯的 LLM 推理可能不稳定，而单纯的查表（DimensionBest）太粗糙。混合策略既利用了先验知识，又通过 kNN 捕捉了细粒度的任务特征。

*   **Verifier（验证器）：事实的裁判**
    它负责生成真实的 Feedback。对于代码任务，它不只是看 LLM 生成的文本，而是：
    - 在沙箱（Sandbox）中执行代码。
    - 运行单元测试（Pass@1）。
    - 结合 AST 解析、LLM-as-Judge 等多重信号，加权计算出一个 $[0, 1]$ 的分数 $u_i$。
    *关键点*：这个反馈是**执行 grounded（基于执行）**的，而非模型自评估，保证了信息的真实性。

*   **Memory（记忆模块）：经验的仓库**
    这是一个在线向量存储。每次循环结束后，将 $(a_i, f_i)$ 存入。
    - **检索机制**：使用 kNN 检索相似任务。
    - **容量限制**：采用 FIFO（先进先出）策略，上限设为 20K 条，确保记忆是最新的且不过载。
    *创新点*：传统的 Bandit 算法（如 LinUCB）通常维护每个臂的参数分布，而 ACRouter 维护的是**具体的任务 - 结果对**。这使得它能捕捉到非线性的、复杂的任务特征，而不仅仅是线性特征。

**3. 奖励与遗憾计算**
为了平衡性能与成本，定义单任务奖励：
$$ r_i(a_i) = \epsilon_1 s_i(a_i) + \epsilon_2 \kappa_i(a_i) $$
其中 $\epsilon_1 > 0$ 奖励性能，$\epsilon_2 < 0$ 惩罚成本（文中设为 $1$ 和 $-0.1$）。
累积遗憾（Cumulative Regret）定义为：
$$ \mathrm{CumReg}_N(\pi) = \sum_{i=1}^N (r_i^* - r_i(a_i)) $$
其中 $r_i^*$ 是 Oracle（上帝视角）在该任务上的最大可能奖励。我们的目标是让这个值最小化。

## Challenges in the field — and what this work addresses

**挑战 1：静态路由无法适应分布外（OOD）任务**
*为什么难？* 现有的路由器（如 RouteLLM 或静态分类器）通常在固定的训练集上训练，学习的是训练集分布下的特征映射。一旦遇到全新的任务类型（如从“单函数生成”变为“多文件仓库级调试”），训练好的特征提取器完全失效，导致性能断崖式下跌。
*本文方案*：ACRouter 不依赖固定的训练分布，而是通过 **C-A-F 循环** 在线积累经验。即使在 OOD 任务流开始时表现一般，随着 Memory 中积累了该新领域的反馈，路由器能迅速调整策略，实现“越用越准”。实验证明，ACRouter 在 OOD 任务上性能（62.50%）甚至超过了最强的单模型（57.14%）。

**挑战 2：信息缺失导致路由决策盲目**
*为什么难？* 很多路由器仅凭任务文本和模型简介做决定，缺乏对“模型在特定任务上实际表现”的感知。这导致路由器无法区分“模型 A 理论上擅长”和“模型 A 实际上在这个任务上表现好”。
*本文方案*：通过 **Verifier** 提供执行层面的真实反馈，并通过 **Memory** 将这些反馈作为 Context 的一部分。消融实验显示，仅向路由器提供维度级的性能统计（+Perf stats），就能带来 15.3% 的相对提升，证明了信息比推理能力更关键。

**挑战 3：成本与性能的权衡难以动态优化**
*为什么难？* 不同模型价格差异巨大（如 Opus 是 MiniMax 的 20 倍）。静态策略要么为了性能无脑选贵的，要么为了省钱选便宜的，无法根据任务难度动态调整。
*本文方案*：在奖励函数 $r_i$ 中显式引入成本项 $\kappa_i$。ACRouter 能够根据历史经验，自动学会在简单任务上选便宜模型，在复杂任务上选昂贵模型，从而在 Pareto 前沿上达到最优。

**本文未解决的问题**：
- **冷启动问题**：虽然 Memory 能在线更新，但在初始阶段（Memory 为空或很少时），路由器的表现仍依赖于先验知识（DimensionBest）。如果先验知识完全错误，初期性能会受影响。
- **验证器的开销**：Verifier 需要运行沙箱和测试，这增加了单次路由的延迟和计算成本。对于对延迟极度敏感的场景，这可能是一个瓶颈。

## Experiments and results

**数据集与设置**：
- **CodeRouterBench**：10,111 个任务，分为 9 个分布内（ID）维度（如代码生成、算法设计）和 1 个分布外（OOD）维度（智能体编程）。
- **模型池**：8 个前沿模型，包括 Claude Opus 4.6, GPT-5.4, Qwen3-Max 等。
- **评估指标**：AvgPerf（平均性能）、CumReg（累积遗憾）、Perf/$（性价比）。

**核心结果**：
1.  **分布内（ID）表现**：
    - **ACRouter** 以 **49.98%** 的 AvgPerf 和 **205.5** 的 CumReg 位居第一。
    - 优于次优的启发式基线 **DimensionBest**（47.50% AvgPerf, 277.4 CumReg）。
    - 显著优于静态训练的分类器（如 RouteLLM-BERT, CumReg ~285）。
    - **性价比**：ACRouter 的 Perf/$ 为 3.79，优于 Always-Opus (1.29)，说明它成功避开了不必要的昂贵调用。

2.  **分布外（OOD）表现（关键亮点）**：
    - 在从未见过的“智能体编程”任务上，静态基线（LogReg, RouteLLM）性能暴跌至 **8.93% - 21.43%**，甚至不如随机选择（31.25%）。
    - **ACRouter** 依然保持 **62.50%** 的高性能，且 CumReg 仅为 **17.0**，远低于 Always-Opus (26.7)。
    - 这证明了 C-A-F 循环在应对分布偏移时的强大泛化能力。

3.  **消融实验结论**：
    - **信息 vs 推理**：在 Vanilla LLM Router 中加入维度级性能统计（+Perf stats），性能从 41.41% 提升至 47.74%（+15.3%），证明瓶颈是信息而非推理。
    - **组件贡献**：移除 Memory 或 Verifier 会导致性能显著下降，验证了三个模块的必要性。

## Open questions and limitations

1.  **冷启动延迟**：在 Memory 为空或数据稀疏的初期，路由器的表现依赖于先验知识。如果先验知识（如 DimensionBest）本身不准确，初期性能可能较差。如何设计更高效的冷启动策略（如主动学习）是一个开放问题。
2.  **验证成本**：Verifier 需要执行代码，这在某些场景下可能耗时较长或存在安全风险（如恶意代码执行）。如何平衡验证的准确性与执行开销？
3.  **成本估算的局限性**：论文指出，由于无法观测到云厂商的缓存命中率，成本估算基于公开定价。实际部署中，缓存策略可能会显著改变成本结构，导致理论上的 Perf/$ 与实际有偏差。
4.  **扩展性**：目前主要针对代码任务。虽然框架通用，但将 C-A-F 循环扩展到其他领域（如数学推理、创意写作）时，如何设计高效的 Verifier 是一个挑战。
