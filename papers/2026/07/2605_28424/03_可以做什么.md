# 可以做什么

基于 Skill0.5 的核心逻辑（**通用技能内化 + 任务技能外置 + 难度动态路由 + 反事实防捷径**），以下是可直接落地的执行方案。

## 可迁移到的场景（≥4）

1.  **企业级 RAG 智能客服（动态知识库）**
    *   **痛点**：通用对话能力（礼貌、逻辑）与具体产品知识（库存、促销规则）混在一起，导致长上下文干扰或知识冲突。
    *   **迁移**：
        *   **内化**：将“安抚情绪”、“分步推理”、“多轮追问”等通用交互逻辑通过 SFT/RL 固化到模型参数中。
        *   **外置**：将“某型号手机参数”、“最新退款政策”等动态知识保留在 RAG 检索的 Prompt 中。
        *   **路由**：根据用户问题的复杂度（如是否涉及多步查询），动态决定是调用通用逻辑还是强制检索外部知识，并防止模型“幻觉”编造政策。

2.  **复杂代码生成与调试 Agent（DevOps 场景）**
    *   **痛点**：模型知道通用编程范式，但不懂当前项目的特定规范（如特定的 API 版本、内部库用法）。
    *   **迁移**：
        *   **内化**：将“代码重构”、“单元测试编写”、“安全审计”等通用工程技能内化。
        *   **外置**：将项目特定的 `README`、`API 文档`、` 遗留代码片段` 作为 Task Skill 注入 Prompt。
        *   **反事实检查**：在生成简单代码时，故意隐去项目文档，若模型仍能写出符合规范的代码（说明已内化），则给予高奖励；若必须依赖文档才能写出，则标记为“需检索”，防止模型在 OOD（新项目）场景下因缺乏文档而崩溃。

3.  **多模态机器人控制（具身智能）**
    *   **痛点**：机器人需要通用的“避障”、“抓取”逻辑，但不同任务（如“倒水”vs“拿苹果”）需要不同的物理参数。
    *   **迁移**：
        *   **内化**：将“视觉 - 动作映射”、“路径规划”等底层控制策略内化到策略网络参数中。
        *   **外置**：将“当前物体的物理属性（重量、摩擦系数）”、“任务目标描述”作为 Prompt 输入。
        *   **难度路由**：对于从未见过的物体（Hard），利用“特权蒸馏”（由人类演示或仿真器提供完美轨迹）引导模型学习通用抓取逻辑；对于常见物体（Easy），检查模型是否真的在利用物体属性，而非死记硬背动作序列。

4.  **金融合规与风控审核 Agent**
    *   **痛点**：审核逻辑（如“识别欺诈模式”）需要内化，但具体的“最新监管条文”和“客户交易数据”必须实时检索。
    *   **迁移**：
        *   **内化**：将“逻辑链条构建”、“风险等级判定”、“异常模式识别”内化。
        *   **外置**：将“当日监管公告”、“客户历史交易流”作为 Task Skill。
        *   **反事实检查**：针对简单的合规查询，移除具体条文，测试模型是否仅凭通用逻辑就能判断风险。如果模型在没有条文时也能准确判断（说明逻辑已内化），则视为高可信；若必须依赖条文，则提示“需人工复核具体条款”。

## 可立刻试的小实验（≥3）

### 实验 1：验证“反事实检查”对防幻觉的有效性
*   **输入**：一个包含“通用推理技能”（如：先拆解问题再回答）和“具体事实”（如：2024 年诺贝尔奖得主是 X）的 Prompt 任务。
*   **步骤**：
    1.  构建一个微调后的模型（或 Prompt 工程模拟），让它回答 10 个简单事实题。
    2.  **正常组**：提供完整 Prompt（含具体事实），记录准确率。
    3.  **反事实组**：移除“具体事实”部分，仅保留“通用推理技能”，让模型回答同样的问题。
    4.  计算 $u_i = \text{准确率}_{\text{正常}} - \text{准确率}_{\text{反事实}}$。
*   **期望输出**：
    *   若模型“走捷径”（死记硬背），$u_i$ 应接近 0（因为没看 Prompt 也能答对，或者完全瞎猜）。
    *   若模型真正“利用”了技能，$u_i$ 应显著大于 0（移除事实后，仅靠推理无法回答，准确率下降）。
    *   **目标**：筛选出那些 $u_i$ 低的样本，在训练中加入惩罚项，强制模型依赖外部知识。

### 实验 2：难度路由器的动态阈值模拟
*   **输入**：一个包含 50 个不同难度任务（Easy/Medium/Hard）的测试集。
*   **步骤**：
    1.  初始化一个滑动窗口（大小=10），计算初始通过率阈值 $\eta_0$。
    2.  模拟模型对前 10 个任务的尝试，记录通过率 $p_i$。
    3.  根据 $p_i$ 与 $\eta_t$ 的关系，将任务分类为 Hard/Medium/Easy。
    4.  更新滑动窗口，重新计算 $\eta_{t+1}$，继续处理下一个任务。
*   **期望输出**：
    *   输出一个动态分类日志，展示阈值如何随模型表现波动。
    *   验证：当模型在 Easy 任务上连续失败时，阈值应自动降低，将这些任务重新归类为 Medium/Hard，触发“特权蒸馏”逻辑（即模拟给予更多提示）。

### 实验 3：通用技能内化 vs 全外置的推理延迟测试
*   **输入**：同一个复杂任务（如：多步数学推理 + 特定领域知识）。
*   **步骤**：
    1.  **方案 A（全外置）**：将通用推理步骤（CoT）和领域知识全部写入 Prompt。
    2.  **方案 B（Skill0.5 模拟）**：将通用推理步骤内化（微调模型或 System Prompt 固化），仅将领域知识写入 Prompt。
    3.  分别测量两种方案的 Token 生成数量（Prompt 长度 + 输出长度）和推理耗时。
*   **期望输出**：
    *   方案 B 的 Prompt 长度显著缩短（减少 30%-50%）。
    *   方案 B 的推理速度更快，且在长任务中，方案 A 出现“迷失在中间”（Lost in the Middle）导致的逻辑错误率应高于方案 B。

## 产品 / Agent 灵感

1.  **“自适应教练”Agent 平台**
    *   **功能**：一个训练平台，用户只需上传任务数据，系统自动运行 Skill0.5 流程。
    *   **亮点**：自动识别哪些是“通用技能”（自动内化），哪些是“任务技能”（自动检索），并生成“难度路由报告”，告诉用户模型在哪些任务上存在“走捷径”风险。
    *   **价值**：降低企业训练垂直 Agent 的门槛，解决 OOD 泛化难题。

2.  **动态知识注入的“活”文档助手**
    *   **功能**：企业内部文档助手。
    *   **机制**：模型内化了“如何阅读文档”、“如何提取关键信息”的通用技能。当员工提问时，系统只检索最新的文档片段（Task Skill）注入。
    *   **创新**：如果员工问的是“如何报销”，系统发现模型已内化报销流程（Easy 任务），则直接回答；如果问的是“新发布的 A 产品报销标准”，系统检测到模型无法内化（Hard 任务），自动触发“特权模式”，展示详细文档并引导模型学习。

3.  **防幻觉的合规审查插件**
    *   **功能**：嵌入到现有 LLM 应用中的中间件。
    *   **机制**：在模型生成回答前，对 Easy 类问题执行“反事实探针”（隐去关键法规），如果模型回答不变，说明它没看法规，直接拦截并标记“疑似幻觉”，要求重新检索法规生成。
    *   **价值**：在金融、法律等高风险场景提供实时的“技能利用度”监控。

## 跟现有系统怎么接

1.  **接入 RAG 系统**
    *   **改造点**：在 RAG 的检索模块后增加一个**Router 层**。
    *   **逻辑**：
        *   输入 Query -> 计算历史通过率/相似度 -> 判定难度。
        *   **Hard**：检索 + 注入“通用 CoT 模板”（作为 Privileged Prompt） -> 生成轨迹 -> 蒸馏。
        *   **Easy**：检索 -> 生成回答 -> **并行**生成一个“无检索”的回答 -> 对比差异 -> 计算利用增益 -> 调整 Loss。
    *   **接口**：修改 RAG 的 `generate` 函数，增加 `is_hard` 和 `enable_counterfactual` 参数。

2.  **接入强化学习框架 (如 Ray RLlib, TRL)**
    *   **改造点**：自定义 `Trainer` 和 `Policy`。
    *   **逻辑**：
        *   在 `compute_loss` 阶段，根据任务标签（或动态计算）选择 Loss 函数：`JSD_Loss` (Hard), `GRPO_Loss` (Medium), `Anti-Shortcut_Loss` (Easy)。
        *   需要实现一个 `DifficultyEstimator` 模块，维护滑动窗口通过率。
    *   **接口**：继承 `GRPOTrainer`，重写 `get_advantages` 方法，加入反事实增益计算。

3.  **接入现有 Agent 编排框架 (如 LangChain, AutoGen)**
    *   **改造点**：作为 System Prompt 的动态生成器。
    *   **逻辑**：
        *   定义两个 Prompt 模板：`General_Template` (内化后保留在 System Message) 和 `Task_Template` (动态插入 User Message)。
        *   在 Agent 的 `run` 循环中，根据上一轮的成功率，动态调整 `Task_Template` 的注入策略（如：Easy 时尝试移除部分 Task Info 进行自我验证）。

## 风险与坑

1.  **技能边界模糊（分类错误）**
    *   **风险**：很难自动区分什么是“通用技能”，什么是“任务技能”。如果把本该内化的逻辑留在了 Prompt，会导致上下文过载；如果把本该外置的具体规则内化，会导致 OOD 失败。
    *   **对策**：初期需要人工标注或基于规则（如：出现频率高、跨任务通用的为 General）进行冷启动，后期通过聚类分析自动划分。

2.  **训练成本激增**
    *   **风险**：Skill0.5 要求对 Easy 任务做反事实采样，对 Hard 任务做特权采样。这意味着每个 Batch 的采样量可能是标准 RL 的 2-3 倍，显存和计算时间翻倍。
    *   **对策**：仅在验证集或小规模数据上运行完整流程，生产环境可简化为“仅对 Hard 任务做蒸馏，对 Easy 任务做抽样检查”。

3.  **反事实检查的误杀**
    *   **风险**：如果模型真的通过通用逻辑解决了问题（即不需要外部技能），反事实检查可能会错误地惩罚它（因为 $p_i \approx p_i^{none}$，增益低）。
    *   **对策**：引入“任务依赖性”指标。如果任务本身就不依赖外部知识（如纯逻辑推理），则跳过反事实检查。

4.  **冷启动困难**
    *   **风险**：在训练初期，模型对所有任务都是 Hard，特权蒸馏如果生成的轨迹质量不高（老师本身也不行），会导致模型学到错误的通用技能。
    *   **对策**：Privileged Prompt 必须由强模型（如 GPT-4o）或人工专家生成，确保“老师”的轨迹是高质量的。

## 跟进清单

- [ ] **数据准备**：整理一个包含“通用逻辑”和“特定知识”混合的测试集（如 ALFWorld 的 OOD 子集）。
- [ ] **原型开发**：编写一个简单的 Python 脚本，实现“难度路由器”逻辑（滑动窗口计算阈值）。
- [ ] **反事实探针实现**：在现有 LLM 调用中，增加一个“移除 Prompt 关键信息”的测试分支，验证 $p_i$ 和 $p_i^{none}$ 的差异。
- [ ] **基线对比**：复现 SkillRL（全外置）和 SKILL0（全内化）在本地小数据集上的表现，确立对比基准。
- [ ] **边界定义**：制定一套规则，用于自动判断新任务中的技能是“通用”还是“特定”（例如：基于 TF-IDF 或 Embedding 相似度）。
- [ ] **成本评估**：测算在 7B 模型上，引入 Skill0.5 逻辑后的训练时间增量，评估是否可接受。
