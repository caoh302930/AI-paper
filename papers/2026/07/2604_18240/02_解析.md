**Authors:** Wentao Shi, Yu Wang, Yuyang Zhao, et al. (USTC, NUS, Meituan)  
**Venue:** ACL 2026 (Projected/Preprint)

## TL;DR and contributions
这篇论文提出了 **AJ-Bench**，这是首个专门用于评测“裁判智能体”（Agent-as-a-Judge）的基准测试。它打破了传统裁判仅靠阅读文本进行判断的局限，要求裁判智能体必须**主动进入环境**（如搜索引擎、文件系统、图形界面），调用工具去“取证”，从而验证被评测智能体（Task-Solving Agent）的执行轨迹是否正确。实验表明，具备环境交互能力的裁判智能体，其判断准确率（F1 分数）比纯文本裁判（LLM-as-a-Judge）平均提升了 **13%**，且弱模型裁判在开启工具后能媲美强模型纯文本裁判的表现。

**Main contributions:**
- 构建了包含 155 个任务、516 条标注轨迹的 AJ-Bench 基准，覆盖搜索（Search）、数据系统（DS）和图形界面（GUI）三个领域。
- 首次系统性地定义了裁判智能体的三大核心能力：信息获取（Information Acquisition）、状态验证（State Verification）和过程验证（Process Verification）。
- 通过大规模实验证明，赋予裁判“行动权”（调用工具、访问环境）能显著提升判断的可靠性，揭示了纯文本裁判在复杂环境下的根本缺陷。
- 提供了详细的失败模式分析，指出当前裁判智能体在“误读工具输出”和“推理错误”方面仍存在主要瓶颈。

**Compared against:** LLM-as-a-Judge (纯文本裁判，无工具调用能力)
**On datasets:** AJ-Bench (Search: Mind2Web2/WideSearch; DS: MCPMark; GUI: OSWorld)
**Headline improvements:** Agent-as-a-Judge 相比 LLM-as-a-Judge 平均 F1 提升 **0.13** (从 0.59 提升至 0.72)；弱模型（gpt-5-mini-low）开启 Agent 模式后，性能超越强模型（如 gemini-2.5-pro）的纯文本模式。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** "Agent-as-a-Judge" 范式：裁判不再是被动的文本阅读器，而是主动的“侦探”。它必须通过调用工具（如搜索、读取文件、操作 GUI）来验证被评测者留下的“痕迹”是否真实。这是本文最核心的洞察。
- **🔧 Useful in practice:** 三个领域的任务设计细节（3.1 节）和轨迹构建方法（3.2 节）。特别是如何构建可复现的 GUI 和 DS 环境，以及如何通过“回放”机制让裁判进入环境，这对复现实验至关重要。
- **📎 Nice to know:** 消融实验（4.3 节）：关于“思考模式”（Thinking）和“交互轮数”（Interaction Turns）对裁判性能的影响。有趣的是，更强的推理能力并不总是带来更好的裁判表现，交互次数越多通常越好。
- **⚠️ Deprecated / superseded:** 传统的 LLM-as-a-Judge 在涉及事实核查和环境状态验证的任务中，其局限性已被本文充分暴露，未来研究应转向 Agent-as-a-Judge。
- **🔕 Skippable:** 详细的 Prompt 模板（Appendix A.11）除非你需要直接复现，否则只需了解其核心指令逻辑即可；部分统计表格（如 Table 2 的细分数据）可快速浏览。

## Context and prerequisites

要理解这篇论文，首先需要厘清 **LLM-as-a-Judge** 与 **Agent-as-a-Judge** 的本质区别。传统的 LLM-as-a-Judge 就像是一个只读文章的阅卷老师，它只能根据被评测者提交的“答卷”（文本轨迹）来判断对错。如果答卷里写“我查了谷歌，结果是 X"，老师只能凭自己的知识库判断 X 是否合理，或者根本不知道 X 是否真的存在。这在面对复杂环境（如网页搜索、数据库操作）时极易出错，因为老师无法“亲自去查”。

而 **Agent-as-a-Judge** 则像是一个拥有“调查权”的侦探。它不仅能读答卷，还能**亲自进入现场**。如果答卷说“文件已创建”，裁判智能体可以调用文件系统工具去读取该文件；如果答卷说“网页已打开”，裁判可以调用浏览器去截图验证。这种从“被动阅读”到“主动取证”的转变，是解决强化学习（RL）中奖励信号（Reward Signal）不可靠问题的关键。随着 LLM Agent 在长程任务中的能力增强，单纯依靠文本比对已无法准确评估其真实表现，必须引入环境感知能力。

此外，读者需理解 **Benchmark Construction（基准构建）** 中的“可复现性”挑战。在搜索和 GUI 领域，环境是动态变化的（网页内容会变，UI 状态会乱）。AJ-Bench 通过筛选“非时间敏感”任务、使用 MCPMark 等框架固化环境状态，并采用“轨迹回放”（Trajectory Replay）技术，确保了裁判智能体能在一个稳定的、可交互的虚拟环境中进行验证，这是实验能够成立的前提。

## Method

### The big picture (layman version)
想象一下，你要评估一个学生（Task-Solving Agent）是否真的完成了“去图书馆借书并整理成报告”的任务。
传统的评估方法（LLM-as-a-Judge）是：学生交给你一份报告，你只读报告，凭记忆判断他说的是不是真的。如果学生撒谎说“我借了《哈利波特》”，而你也记得有这本书，你就可能误判。
AJ-Bench 提出的新方法（Agent-as-a-Judge）是：你（裁判）不仅读报告，还**亲自去图书馆**。你可以打开电脑（GUI），连接图书馆数据库（DS），或者上网搜索（Search）。如果学生说“我借了书”，你就去系统里查借阅记录；如果他说“书在桌上”，你就去截图看桌面。
这个方法的核心在于：**裁判拥有“行动权”**。它不再依赖被评测者提供的信息是否诚实，而是通过自己的工具调用，独立获取证据，从而对任务的完成情况进行“取证式”判决。这解决了“黑盒验证”的难题，让评估结果更加客观、可信赖。

### The walkthrough
AJ-Bench 的方法论构建分为三个关键步骤：任务设计、轨迹收集与标注、以及裁判的评估流程。

**第一步：任务设计（Task Design）**
为了全面测试裁判的“取证”能力，作者设计了三个不同维度的领域，每个领域对应一种验证挑战：
1.  **搜索领域（Search Domain）：** 基于 Mind2Web2 和 WideSearch。挑战在于**信息获取**。裁判需要验证被评测者找到的信息（如电影上映日期）是否真实。这里的关键是裁判必须能调用浏览器工具，去访问链接或重新搜索，而不是仅靠内部知识。
2.  **数据系统领域（DS Domain）：** 基于 MCPMark（文件系统与 Postgres 数据库）。挑战在于**状态验证**。裁判需要检查文件是否被正确创建、修改，或者数据库记录是否更新。裁判必须能执行 `ls`, `cat`, `sql query` 等工具，直接读取环境状态。
3.  **图形界面领域（GUI Domain）：** 基于 OSWorld（PPT, Word, Excel）。挑战在于**过程与状态的双重验证**。裁判不仅要看到最终结果（图片是否在右侧），还要能通过回放轨迹或操作 GUI，确认操作过程是否合规。

**第二步：轨迹收集与标注（Trajectory Collection & Labeling）**
这是基准构建中最耗时的一步。作者收集了 516 条轨迹，分为成功（Positive）和失败（Negative）。
- **来源：** 结合了现有基准（如 OSWorld, MCPMark）的轨迹和重新生成的轨迹。
- **去偏：** 为了防止模型偏差，作者确保同一任务下的轨迹来自不同模型（如 Claude, GPT, Qwen 等）。
- **标注（Labeling）：** 采用二元标签（1/0）。
    - 在 Search 领域，标注细化到“单项”（Single-Item），即报告中的每一行数据都要验证。
    - 在 DS 和 GUI 领域，标注基于“轨迹级”（Trajectory-level），即整个任务是否完成。
    - **关键点：** 标注过程引入了人工复核和自动化脚本（如 MCPMark 的验证器），确保 Ground Truth 的准确性。

**第三步：裁判评估流程（Evaluation Pipeline）**
这是 Agent-as-a-Judge 的核心运行机制。
1.  **环境初始化：** 裁判智能体被部署在一个与任务描述一致的独立环境中（如一个空的文件系统或一个特定的网页）。
2.  **轨迹回放与交互：** 裁判首先读取被评测者的执行轨迹（Trajectory），了解对方做了什么。然后，裁判**主动调用工具**进行验证。
    - *例如：* 被评测者说“我创建了文件 `timeline.txt`"。裁判不会直接信，而是调用 `read_file` 工具去读取该文件，检查内容是否符合要求。
    - *例如：* 被评测者说“我找到了 2024 年上映的电影”。裁判会调用 `browser_navigate` 去访问提供的链接，或者使用搜索工具重新查询，对比日期。
3.  **判决生成：** 基于收集到的证据（工具返回的结果、截图、文件内容），裁判生成最终的判决（Pass/Fail）和理由。

**设计选择背后的逻辑：**
为什么选择 MCPMark 框架？因为 MCP (Model Context Protocol) 提供了标准化的工具接口，使得裁判可以无缝调用各种工具，而无需针对每个任务重写代码。
为什么强调“回放”？因为直接让裁判从零开始做任务太慢且成本高。回放被评测者的轨迹，让裁判站在“终点”去检查“过程”，既高效又能精准定位错误点。

## Challenges in the field — and what this work addresses

**挑战一：传统裁判的“幻觉”与“轻信”**
- **难点：** LLM-as-a-Judge 往往基于训练数据中的先验知识进行判断，或者被被评测者生成的“看似合理”的文本误导。在涉及实时数据（如新闻、股价）或特定环境状态（如文件内容）时，纯文本裁判极易产生幻觉，无法区分“编造的事实”和“真实的事实”。
- **本文对策：** AJ-Bench 强制裁判**进入环境**。通过工具调用（Tool Use），裁判获取的是“一手证据”而非“二手文本”。实验证明，这种机制显著降低了幻觉率，提升了 F1 分数。

**挑战二：复杂环境下的验证成本与可复现性**
- **难点：** 在 GUI 或搜索环境中，状态是动态变化的。今天能搜到的网页，明天可能 404；今天的文件操作，明天可能因系统更新而失败。构建一个稳定、可复现的评测环境极其困难。
- **本文对策：** 作者通过严格的任务筛选（剔除时间敏感任务）、利用 MCPMark 的标准化环境、以及采用“轨迹回放”技术（Replay），在保持环境动态性的同时，确保了评测过程的可控性和可复现性。

**挑战三：裁判自身的“能力天花板”**
- **难点：** 即使有了工具，裁判智能体本身也可能犯错。比如，它可能不知道如何正确使用工具，或者错误解读工具返回的结果（如把错误的数据当成正确的）。
- **本文对策：** 论文通过详细的失败模式分析（Failure Modes Analysis）揭示了这一点。研究发现，裁判的主要错误在于“误读工具输出”（Misinterpretation of tool outputs）和“推理错误”（Incorrect reasoning despite correct evidence）。这为未来的改进指明了方向：不仅要给裁判工具，还要提升其“工具理解力”和“逻辑推理力”。

**本文未解决的问题：**
- **任务多样性与扩展性：** 目前任务多基于现有基准修改，缺乏完全原创的复杂任务。
- **环境稳定性：** 搜索领域仍受网络波动影响，GUI 领域在极端复杂交互下仍可能存在状态不稳定的问题。

## Experiments and results

实验部分通过对比 **LLM-as-a-Judge**（纯文本）和 **Agent-as-a-Judge**（带工具）在不同模型上的表现，得出了以下关键数据：

1.  **整体性能提升：**
    - 在相同的基座模型下，开启 Agent 模式（调用工具）后，裁判的 F1 分数平均提升了 **0.13**（从约 0.59 提升至 0.72）。
    - 这一提升在所有三个领域（Search, DS, GUI）均显著存在。

2.  **弱模型 vs 强模型：**
    - 一个有趣的发现是：**弱模型 + Agent 模式 > 强模型 + 纯文本模式**。
    - 例如，`gpt-5-mini-low` 在开启 Agent 模式后，F1 达到 **72.41**，超过了 `gemini-2.5-pro`（强模型）纯文本模式的 **68.31**。
    - 这表明，**“行动能力”比单纯的“模型智力”在验证任务中更为关键**。

3.  **消融实验（Ablation Study）：**
    - **思考模式（Thinking）：** 增加推理轮次（Thinking）并不总是带来提升。对于 `gpt-5-mini`，中等推理强度效果最好；对于 `deepseek-v3.2`，开启 Thinking 反而性能下降。这说明裁判更需要的是“正确的工具调用策略”，而非过度的内部推理。
    - **交互轮数（Interaction Turns）：** 增加交互轮数（即允许裁判多问几次、多查几次）能显著提升 F1 分数，尤其是在 Word 和 PPT 等复杂 GUI 任务中。
    - **多模态输入（Multimodal）：** 在 GUI 领域，混合使用“截图”和“可访问性树（Accessibility Tree）”并不总是优于单一模态。例如在 Word 任务中，仅用截图效果更好；而在 Excel 中，混合模态最佳。这说明模态选择需适配具体任务。

4.  **失败模式分析：**
    - 主要错误类型包括：(a) 未调用必要工具（~4-20%）；(b) 调用错误工具（~2-3%）；(c) **误读工具输出**（~30-80%，最大痛点）；(d) 证据正确但推理错误（~10-60%）。
    - 数据表明，裁判智能体目前最大的瓶颈在于**理解工具返回的复杂信息**，而非工具调用本身。

## Open questions and limitations

1.  **工具理解的深度：** 实验显示裁判在“误读工具输出”上错误率极高。未来的研究需要探索如何让裁判更深刻地理解工具返回的原始数据（如复杂的 JSON、长文本日志），而不仅仅是表面匹配。
2.  **动态环境的泛化：** 目前基准主要依赖静态或半静态环境。对于完全动态、实时变化的环境（如实时股市、突发新闻），裁判的验证能力仍有待验证。
3.  **成本与效率的权衡：** Agent-as-a-Judge 需要多次调用工具和交互，推理成本远高于纯文本裁判。如何在保证准确性的前提下，优化交互策略（如自适应停止）是一个重要问题。
4.  **多模态的融合策略：** 实验表明混合模态并不总是最优。如何根据任务类型自动选择最佳模态组合（截图 vs 文本 vs 树结构）仍需探索。

## 与 B 站讲解的对照

- **视频强调点：** 视频标题和简介重点突出了“让裁判进环境取证”这一核心概念，并强调了美团、中科大等机构背景。视频可能通过直观的案例（如“裁判去查网页”）来解释 Agent-as-a-Judge 的优势，这非常符合 Feynman 技巧，帮助观众快速建立直觉。
- **可能的简化/遗漏：**
    - **细节缺失：** 视频可能未深入探讨三个领域（Search, DS, GUI）的具体构建差异，以及“轨迹回放”这一技术细节的重要性。
    - **数据深度：** 视频可能只展示了“提升 13%"这一 headline 数据，而忽略了消融实验中关于“思考模式”和“多模态”的复杂发现（如 Thinking 有时反而有害）。

    - **基准构建难度：** 视频可能未强调构建可复现环境（特别是 GUI 和 DS）的巨大工程挑战，这往往是复现此类工作的最大难点。
