# 可以做什么：基于 STS 的 LLM 微调预判与防御实战

## 可迁移到的场景

1.  **垂直领域 SFT 前的“副作用”评估**
    *   **场景**：医疗、法律、金融等强专业领域微调。
    *   **痛点**：微调医疗数据后，模型可能突然无法回答通用常识或丧失代码能力（灾难性遗忘）。
    *   **应用**：在正式训练前，用 STS 扫描目标微调数据对“通用能力”、“代码能力”、“逻辑推理”等维度的潜在冲击。如果 STS 分数过高，自动预警并建议增加通用数据配比。

2.  **动态数据混合（Data Mixture）策略优化**
    *   **场景**：构建多任务微调数据集（如同时微调客服、写作、编程）。
    *   **痛点**：人工经验难以平衡不同任务数据的比例，容易导致模型“顾此失彼”。
    *   **应用**：计算各任务子集对核心能力（如通用指令遵循）的 STS 分数。根据分数反比分配数据量：STS 高的任务（破坏力大）减少采样，STS 低的任务（安全）增加采样，实现“无损”多任务学习。

3.  **模型能力“体检”与基线选择**
    *   **场景**：企业选型，决定在哪个基座模型（Llama3 vs Qwen）上微调特定业务。
    *   **痛点**：不同基座模型内部特征解耦程度不同，对同一微调任务的敏感度不同。
    *   **应用**：对候选基座模型分别运行 STS 测试。选择 STS 分数较低（即微调对其跨领域能力影响较小）的模型作为基座，降低微调风险。

4.  **RLHF/DPO 前的预筛选（需变通）**
    *   **场景**：准备进行偏好对齐（RLHF）或直接偏好优化（DPO）。
    *   **痛点**：RL 没有 Ground Truth，无法直接套用 STS。
    *   **应用**：利用 STS 筛选出的“敏感特征维度”，在构建偏好对（Prompt, Chosen, Rejected）时，人工或自动检查这些维度在“拒绝样本”中是否被过度激活。或者，用 SFT 模拟 RL 的指令部分，预判 RL 可能引发的能力崩塌点，提前在偏好数据中加入“保护性样本”。

## 可立刻试的小实验

### 实验 1：微调前的“副作用”预测
*   **输入**：
    *   基座模型：`Qwen2.5-7B-Instruct` (或 HuggingFace 可访问的开源模型)。
    *   微调数据集：100 条数学推理数据（如 GSM8K 子集）。
    *   待测领域：100 条法律问答数据（如 CAIL 子集）。
    *   SAE 模型：加载该模型对应的开源 SAE（如 `gemma-scope` 或针对 Qwen 训练的 SAE）。
*   **步骤**：
    1.  **模拟微调**：将数学数据作为 ICL Prompt（含答案）输入模型，提取 SAE 特征，计算 Top-50 变化最大的维度 $D_{math}$。
    2.  **计算 STS**：将法律数据输入模型，计算其在 $D_{math}$ 维度上的平均激活值 ($STS_{act}$) 或 ICL 扰动值 ($STS_{ICL}$)。
    3.  **真实微调**：用数学数据对模型进行 1 轮 SFT（或 LoRA 微调）。
    4.  **验证**：在微调后的模型上测试法律数据，记录准确率变化 $\Delta Acc$。
*   **期望输出**：
    *   STS 分数与 $\Delta Acc$ 呈显著负相关（例如：STS 越高，法律准确率下降越多）。
    *   若 STS 接近 0，则微调后法律能力基本无损。

### 实验 2：数据混合比例自动调整
*   **输入**：
    *   两个微调子集：A（高难度代码，预计破坏通用性），B（通用对话，预计安全）。
    *   目标：保持通用能力不下降。
*   **步骤**：
    1.  分别计算 A 和 B 对“通用指令遵循”能力的 STS 分数（$S_A, S_B$）。
    2.  设定混合策略：$Ratio_A : Ratio_B = 1/S_A : 1/S_B$（分数越高，比例越低）。
    3.  构建两个数据集：
        *   **对照组**：A:B = 1:1。
        *   **实验组**：按 STS 反比混合。
    4.  分别微调模型并测试通用能力（如 MMLU 子集）。
*   **期望输出**：
    *   实验组在通用能力上的保留率显著高于对照组，同时 A 任务（代码）性能未受明显影响。

### 实验 3：SAE 单义性对预测精度的影响（消融验证）
*   **输入**：
    *   同一模型的两个不同 SAE 版本：
        *   版本 1：高稀疏度（L0 范数低，单义性强）。
        *   版本 2：低稀疏度（L0 范数高，接近多义性）。
    *   微调任务：健康对话微调。
*   **步骤**：
    1.  分别用两个 SAE 提取微调模拟后的特征漂移维度。
    2.  计算下游“代码能力”的 STS 分数。
    3.  对比两者与真实性能变化的相关性（Pearson Correlation）。
*   **期望输出**：
    *   版本 1（高单义性）的相关系数 > 0.7。
    *   版本 2（低单义性）的相关系数 < 0.2（验证论文中 SAE 必要性的结论）。

## 产品 / Agent 灵感

1.  **LLM 微调“保险丝”插件 (Fine-tuning Fuse)**
    *   **功能**：一个嵌入在微调流程（如 Axolotl, LLaMA-Factory）中的插件。
    *   **机制**：用户上传微调数据后，插件自动运行 STS 分析，生成“风险报告”。
    *   **价值**：如果检测到对核心能力（如安全、通用推理）的 STS 分数过高，自动建议调整数据配比或增加正则化参数，甚至直接阻止高风险训练启动。

2.  **智能数据清洗与配比 Agent**
    *   **功能**：针对企业私有数据清洗 Agent。
    *   **机制**：在数据入库前，计算每条数据对模型现有能力的“潜在破坏力”。
    *   **价值**：自动构建“安全微调数据集”，剔除那些虽然任务相关但会剧烈破坏模型其他能力的“有毒”数据，或自动插入保护性样本。

3.  **模型能力迁移评估平台 (Transferability Dashboard)**
    *   **功能**：面向模型即服务 (MaaS) 提供商的 SaaS 工具。
    *   **机制**：客户输入微调需求，平台基于 STS 快速输出预测曲线：“微调此任务后，您的模型在 X、Y、Z 领域的表现预计变化为..."。
    *   **价值**：降低客户试错成本，提供可量化的微调 ROI 预测。

## 跟现有系统怎么接

1.  **接入 SAE 推理层**
    *   需要集成 `saes` 库或 HuggingFace 上预训练的 SAE 模型（如 `gemma-scope`）。
    *   **接口**：`model(input_ids) -> hidden_states` -> `sae(hidden_states) -> feature_activations`。
    *   **注意**：需确保 SAE 的层数选择（论文通常关注中间层，如 Llama 的 L10-L15），建议封装为统一接口。

2.  **集成到微调框架 (LLaMA-Factory / Axolotl)**
    *   **Hook 点**：在 `DataLoader` 阶段或 `TrainingArguments` 初始化阶段插入 STS 计算脚本。
    *   **流程**：
        1.  读取训练数据 -> 构建 ICL Prompt。
        2.  运行前向传播（不更新权重） -> 提取特征变化。
        3.  计算 STS -> 输出 JSON 报告。
        4.  (可选) 根据报告动态修改 `train_data` 的采样权重。

3.  **可视化与监控**
    *   将 STS 分数映射到 TensorBoard 或 WandB。
    *   展示维度热力图：横轴为下游领域，纵轴为微调任务，颜色深浅代表 STS 分数（潜在影响大小）。

## 风险与坑

1.  **SAE 质量依赖（致命坑）**
    *   如果 SAE 训练质量差（特征不稀疏、概念纠缠），STS 将完全失效（相关性趋近于 0）。
    *   **对策**：必须先验证 SAE 的单义性指标（如 Top-K 激活占比、特征解释性），不要盲目使用未经验证的 SAE。

2.  **RL/无监督场景失效**
    *   STS 强依赖 Ground Truth 答案构建 ICL Prompt。在 RLHF、DPO 或纯无监督预训练中，无法直接应用。
    *   **对策**：目前只能用于 SFT 场景。对于 RL，需探索用“人工构造的标准答案”或“高置信度生成样本”作为替代 Prompt，但效果存疑。

3.  **计算成本与延迟**
    *   虽然比 SFT 快，但需要多次前向传播（ICL 模拟 + 下游激活），对于 70B+ 模型，推理成本依然显著。
    *   **对策**：仅对数据子集（Sample）进行计算，或使用量化后的模型进行 STS 评估（需验证量化对 SAE 激活的影响）。

4.  **负迁移方向的不确定性**
    *   STS 预测的是“变化幅度”，虽然实验中多为负迁移，但理论上无法 100% 保证是“下降”而非“提升”（尽管 SFT 通常导致过拟合和遗忘）。
    *   **对策**：将 STS 视为“风险预警”而非“绝对预测”，结合少量验证集（Few-shot）进行二次确认。
