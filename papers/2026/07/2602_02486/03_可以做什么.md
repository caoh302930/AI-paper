# 可以做什么：RE-TRAC 工程化落地指南

基于 RE-TRAC 的核心洞察——**将线性轨迹压缩为结构化状态，实现跨轮次的渐进式学习**，以下是可直接落地的执行方案。

## 可迁移到的场景

1.  **复杂信息检索与深度研报生成 (Deep Research)**
    *   **痛点**：传统 Agent 在搜索 10+ 个网页后，忘记最初的假设或遗漏了计划中的分支（如“查 A 公司财报”但只查了“新闻”）。
    *   **应用**：构建“多轮迭代研究员”。每轮搜索结束后，强制生成包含 `Verified Facts`（已验证事实）、`Failed Paths`（无效搜索词/死胡同）、`Pending Hypotheses`（待验证假设）的状态卡。下一轮直接基于状态卡续写，而非重新读取全部历史。

2.  **长周期代码调试与重构 (Long-horizon Debugging)**
    *   **痛点**：修复深层 Bug 时，Agent 尝试了方案 A 失败后，下一轮尝试 B 时又重复了方案 A 的错误，或者忘记了方案 A 中部分有效的代码片段。
    *   **应用**：将代码修改历史压缩为 `Code State`。记录：`Working Changes`（生效修改）、`Rejected Changes`（导致报错的修改及原因）、`Unexplored Modules`（尚未检查的依赖文件）。Agent 基于此状态进行下一轮 Patch，避免“原地打转”。

3.  **多轮法律/合规审查 (Legal Compliance Review)**
    *   **痛点**：审查长合同或法规时，Agent 容易在长篇大论中遗漏前文定义的“关键定义”或“例外条款”。
    *   **应用**：建立 `Legal State` 结构。字段包括：`Defined Terms`（已定义术语）、`Contradictions Found`（发现的条款冲突）、`Missing Clauses`（根据法规要求但未在合同中找到的条款）。每轮审查更新状态，确保审查逻辑的连贯性。

4.  **游戏 NPC 长期记忆与任务规划 (Game NPC Memory)**
    *   **痛点**：开放世界游戏中，NPC 执行长任务链（如“寻找失落的宝藏”）时，容易因对话过长而遗忘任务目标或重复询问玩家已知信息。
    *   **应用**：将 NPC 的对话和探索轨迹压缩为 `Mission State`。记录：`Known Locations`（已探索地点）、`False Leads`（误导线索）、`Next Priority`（下一步高优先级行动）。NPC 基于此状态与玩家互动，表现出“记得之前经历”的智能感。

## 可立刻试的小实验

### 实验 1：对比“独立重试”与“状态递归”的 Token 效率
*   **目标**：验证 RE-TRAC 是否真的能减少冗余调用。
*   **输入**：一个需要多步搜索的复杂问题（例如：“找出 2023 年某特定小众科技初创公司的创始人背景，并确认其是否获得过 A 轮融资”）。
*   **步骤**：
    1.  **基线组 (Baseline)**：让模型独立运行 3 次（Pass@3），每次都是从头开始搜索，最后投票取结果。记录总 Token 消耗和工具调用次数。
    2.  **RE-TRAC 组**：
        *   第 1 轮：正常搜索，结束后输出结构化状态（JSON 格式：`{facts, failures, pending}`）。
        *   第 2 轮：输入 `Prompt + 上一轮状态`，指示模型“基于未完成的 pending 项继续搜索”。
        *   第 3 轮：同上。
    3.  对比两组达到相同准确率时的总消耗。
*   **期望输出**：RE-TRAC 组在达到同等或更高准确率时，总 Token 和工具调用次数应显著低于基线组（预期减少 30-50%）。

### 实验 2：手动构造“失败路径”注入，测试模型避坑能力
*   **目标**：验证 `Failed Attempts` 字段是否能有效防止模型重复错误。
*   **输入**：一个已知容易误导的搜索任务（例如：搜索一个不存在的“某公司 2025 年财报”，模型容易幻觉）。
*   **步骤**：
    1.  构造一个初始状态 $S_0$，其中 `Failed Attempts` 字段明确写入：“尝试搜索 'Company X 2025 Annual Report' 失败，因为该公司 2025 年尚未结束，且官网无此页面。”
    2.  将 $S_0$ 作为第 1 轮输入，指令模型：“基于此状态，寻找替代信息源（如 2024 年报或新闻）。”
    3.  观察模型是否还会尝试搜索 "2025 Annual Report"。
*   **期望输出**：模型应直接跳过 2025 年报的搜索，转而搜索 2024 年报或相关新闻，证明其读取并利用了“失败记录”。

### 实验 3：小模型 (4B-7B) + RE-TRAC SFT 模拟
*   **目标**：验证小模型是否必须经过“状态理解”微调才能生效。
*   **输入**：使用 Qwen2.5-7B-Instruct 或类似小模型。
*   **步骤**：
    1.  **未微调**：直接让小模型执行 RE-TRAC 流程（输入状态卡，要求续写）。观察其是否能正确解析 JSON 状态并规划下一步。
    2.  **模拟微调**：构造 10 条“状态卡 -> 正确行动”的 Few-Shot 示例，放入 System Prompt 中（模拟 SFT 效果）。
    3.  对比两者的规划逻辑连贯性。
*   **期望输出**：未微调模型可能忽略状态卡中的 `pending` 字段或格式混乱；Few-Shot 后应能清晰识别“未完成任务”并执行对应动作。

## 产品 / Agent 灵感

1.  **“侦探模式”搜索助手**
    *   **功能**：用户侧不展示冗长的搜索历史，而是展示一个动态更新的“案件档案”（Case File）。
    *   **亮点**：档案中明确列出“已排除嫌疑人”（失败尝试）和“待核实线索”（未探索分支）。用户可随时点击“重新调查”并基于当前档案继续，而非重新开始。
    *   **价值**：解决用户“搜着搜着就忘了之前查过什么”的焦虑，提供可控的长程推理体验。

2.  **自适应调试 Agent (Self-Healing CI/CD)**
    *   **功能**：在 CI/CD 流水线中，当构建失败时，Agent 自动进入 RE-TRAC 模式。
    *   **亮点**：第一轮尝试修复后，无论成功失败，生成 `Debug State`。如果失败，第二轮自动读取“失败原因”和“已尝试方案”，避免重复提交相同的 Patch。
    *   **价值**：大幅减少无效的代码提交次数，缩短修复 MTTR (Mean Time To Repair)。

3.  **长程任务规划器 (Project Manager Agent)**
    *   **功能**：管理跨周的项目任务。
    *   **亮点**：每天结束时，Agent 自动压缩当天的沟通、代码提交、文档更新为 `Daily State`。第二天启动时，直接加载昨日状态，自动识别“昨日未完成”和“今日新风险”。
    *   **价值**：让 AI 项目经理具备“连续记忆”，无需人类每天重新同步背景。

## 跟现有系统怎么接

1.  **中间件层 (Middleware Layer)**
    *   在现有的 Agent 框架（如 LangChain, AutoGen, Dify）中插入一个 `StateCompressor` 节点。
    *   **流程**：`Tool Execution` -> `StateCompressor` (生成 JSON) -> `Context Pruner` (丢弃原始长历史) -> `Next Turn Prompt`。
    *   **关键点**：确保 `StateCompressor` 的 Prompt 严格遵循论文中的 7 字段结构（Facts, Evidence, Uncertainties, Failed Attempts, Uncompleted Proposals, Discarded Possibilities, Next Steps）。

2.  **向量数据库 (Vector DB) 的替代/补充**
    *   不要单纯依赖 RAG 检索历史。将 RE-TRAC 生成的 `State` 作为**元数据 (Metadata)** 或 **系统级上下文 (System Context)** 直接注入。
    *   **策略**：对于短轮次任务，直接用 State 替换长上下文；对于超长任务，将 State 存入 DB，每次只检索与当前任务最相关的 State 片段。

3.  **微调数据流水线 (SFT Pipeline)**
    *   如果自有模型较小，需建立数据合成管线：
        *   利用大模型（如 GPT-4o/GLM-4）生成“问题 -> 多轮搜索轨迹 -> 结构化状态”的三元组数据。
        *   重点合成 `Failed Attempts` 和 `Uncompleted Proposals` 的样本，训练小模型学会“承认错误”和“规划遗漏”。

## 风险与坑

1.  **状态幻觉 (State Hallucination)**
    *   **风险**：如果压缩器（Summarizer）在生成 $S_t$ 时产生幻觉（例如编造了一个不存在的失败原因），后续所有轮次都会基于错误前提执行，导致“错误累积”。
    *   **对策**：在 Prompt 中加入“批判性评估”指令（如论文 Figure 11），强制模型质疑 $S_{t-1}$ 中的内容；或者引入一个独立的“审计模型”专门校验 State 的准确性。

2.  **状态膨胀 (State Bloat)**
    *   **风险**：随着轮次增加，`Uncompleted Proposals` 和 `Pending Hypotheses` 可能无限堆积，导致 $S_t$ 本身变得过大，超出小模型的上下文窗口。
    *   **对策**：设计**状态剪枝机制**。例如，每 3 轮强制合并相似假设，或根据置信度丢弃低优先级分支。

3.  **过度依赖 (Over-reliance)**
    *   **风险**：模型可能变得“懒惰”，完全照搬 $S_{t-1}$ 中的计划，不再进行新的探索，陷入局部最优。
    *   **对策**：在 Continuation Prompt 中明确加入“鼓励探索”和“允许推翻旧结论”的指令权重，如论文所示，这是性能提升的关键。

4.  **小模型能力断层**
    *   **风险**：直接用 RE-TRAC 框架跑 4B/7B 模型，效果可能不如基线（如实验 3 所示），因为小模型无法理解复杂的状态结构。
    *   **对策**：必须先进行针对性的 SFT，或者使用“大模型压缩 + 小模型执行”的混合架构（Teacher-Student）。
