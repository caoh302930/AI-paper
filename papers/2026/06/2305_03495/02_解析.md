**Authors:** Reid Pryzant, Dan Iter, Jerry Li, Yin Tat Lee, Chenguang Zhu, Michael Zeng  
**Venue:** EMNLP 2023 (Early Access / arXiv 2023)  
**Organization(s):** Microsoft Azure AI  
**arXiv:** [2305.03495](https://arxiv.org/abs/2305.03495)

## TL;DR and contributions
这篇论文提出了一种名为 **ProTeGi** (Prompt Optimization with Textual Gradients) 的框架，旨在解决大语言模型（LLM）提示词（Prompt）编写依赖人工试错的问题。它不修改模型参数，而是通过模拟“梯度下降”的过程，利用 LLM 自身生成自然语言的“梯度”（即对当前提示词错误的自然语言批评），并据此迭代优化提示词，同时结合束搜索（Beam Search）和老虎机算法（Bandit）来高效筛选候选提示词。

**Main contributions:**
- 提出了 **ProTeGi** 算法，将连续空间的梯度下降思想映射到离散的自然语言提示词优化中，无需访问模型内部梯度。
- 设计了基于自然语言反馈的“梯度”生成与编辑机制，通过 $\nabla$（生成批评）和 $\delta$（执行修改）两个 LLM 提示步骤实现定向搜索。
- 引入束搜索（Beam Search）作为外层循环，并利用多臂老虎机（Multi-armed Bandit，如 UCB、Successive Rejects）策略高效评估候选提示词，显著减少 API 调用成本。
- 在四个 NLP 任务（包括新颖的越狱检测任务）上验证了有效性，相比初始提示词性能提升最高达 31%，优于现有的蒙特卡洛搜索和强化学习基线。

**Compared against:** Monte-Carlo (MC) search (Zhou et al. 2022), Reinforcement Learning (RL) based methods (GRIPS, TEMPERA), AutoGPT, Evolutionary Search.
**On datasets:** Jailbreak detection (452 examples), Ethos (Hate speech, 997 examples), Liar (Fake news, 4000 examples), Sarcasm (Arabic, 10,000 examples).
**Headline improvements:** 平均提升初始提示词性能 **15.3%**；相比蒙特卡洛搜索提升 **3.9%**，相比强化学习基线提升 **8.2%**；在 Jailbreak 任务上，Beam Search 版本比贪婪搜索提升显著（F1 从 0.82 提升至 0.85）。

## Context and prerequisites

要真正读懂这篇论文，你需要理解三个关键概念，它们构成了 ProTeGi 的基石。

首先是**提示词工程（Prompt Engineering）的痛点**。在大模型时代，模型能力虽然强大，但极度依赖输入提示词的质量。传统的提示词编写是一个“黑盒试错”过程：人类工程师写一个提示词，跑数据，看结果，如果不理想就凭直觉修改，再跑，再改。这个过程耗时耗力，且难以保证找到最优解。现有的自动优化方法要么需要访问模型内部参数（如软提示 Soft Prompts），这在实际 API 调用中不可行；要么是基于无方向的随机搜索（如蒙特卡洛），效率低下且容易陷入局部最优。

其次是**梯度下降（Gradient Descent）的本质**。在传统的深度学习中，梯度下降通过计算损失函数对参数的导数，告诉我们在参数空间中哪个方向能让损失最小。然而，提示词是离散的文本序列，无法直接求导。这篇论文的巧妙之处在于，它**重新定义了“梯度”**：它不再是一个数值向量，而是一段**自然语言描述**，这段描述指出了当前提示词在哪些具体样本上失败了，以及*为什么*会失败。这就把“数值梯度”转化为了“语义梯度”。

最后是**束搜索（Beam Search）与多臂老虎机（Bandit）**。由于提示词空间是巨大的，我们无法穷举所有可能的修改。束搜索允许我们在每一步保留多个（Beam width）最有希望的候选提示词，而不是只保留一个（贪婪搜索），从而增加了探索到全局最优解的概率。但是，评估每一个候选提示词都需要调用昂贵的 LLM API，因此不能对所有候选进行全量测试。这就引入了多臂老虎机问题：如何在有限的“拉闸”次数（API 调用预算）内，最快地找出表现最好的那一个提示词？论文通过 UCB 或 Successive Rejects 算法，在“探索”（测试表现未知的提示词）和“利用”（测试当前表现最好的提示词）之间取得了平衡。

## Method

### The big picture (layman version)

想象你在教一个学生（LLM）做数学题，但他总是做错。传统的做法是你直接告诉他答案，或者让他自己瞎猜。ProTeGi 的做法是：你让他先做一批题，然后让他自己**写一份“错题分析报告”**（这就是“自然语言梯度”），告诉他哪里错了、为什么错。接着，你让他根据这份报告**修改他的解题思路**（即修改提示词），生成几个新的解题版本。为了不让他在错误的道路上走太远，你让他保留几个看起来最有希望的版本（束搜索），并只挑选其中几个进行小规模的测试（老虎机策略），选出最好的那个进入下一轮。这个过程循环往复，直到他的解题思路（提示词）变得非常精准。

简单来说，ProTeGi 就是把“梯度下降”中的“计算导数”替换成了"LLM 生成错误分析”，把“参数更新”替换成了"LLM 根据分析修改提示词”，并配合高效的搜索策略，在不需要修改模型权重的情况下，自动把提示词越改越好。

### The walkthrough

让我们深入拆解 ProTeGi 的运作流程。整个算法是一个迭代优化的过程，核心循环包含两个主要阶段：**扩展（Expansion）**和**选择（Selection）**。

#### 1. 扩展阶段：模拟梯度下降
这是算法最核心的部分，旨在生成新的候选提示词。假设当前提示词为 $p$，我们有一批训练数据 $\mathcal{D}_{tr}$。

**第一步：收集错误（Collect Errors）**
我们随机采样一个小批量（minibatch）的数据，用当前提示词 $p$ 去跑，记录下所有预测错误的样本集合 $e$。
$$ e = \{ (x_i, y_i) \mid LLM_p(x_i) \neq y_i \} $$
这里 $x_i$ 是输入，$y_i$ 是真实标签。这一步相当于计算损失，但我们是直接看结果对不对。

**第二步：生成“文本梯度”（Generate Textual Gradients）**
这是本文的点睛之笔。我们将当前提示词 $p$ 和错误集合 $e$ 输入给一个专门的 LLM 提示 $\nabla$（Gradient Prompt）。这个提示词的任务是：“请分析为什么当前的提示词 $p$ 会导致这些错误 $e$？”
$$ \{g_1, g_2, \dots, g_m\} = LLM_{\nabla}(p, e) $$
生成的 $g_i$ 不是数字，而是一段自然语言，例如：“提示词过于关注字面匹配，忽略了上下文中的讽刺语气”或者“提示词没有明确区分‘仇恨言论’和‘宗教批评’"。这些 $g_i$ 就是我们在语义空间中的“梯度”，它们指出了当前提示词的缺陷方向。

**第三步：执行“反向更新”（Edit Prompt）**
有了梯度 $g_i$，我们需要沿着“相反方向”修改提示词。我们使用另一个 LLM 提示 $\delta$（Edit Prompt），输入当前提示词 $p$ 和梯度 $g_i$，要求 LLM 修改 $p$ 以修复 $g_i$ 中指出的问题。
$$ \{p'_{i1}, \dots, p'_{iq}\} = LLM_{\delta}(p, g_i, e) $$
这一步生成了 $q$ 个改进后的候选提示词。注意，这里 LLM 不仅是在修改，而是在进行“语义推理”，它需要理解错误原因并重构指令。

**第四步：局部蒙特卡洛探索（Monte Carlo Exploration）**
为了防止 LLM 的修改过于激进或陷入局部最优，我们还会对生成的新提示词 $p'$ 进行同义改写（Paraphrasing）。使用一个专门的改写模型 $LLM_{mc}$，生成语义相同但措辞不同的变体：
$$ \{p''_{ijk}\} = LLM_{mc}(p'_{ij}) $$
这一步增加了搜索的多样性，相当于在梯度下降的“下降方向”附近进行小范围的随机扰动。

#### 2. 选择阶段：高效筛选
经过扩展，我们可能得到了几十个候选提示词。如果直接对每个候选在全部训练集上测试，API 成本会爆炸。因此，我们需要一个高效的筛选机制。

论文将这个问题建模为**多臂老虎机（Multi-armed Bandit）**问题中的“最佳臂识别”（Best Arm Identification）。
- **臂（Arm）：** 每一个候选提示词。
- **奖励（Reward）：** 提示词在随机采样数据上的表现（如 F1 分数）。
- **目标：** 用最少的采样次数，找出表现最好的 $b$ 个提示词（即束宽）。

论文对比了两种策略：
1.  **UCB (Upper Confidence Bound):** 经典的平衡探索与利用的算法。它倾向于选择当前平均表现好，或者被测试次数少（不确定性高）的提示词。
    $$ \text{Score}(p) = Q_t(p) + c \sqrt{\frac{\log t}{N_t(p)}} $$
    其中 $Q_t(p)$ 是估计的平均得分，$N_t(p)$ 是测试次数，$c$ 是探索参数。
2.  **Successive Rejects (SR):** 一种无超参数的算法。它将候选集分成若干轮，每轮测试所有剩余候选，然后直接淘汰得分最低的那个，直到剩下最好的几个。

实验表明，虽然理论上 SR 更优，但在实际 LLM 任务中，**UCB 及其变体（UCB-E）**往往表现更好，因为它们能更好地适应 LLM 输出的高方差特性。

最终，算法保留得分最高的 $b$ 个提示词进入下一轮迭代，直到达到最大迭代次数 $r$。

## Challenges in the field — and what this work addresses

**挑战一：离散空间的优化难题**
*为什么难？* 传统的梯度下降依赖连续可微的函数空间。提示词是离散的文本，无法计算导数。现有的方法要么需要访问模型内部（不可行），要么只能做无方向的随机搜索（效率低）。
*本文方案：* ProTeGi 创造性地用**自然语言反馈**替代了数值梯度。通过让 LLM 自己“反思”错误，生成语义上的“梯度”，从而实现了在离散文本空间中的**定向搜索**。这解决了“如何知道往哪个方向改”的核心问题。

**挑战二：搜索空间巨大与评估成本高昂**
*为什么难？* 提示词的修改组合是天文数字。如果对每个候选都进行全量评估，API 调用成本将不可接受。
*本文方案：* 引入**束搜索**结合**多臂老虎机**。束搜索保证了不丢失潜在的优质路径（避免贪婪搜索的早熟），而老虎机算法（如 UCB）通过智能分配评估预算，用极少的采样次数就能筛选出高质量的候选，大幅降低了计算成本。

**挑战三：提示词优化的可解释性与可控性**
*为什么难？* 许多自动优化方法（如强化学习）生成的提示词往往是乱码或不可读的句子片段，人类无法理解优化逻辑。
*本文方案：* ProTeGi 生成的每一步修改都是基于自然语言的“错误分析”，因此优化过程是**可解释的**。人类可以阅读“梯度”文本，理解模型为什么认为当前提示词不好，以及它是如何被修正的。

**本文未解决的问题：**
- **效率瓶颈：** 尽管使用了老虎机，但每一轮仍需多次调用 LLM 生成梯度和编辑提示词，对于超大规模数据集或实时应用，延迟依然较高。
- **局部最优与过拟合：** 实验显示，优化过程在 3-4 步后容易过拟合训练数据或陷入局部最优，如何设计自适应的“学习率”或早停机制仍需探索。

## Experiments and results

论文在四个任务上进行了验证，结果具有说服力：

1.  **整体性能提升：**
    - 相比初始提示词（No iteration），ProTeGi 平均提升了 **15.3%** 的 F1 分数。
    - 相比最强的基线（蒙特卡洛搜索 MC），平均提升 **3.9%**。
    - 相比基于强化学习的基线（RL），平均提升 **8.2%**。
    - 在特定任务（如 Jailbreak 检测）上，性能提升甚至达到了 **31%**。

2.  **消融实验（Ablation Study）：**
    - **束搜索 vs 贪婪搜索：** 在 Jailbreak 任务上，束搜索（Beam）F1 为 **0.85**，而贪婪搜索（Greedy）仅为 **0.82**，无迭代（No iteration）为 **0.80**。这证明了保留多个候选路径的重要性。
    - **老虎机算法对比：** 在 Liar 和 Jailbreak 任务上，UCB 和 UCB-E 的表现普遍优于 Successive Rejects (SR) 和 Successive Halving (SH)。例如在 Jailbreak (25 queries) 上，UCB 达到 **0.83**，而 SR 仅为 **0.81**。这表明在 LLM 高方差环境下，UCB 的探索策略更稳健。

3.  **基线模型影响：**
    - 使用更强的基座模型（如 GPT-4）作为优化器时，ProTeGi 的效果显著提升。GPT-4 优化的 Jailbreak 检测 F1 达到 **0.88**，而 GPT-3 仅为 **0.55**。这说明“梯度”生成的质量高度依赖于优化器（LLM）本身的推理能力。

4.  **学习曲线：**
    - 性能通常在 **3 步** 左右达到峰值，之后趋于平稳甚至下降（过拟合）。这提示我们在实际应用中应限制迭代次数。

## Open questions and limitations

1.  **过拟合风险：** 实验显示优化过程容易在 3-4 步后过拟合训练集。如何引入正则化或验证集机制来防止“过度优化”是一个开放问题。
2.  **计算成本：** 尽管比全量搜索高效，但 ProTeGi 仍然需要大量的 LLM API 调用（生成梯度、编辑、评估）。在资源受限场景下，如何进一步压缩成本？
3.  **任务泛化性：** 论文仅在分类任务上验证。对于生成式任务（如写作、代码生成），其评估指标（如 F1）难以定义，ProTeGi 的“梯度”生成机制是否依然有效？
4.  **梯度质量依赖：** 优化效果高度依赖于优化器（LLM）生成“梯度”的质量。如果优化器本身无法准确识别错误，整个优化链条就会失效。
