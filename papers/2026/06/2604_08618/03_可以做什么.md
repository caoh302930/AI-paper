# 可以做什么

基于 SkillForge 的“失败归因 - 根因诊断 - 最小修改”闭环，核心在于**将 Agent 的优化对象从“模型参数”或“模糊 Prompt"转变为“结构化技能文件（Skill Artifact）”**。这允许我们在不重新训练模型的前提下，通过迭代“剧本”来持续提升业务表现。

以下是基于该论文逻辑的务实落地方案：

## 可迁移到的场景（≥4）

1.  **企业 IT 运维与故障排查 (IT Ops)**
    *   **痛点**：故障场景千变万化，通用模型常给出泛泛而谈的“重启试试”，缺乏针对特定架构（如 K8s 集群、特定数据库版本）的精准排查步骤。
    *   **应用**：构建 `Troubleshooting_Skill.md`。利用历史工单挖掘“现象 - 工具 - 解决”路径。当 Agent 排查失败时，归因是“缺少特定日志分析指令”还是“工具参数错误”，自动更新技能文件中的排查流程图。

2.  **合规与风控审核助手 (Compliance Agent)**
    *   **痛点**：法规更新快，审核规则复杂，人工编写规则库滞后且易出错。
    *   **应用**：将审核逻辑封装为 `Compliance_Skill.md`。当 Agent 误判（漏放或误杀）时，归因是“知识缺失（新法规未覆盖）”还是“逻辑冲突”。系统自动在技能文件中插入新的“例外条款”或修正判断逻辑，而非微调模型。

3.  **垂直领域销售/咨询顾问 (Sales Consultant)**
    *   **痛点**：销售话术需要根据客户反馈动态调整，但人工培训周期长，标准化难。
    *   **应用**：定义 `Sales_Playbook.md`。分析对话录音，若 Agent 在“异议处理”环节失败，归因为“澄清不足”或“价值传递风格生硬”。自动优化话术模板，生成针对特定行业（如 SaaS、制造业）的专属销售剧本。

4.  **代码审查与重构助手 (Code Review Agent)**
    *   **痛点**：代码规范（Linting）是静态的，但架构设计原则（如“避免循环依赖”）难以通过 Prompt 完全约束。
    *   **应用**：构建 `Code_Review_Skill.md`。当 Agent 未能发现深层架构问题或给出错误重构建议时，归因是“缺乏特定设计模式知识”或“工具调用（如静态分析）参数错误”。自动在技能文件中补充新的“反模式检查清单”。

## 可立刻试的小实验（≥3）

### 实验一：构建“失败归因”原型机
*   **输入**：3-5 个真实的 Agent 失败案例（包含：用户问题、Agent 回答、专家正确回答、失败原因简述）。
*   **步骤**：
    1.  准备一个 Prompt，让 LLM 扮演“诊断专家”，强制要求将失败原因映射到四个维度：**知识缺失、工具错误、澄清不足、风格问题**。
    2.  要求输出结构化 JSON，包含 `dimension` (维度), `severity` (高/中/低), `evidence` (引用原文), `suggested_fix` (一句话修改建议)。
    3.  人工校验归因的准确性。
*   **期望输出**：一份 JSON 报告，证明 LLM 能稳定地将模糊的“回答错误”拆解为具体的“技能缺陷”，且归因逻辑符合业务直觉（如：工具参数错优先于风格问题）。

### 实验二：模拟“最小修改”技能迭代
*   **输入**：一个现有的 `SKILL.md` 文件（约 500 字，包含背景、流程、FAQ）+ 实验一生成的 `suggested_fix`。
*   **步骤**：
    1.  编写一个 Prompt，让 LLM 扮演“技能编辑器”。
    2.  输入：原 `SKILL.md` + 修改建议。
    3.  约束：必须遵循“最小修改原则”，只修改受影响的段落，保留其他内容原样，并输出 Diff 格式（+/- 标记）。
    4.  检查修改后的文件是否逻辑自洽，是否引入了新幻觉。
*   **期望输出**：一个 Diff 文件，清晰展示仅针对失败点进行了精准修补，且文件整体结构未崩坏。

### 实验三：冷启动“领域情境化”挖掘
*   **输入**：10 条历史真实工单（包含：用户描述、专家解决步骤、使用的工具/命令）。
*   **步骤**：
    1.  设计 Prompt，让 LLM 从这 10 条数据中提取：
        *   **标准工作流**（步骤 1->2->3）。
        *   **关键工具**（工具名、参数定义）。
        *   **高频知识点**（FAQ 形式）。
    2.  将提取内容填入预定义的 `SKILL.md` 模板。
    3.  对比“通用生成”（直接让 LLM 写）与“挖掘生成”（基于数据）生成的技能文件，评估其包含的“可执行动作”数量。
*   **期望输出**：两个版本的 `SKILL.md`。挖掘版本应包含更多具体的工具调用指令和领域术语，而非通用的“请检查配置”等空话。

## 产品 / Agent 灵感

1.  **“技能版本控制”插件 (Skill Version Control Plugin)**
    *   **概念**：类似 Git 的 Agent 技能管理后台。
    *   **功能**：自动记录每次 Bad Case 触发的技能修改（Commit），支持 `Skill_v1` 回滚到 `Skill_v0`。提供“修改影响范围”分析，告诉运营人员：这次修改修复了 3 个 DNS 问题，但可能影响 1 个账号问题。
    *   **价值**：解决企业不敢用自动进化的“黑盒恐惧”，提供可解释的变更审计。

2.  **动态“剧本”生成器 (Dynamic Playbook Generator)**
    *   **概念**：面向非技术业务人员的低代码平台。
    *   **功能**：业务人员上传一份 Excel 工单表，系统自动挖掘并生成初始 `SKILL.md`。业务人员只需在界面上点击“修复这个错误”，系统后台自动执行“归因 - 诊断 - 修改”流程，无需接触代码。
    *   **价值**：将 Agent 的维护门槛从“提示词工程师”降低到“业务专家”。

3.  **技能健康度仪表盘 (Skill Health Dashboard)**
    *   **概念**：监控 Agent 技能进化的实时看板。
    *   **功能**：展示四维失败率的趋势图（如：知识类错误周环比下降 20%）。标记“知识天花板”区域（即连续 3 轮进化无改善的 Bad Case），提示需要人工介入或引入外部知识库。
    *   **价值**：量化 Agent 的进化效果，指导资源投入方向。

## 跟现有系统怎么接

1.  **接入 RAG 系统**：
    *   将 `SKILL.md` 中的“引用链接”部分对接现有的向量数据库。当诊断器判定为“知识缺失”时，优先触发 RAG 检索，若检索不到权威文档，再触发“生成新 FAQ"流程，避免幻觉。
2.  **接入工单系统 (Ticketing System)**：
    *   将工单系统作为“执行监控”的数据源。当工单状态标记为“解决失败”或“用户不满意”时，自动触发 SkillForge 的**失败分析**流程，将工单内容作为 Bad Case 输入。
3.  **接入 CI/CD 流水线**：
    *   将 `SKILL.md` 的修改视为代码提交。在合并到生产环境前，增加一个**自动化回归测试**环节：用历史测试集（Golden Dataset）跑一遍新技能，确保 Strict CR 未下降，否则自动回滚。

## 风险与坑

1.  **灾难性遗忘 (Catastrophic Forgetting)**：
    *   **风险**：为了修复一个新 Bug，修改了通用逻辑，导致原本能处理的旧场景失效。
    *   **对策**：严格执行“最小修改”原则；每次修改后必须运行全量回归测试（Regression Test）。
2.  **归因错误导致的“越修越错”**：
    *   **风险**：诊断器误判（例如将“工具参数错”判为“知识缺失”），导致技能文件被错误地增加了大量无关知识，变得臃肿且混乱。
    *   **对策**：引入“人在回路”（Human-in-the-loop）机制，对高置信度修改自动执行，对低置信度或高风险修改（如涉及核心逻辑）需人工确认。
3.  **数据偏差放大**：
    *   **风险**：如果历史工单中人类专家的回答本身存在偏见或错误，SkillForge 会不断“学习”并固化这些错误，甚至将其优化得更“像专家”。
    *   **对策**：在初始化阶段引入“多专家投票”或“权威文档校验”机制；在进化过程中设置“异常检测”，当修改偏离权威文档过远时报警。
4.  **知识天花板**：
    *   **风险**：遇到需要复杂推理或隐性经验（Tacit Knowledge）的问题，纯文本技能文件无法表达，导致进化停滞。
    *   **对策**：明确界定技能边界，对于长尾复杂问题，设计“转人工”或“调用外部专家系统”的兜底策略，不强行让技能文件承担所有逻辑。

## 跟进清单

- [ ] **数据准备**：收集至少 50 个包含“用户问题 -Agent 回答 - 专家修正”的 Bad Case 对，用于验证归因模块。
- [ ] **原型开发**：搭建最小可行性闭环（MVP），实现：输入 Bad Case -> 输出 JSON 归因 -> 输出 Diff 修改建议。
- [ ] **评估指标定义**：确定业务侧的“成功标准”（如：工单一次性解决率、用户满意度评分），而不仅仅是文本一致性。
- [ ] **安全沙箱设计**：设计虚拟文件系统（VFS）的模拟环境，确保技能修改不会导致文件结构损坏或逻辑死循环。
- [ ] **人工审核流程**：制定“自动进化”转“人工审核”的阈值规则（如：连续 3 次修改同一文件触发人工复核）。
