# SkillForge: Forging Domain-Specific, Self-Evolving Agent Skills in Cloud Technical Support

**Authors:** Xingyan Liu, Xiyue Luo, Linyu Li, Ganghong Huang, Jianfeng Liu, Honglin Qiao (Alibaba Cloud Computing)
**Venue:** ACM SIGIR 2026 Industry Track
**Organization(s):** Alibaba Group
**arXiv:** [2604.08618](https://arxiv.org/abs/2604.08618)
**Code:** not released (论文未提供公开仓库链接)
**Project page:** none

## TL;DR and contributions
SkillForge 是一个针对企业云技术支持场景的“自我进化”框架，旨在解决大模型智能体（Agent）技能（Skill）难以初始化且无法根据真实反馈持续优化的问题。它通过“领域情境化技能创建器”生成高质量初始技能，并利用“失败归因 - 根因诊断 - 最小修改”的自动化闭环，让技能在真实工单反馈中不断迭代升级。

**Main contributions:**
- 提出端到端的技能创建 - 评估 - 优化闭环，无需人工逐条标注即可实现技能自进化。
- 设计了四维失败分析（知识、工具、澄清、风格）与根因诊断机制，将执行失败精准映射到技能文件的具体缺陷。
- 在 5 个真实云支持场景中验证，初始技能质量优于通用生成器（+4.3pp），且进化后能超越人工专家编写的技能（+10.99pp）。

**Compared against:** Generic Skill Creator (S_generic), Manually authored skills (S_manual), Production Legacy System.
**On datasets:** 5 real-world cloud support scenarios (Account, DNS, OSS, ECS, etc.), totaling 1,883 tickets and 3,737 tasks.
**Headline improvements:** 
- 初始技能一致性（Strict CR）提升 +4.3pp (vs S_generic)。
- 经过 3 轮进化，通用起点技能提升 +11.60pp，人工起点技能提升 +10.99pp。
- 最终版本比现有生产遗留系统提升 +13.76pp。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 技能进化的核心不在于微调模型参数，而在于**修改技能文件（Skill Artifact）本身**。通过“失败分析器”将 Bad Case 归因到具体维度，再由“诊断器”定位到 `SKILL.md` 的具体段落，最后由“优化器”执行最小化修改。这种“诊断 - 处方 - 手术”的流水线是本文最大的创新点。
- **🔧 Useful in practice:** 四维失败分析框架（知识/工具/澄清/风格）及其优先级判定逻辑（Knowledge > Tool > Clarification > Style），以及“虚拟文件系统（VFS）”的安全执行设计，对构建企业级 Agent 极具参考价值。
- **📎 Nice to know:** 领域情境化创建器（Domain-Contextualized Skill Creator）的具体挖掘步骤（工作流挖掘、工具挖掘、知识提取），展示了如何利用历史工单冷启动。
- **⚠️ Deprecated / superseded:** 无明确被替代技术，但指出纯文本自动化优化存在“知识天花板”（Knowledge Plateau），无法完全消除长尾幻觉。
- **🔕 Skippable:** 附录中关于 VFS 的具体代码实现细节（如 key-value 存储结构）以及 LLM-Judge 的完整 Prompt 文本，除非需要复现底层系统，否则可略读。

## Context and prerequisites

要理解 SkillForge，首先需要建立对**Agent Skill（智能体技能）**的直观认知。在传统的 LLM 应用中，我们通常通过 Prompt Engineering 告诉模型“怎么做”，但这往往是一次性的、难以复用的。而在企业级场景中，Skill 被定义为一种**可版本化、可组合的文件包**（类似软件模块），它包含了 `SKILL.md`（指令与逻辑）、`references/`（领域文档）和 `tools.json`（工具定义）。SkillForge 的核心假设是：与其让模型在运行时“临场发挥”，不如预先写好一套经过验证的、包含领域知识的“剧本”，让模型照着演。

其次，需要理解**自我进化（Self-Evolution）**在 Agent 领域的特殊性。早期的自我进化（如 Reflexion, Self-Refine）通常关注于优化模型的输出结果或调整 Prompt 的措辞，属于“软性”调整。而 SkillForge 关注的是**硬性资产**的迭代：它不改变模型权重，也不仅仅调整 Prompt，而是直接修改作为“剧本”的 `SKILL.md` 文件。这就像是一个编剧团队，根据观众（用户）的反馈，不断修改剧本的台词和剧情走向，而不是训练演员（模型）去适应新剧本。

最后，**失败归因（Failure Attribution）**是连接“执行结果”与“技能修改”的桥梁。在复杂的 Agent 任务中，一个回答错误可能源于知识缺失、工具调用错误、提问方式不当或语气生硬。如果无法精准定位是哪个环节出了问题，优化就会变成盲目的“试错”。SkillForge 通过多维度的并行分析，将模糊的“回答不好”拆解为具体的“知识缺失”或“参数错误”，从而让后续的修改有的放矢。

## Method

### The big picture (layman version)
想象你正在训练一个云客服机器人，但它总是答错问题。SkillForge 的做法不是让机器人去“死记硬背”正确答案，而是建立一个**自动化的“剧本修改工厂”**。
首先，工厂利用历史工单和文档，自动写出一份初版剧本（Skill_v0）。
然后，机器人拿着剧本去处理真实工单。如果答错了，系统不会只记录“错了”，而是像医生一样进行**四维体检**：是知识没学全？工具用错了？还是问话太啰嗦？
接着，**诊断专家**拿着体检报告，对照剧本，精准指出哪一行台词有问题，是缺了知识还是逻辑不通，并开出处方（优化计划）。
最后，**修改助手**根据处方，只修改剧本中必须改的那几行，保留其他正确的部分，生成新版剧本（Skill_v1）。
这个过程循环往复，剧本越改越准，最终甚至能超越人类专家编写的初版。

### The walkthrough

SkillForge 的整个流程是一个五阶段的闭环，我们可以将其拆解为**初始化**、**执行监控**、**诊断**和**优化**四个核心步骤。

**1. 初始化：领域情境化技能创建器 (Domain-Contextualized Skill Creator)**
传统的技能生成往往依赖通用大模型，缺乏领域深度。SkillForge 首先解决“冷启动”问题。它不凭空生成，而是从历史数据中“挖矿”：
- **工作流挖掘 (Workflow Mining):** 分析历史工单中人类专家的对话，提取出标准的解决路径（例如：澄清问题 $\rightarrow$ 诊断 $\rightarrow$ 解决）。
- **工具挖掘 (Tool Mining):** 统计人类专家高频使用的工具，提取其 Schema（参数定义）。
- **知识提取 (Knowledge Extraction):** 从内部文档和工单引用的链接中，提取关键领域知识。
- **合成:** 将这些挖掘出的内容填入预定义的 `SKILL.md` 模板。模板包含背景知识、案例分类树、具体处理流程、FAQ 和参考索引。
*设计动机：* 直接让 LLM 生成技能容易“幻觉”或偏离实际业务，基于真实历史数据挖掘能保证初始技能的**领域对齐（Domain Grounding）**。

**2. 执行与监控 (Execution & Monitoring)**
Agent 加载当前的 `Skill_v_n` 处理任务。系统使用一个 **LLM-Judge** 将 Agent 的回答与历史工单中人类专家的真实回答进行比对。
- 如果一致性高，视为通过。
- 如果一致性低（Inconsistent 或 Partially Consistent），则标记为 **Bad Case**，进入诊断流程。
*注意：* 这里的评估标准是“核心行动是否一致”，而非字面完全相同，允许存在合理的替代方案。

**3. 自动化诊断 (Automated Diagnosis)**
这是 SkillForge 最核心的创新部分，分为两步：
- **多维失败分析 (Failure Analyzer):** 对每个 Bad Case 进行**并行**的四维分析：
    1.  **知识 (Knowledge):** 是否缺失、错误或矛盾？
    2.  **工具 (Tool):** 是否漏调、参数错、结果误读？
    3.  **澄清 (Clarification):** 是否问太多、问太少或问偏了？
    4.  **风格 (Style):** 是否太生硬、啰嗦或冷漠？
    *判定逻辑：* 采用确定性规则聚合。只要有一个维度是"High"或两个维度是"Medium"，即判定为 Fail。优先级顺序为：知识 > 工具 > 澄清 > 风格。
- **根因诊断 (Skill Diagnostician):** 这是一个基于 ReAct 的 Agent。它接收聚合后的失败报告（例如：8 次知识缺失，5 次工具参数错），并读取当前的 `SKILL.md`。它的工作是将**现象**映射到**文件位置**：
    - 现象：`knowledge:missing` $\rightarrow$ 定位到 `SKILL.md` 的某一段落，判定为“缺失知识”。
    - 现象：`tool:wrong_params` $\rightarrow$ 定位到工具调用指导部分，判定为“参数文档不足”。
    最终输出一个结构化的**优化计划 (Optimization Plan)**，明确指出修改位置、修改内容、是否需要搜索新知识以及预期影响。

**4. 自动化优化 (Automated Optimization)**
**Skill Optimizer** 根据优化计划，通过**虚拟文件系统 (VFS)** 对 `SKILL.md` 进行编辑。
- **核心原则：**
    1.  **最小修改 (Minimal Modification):** 只改必须改的，不动其他部分。
    2.  **不造成伤害 (Do No Harm):** 采用增量式修改，绝不删除可能有效的旧内容。
    3.  **基于证据 (Evidence-Based):** 每一处修改都必须追溯到具体的 Bad Case。
- **知识分层策略：** 高频稳定的知识直接写入 `SKILL.md`；长尾且无权威文档的放入 FAQ；有官方文档的则只保留引用链接，让 Agent 运行时去检索。这避免了技能文件无限膨胀和幻觉累积。
- **版本控制：** 修改后的文件被保存为 `Skill_v_n+1`，完成一次进化。

## Challenges in the field — and what this work addresses

**挑战一：技能初始化的“领域鸿沟”**
- **难点：** 通用大模型生成的技能往往缺乏企业特定的业务逻辑和工具细节，导致“水土不服”。现有的技能生成方法多关注通用任务，忽略了企业场景对准确性和安全性的严苛要求。
- **SkillForge 的解法：** 提出**领域情境化创建器**，强制技能生成必须基于历史工单和内部知识库的“挖掘”，而非模型的自由发挥。通过工作流和工具的双重挖掘，确保初始技能就具备“专家级”的骨架。

**挑战二：从“失败”到“修改”的归因断层**
- **难点：** 在 Agent 系统中，执行失败是常态。但传统的自我进化方法（如 Prompt 优化）往往只能进行全局的、模糊的调整，无法精准定位是“知识错了”还是“工具调错了”。这种模糊性导致优化效率低下，甚至引入新错误。
- **SkillForge 的解法：** 建立**四维失败分析 + 根因诊断**的流水线。将模糊的失败拆解为具体的维度，并进一步映射到技能文件的具体行号。这种“手术刀式”的诊断机制，使得优化动作精准且可解释。

**挑战三：自动化优化的“知识天花板”**
- **难点：** 纯自动化的文本优化容易陷入局部最优，或者因为缺乏真正的“常识”而无法解决长尾问题。此外，过度依赖历史数据可能导致模型学习到人类专家之间的不一致性（Reference Inconsistency）。
- **SkillForge 的解法：** 承认局限性并设计**分层知识策略**。将技能文件限制为“高频稳定知识”，将长尾和动态知识留给运行时检索。同时，保留“人在回路”（Human-in-the-loop）作为最终的安全网，不追求全自动消除所有错误，而是追求在可接受范围内的持续改进。

**本工作未解决的问题：**
- 无法完全消除由人类专家回答不一致导致的“知识歧义”。
- 对于需要动态执行复杂代码（而非预定义工具）的场景，当前的 VFS 设计尚不支持（文中明确留作未来工作）。

## Experiments and results

实验在 5 个真实的云技术支持场景（Account, DNS, OSS, ECS 等）上进行，共涉及 1,883 个工单和 3,737 个任务。

**1. 初始技能质量 (RQ1)**
- **对比：** 领域创建器 (`S_domain`) vs 通用创建器 (`S_generic`)。
- **结果：** `S_domain` 在所有场景下均优于 `S_generic`。
    - **Strict CR (严格一致性):** 平均提升 **+4.3pp** (从约 56% 提升至 60%+)。
    - **Lenient CR (宽松一致性):** 平均提升 **+3.6pp**。
    - **最大增益：** 在 S5 场景中，Strict CR 提升了 **+7.20pp**。
- **结论：** 仅靠工具挖掘是不够的，领域工作流和知识的挖掘对初始质量至关重要。

**2. 自我进化循环的有效性 (RQ2)**
- **设置：** 从三种起点（人工 `S_manual`、领域 `S_domain`、通用 `S_generic`）开始，进行 3 轮进化。
- **结果 (Strict CR 增量 $\Delta$):**
    - **通用起点 (`S_generic`):** 3 轮后累计提升 **+11.60pp** (提升幅度最大，说明进化对低质量起点最有效)。
    - **人工起点 (`S_manual`):** 3 轮后累计提升 **+10.99pp**。
    - **领域起点 (`S_domain`):** 3 轮后累计提升 **+9.23pp**。
- **关键发现：**
    - **单调递增：** 每一轮进化都带来正向收益，证明循环有效。
    - **超越人工：** 进化后的技能（即使是人工起点）最终表现优于原始人工技能，证明自动化进化能捕捉到人类未显式编码的经验。
    - **收敛性：** 边际收益递减。知识类错误在第二轮后趋于停滞（Knowledge Plateau），而工具和风格类错误持续下降。

**3. 与生产遗留系统对比**
- **结果：** 进化 3 轮后的技能 (`v3`) 比现有的生产遗留系统（基于决策树和人工调优的 Prompt）高出 **+13.76pp** (Strict CR)。
- **意义：** 证明了“领域创建 + 自动进化”的范式可以超越经过长期人工打磨的传统系统。

## Open questions and limitations

1.  **知识天花板的突破：** 论文承认，纯文本的自动化优化无法解决所有知识错误，特别是当历史数据本身存在矛盾或人类专家依赖隐性经验（Tacit Expertise）时。未来是否需要引入外部知识图谱或更强的推理模型来突破这一瓶颈？
2.  **工具依赖的扩展：** 当前框架假设工具是预定义且安全的。如果场景需要 Agent 动态编写代码（如 Python 脚本）来解决问题，VFS 和当前的优化策略是否依然有效？这涉及到更复杂的安全沙箱和代码验证问题。
3.  **评估指标的局限性：** 实验主要依赖 LLM-Judge 和“与历史专家回答的一致性”。如果历史专家的回答本身存在偏差，或者存在多种正确的解决路径（而不仅仅是历史路径），这种评估是否会限制 Agent 的创新性？

## 与 B 站讲解的对照
- **视频强调点：** 视频重点突出了“失败归因”和“持续进化”的概念，形象地展示了从 Bad Case 到 Skill 修改的闭环流程，特别是四维分析（知识、工具、澄清、风格）的直观解释。
- **可能简化/遗漏：**
    - 视频可能未深入解释**虚拟文件系统 (VFS)** 的设计动机（即为了安全和不执行任意代码），这是企业级应用的关键约束。
    - 视频可能未详细讨论**知识天花板（Knowledge Plateau）**的成因（如参考数据不一致、隐性经验缺失），这部分是论文中关于局限性讨论的精华。
    - 视频可能简化了**优化原则**（如“最小修改”和“不造成伤害”），这些原则对于防止进化过程中出现“灾难性遗忘”至关重要。
