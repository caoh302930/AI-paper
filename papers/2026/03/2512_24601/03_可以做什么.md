# 可以做什么：RLM 工程化落地指南

基于 MIT RLM 论文的核心机制（Prompt 即变量 + REPL 递归调用），以下是去理论化、可直接执行的工程方案。

## 可迁移到的场景（≥4）

1.  **超长法律/合规文档的“交叉验证”审查**
    *   **痛点**：传统 RAG 只能检索片段，无法发现“条款 A（第 10 页）”与“条款 B（第 500 页）”之间的逻辑冲突或互斥定义。
    *   **RLM 解法**：利用 `OOLONG-Pairs` 模式。模型编写代码遍历文档所有条款对，递归调用子模型检查每对条款的语义一致性，最后聚合冲突报告。
    *   **价值**：从“检索相关片段”升级为“全量逻辑审计”，解决二次方复杂度的合规风险。

2.  **百万行代码库的“架构重构”与“依赖分析”**
    *   **痛点**：上下文窗口无法容纳整个项目，导致重构建议缺乏全局视野，容易破坏隐式依赖。
    *   **RLM 解法**：将代码库视为 `context` 变量。模型编写脚本递归扫描文件树，对每个模块调用子模型生成“接口摘要”，将摘要存入变量，最后基于摘要图进行全局重构规划。
    *   **价值**：无需将所有代码塞入 Prompt，即可实现全库级别的依赖分析和重构建议。

3.  **多源异构数据（1000+ PDF/网页）的“深度情报聚合”**
    *   **痛点**：竞品分析或市场调研中，需从海量文档中提取特定实体并统计其关联（如：某公司在所有文档中提到的融资轮次与金额的对应关系）。
    *   **RLM 解法**：利用 `BrowseComp-Plus` 模式。模型编写循环代码，对每个文档切片进行实体抽取，将结果写入中间变量列表，最后调用子模型进行跨文档的统计聚合。
    *   **价值**：突破单文档限制，实现跨文档的复杂统计和趋势分析，且成本低于全量长上下文调用。

4.  **小模型（7B-8B）的“长文本专家”化**
    *   **痛点**：小模型无法处理长上下文，但部署大模型成本过高。
    *   **RLM 解法**：利用论文中的**轨迹蒸馏**策略。收集大模型处理长文本的“切分 - 递归 - 聚合”代码轨迹，微调小模型（如 Qwen3-8B），使其学会“如何拆解长任务”而非“如何记忆长文本”。
    *   **价值**：用低成本小模型实现接近大模型的长文本推理能力，且推理过程可控、可解释。

## 可立刻试的小实验（≥3）

### 实验 1：手动模拟 RLM 循环（无需训练）
*   **输入**：一篇 5 万字的长文章（如维基百科长条目），一个问题：“文中提到的所有‘时间’与‘地点’的对应关系是什么？”
*   **步骤**：
    1.  将文章保存为 `doc.txt`，不直接发给 LLM。
    2.  构建一个 Python 脚本，定义 `context = open('doc.txt').read()`。
    3.  定义 `llm_query(chunk)` 函数，调用 API。
    4.  **Prompt 设计**：让 LLM 生成代码，逻辑为：`chunks = [context[i:i+4000] for i in range(0, len(context), 4000)]` -> `results = [llm_query(f"Extract time/place from: {c}") for c in chunks]` -> `final = llm_query(f"Merge: {results}")`。
    5.  在本地 REPL 执行该代码。
*   **期望输出**：一份完整的、无遗漏的时间地点对应表。对比直接一次性发送（会截断或幻觉）的效果。

### 实验 2：小模型“递归思维”蒸馏验证
*   **输入**：10 个来自大模型（如 GPT-4o）处理长文本的“代码轨迹”（包含切分逻辑、递归调用逻辑）。
*   **步骤**：
    1.  准备一个 8B 开源模型（如 Qwen2.5-7B-Instruct）。
    2.  将上述 10 个轨迹格式化为 SFT 数据（Input: 任务描述 + 长文本元数据；Output: 处理该任务的 Python 代码）。
    3.  使用 LoRA 进行微调（仅需 1-2 小时，显存 24GB 即可）。
    4.  测试：给微调后的小模型一个 10 万字的新文本，要求它写出处理代码。
*   **期望输出**：小模型能自动生成正确的切片和递归调用代码，而不是试图直接输出答案或陷入死循环。

### 实验 3：二次方复杂度任务（成对比较）
*   **输入**：100 个短文本片段（每个 500 字），任务：“找出所有语义相似的文本对”。
*   **步骤**：
    1.  构建 `context` 变量存储 100 个片段。
    2.  编写 Prompt 引导模型生成双重循环代码：`for i in range(n): for j in range(i+1, n): compare(i, j)`。
    3.  在代码中调用 `llm_query` 进行两两相似度判断，将结果存入 `pairs` 列表。
    4.  最后聚合 `pairs` 输出。
*   **期望输出**：准确列出所有相似对。对比直接让模型“阅读所有并找出相似对”（通常会遗漏或幻觉），RLM 应能处理 $100 \times 99 / 2$ 次比较。

## 产品 / Agent 灵感

1.  **“无限上下文”代码审查员 (Code Reviewer Infinite)**
    *   **核心功能**：用户上传整个 GitHub 仓库。Agent 自动构建 RLM 循环，递归分析文件依赖、接口定义和潜在 Bug。
    *   **差异化**：不是简单的 RAG 检索，而是生成“全库依赖图”和“跨文件逻辑漏洞报告”。

2.  **智能合同审计助手 (Contract Auditor Pro)**
    *   **核心功能**：针对几十页的复杂合同，自动执行“条款冲突检测”、“义务提取”和“风险评分”。
    *   **差异化**：利用 RLM 的成对比较能力，自动发现“第 3 条的免责”与“第 15 条的赔偿”之间的逻辑矛盾。

3.  **长视频/会议记录深度分析器**
    *   **核心功能**：输入 2 小时的会议转录文本（约 20 万字）。自动提取“决策链”、“待办事项”及“未决争议点”。
    *   **差异化**：通过递归调用，先分章节总结，再跨章节聚合争议点，解决“上下文腐烂”导致的遗忘问题。

4.  **小模型长文本推理服务 (Small-Model RLM API)**
    *   **核心功能**：为中小企业提供基于 7B/8B 模型的长文本 API，通过内置的 RLM 蒸馏模型，以极低 Token 成本处理长文档。
    *   **差异化**：主打“高性价比长文本”，通过代码递归弥补模型能力的不足。

## 跟现有系统怎么接

1.  **替换 RAG 的“检索 - 重排序”层**
    *   **现状**：现有 RAG 是 `Query -> Retrieve Top-K -> Summarize`。
    *   **接入**：将 `Retrieve` 改为 `Full Context as Variable`。当用户查询涉及全局统计或复杂逻辑时，触发 RLM 模式，生成代码遍历 `context` 变量，而非仅检索 Top-K。

2.  **作为 Agent 框架的“长记忆”插件**
    *   **现状**：LangChain/AutoGen 等框架在处理长历史时通常截断或压缩。
    *   **接入**：开发一个 `RLMExecutor` 类。当检测到 `history_length > threshold` 时，自动将历史存入外部变量，并切换 Agent 的 `action_space` 为“编写 Python 代码操作变量”，而非“直接对话”。

3.  **结合向量数据库做混合模式**
    *   **策略**：对于 $O(N)$ 任务（如检索），保留 RAG；对于 $O(N^2)$ 任务（如成对比较、全量聚合），强制切换至 RLM 模式。
    *   **接入**：在 Agent 路由层增加判断逻辑：`if task_complexity == "pairwise_aggregation": use_RLM()`。

## 风险与坑

1.  **同步阻塞导致的延迟爆炸**
    *   **风险**：RLM 默认是同步递归（等待子任务完成才继续），处理百万字文档可能需要数小时。
    *   **对策**：生产环境必须实现**异步递归**（Asyncio + Task Queue），或者限制递归深度（Depth Cap），并在 Prompt 中强制要求“分批次处理”。

2.  **代码生成的鲁棒性（语法错误）**
    *   **风险**：模型生成的 Python 代码若出现缩进错误或变量未定义，整个递归链断裂。
    *   **对策**：在 REPL 层增加**语法检查器**和**自动修复机制**（如：捕获 SyntaxError，将错误信息回传给模型，要求重试）。

3.  **成本失控（死循环）**
    *   **风险**：模型可能陷入 `while True` 或过度递归，导致 Token 费用激增。
    *   **对策**：
        *   设置全局 `max_recursion_depth` 和 `max_token_budget`。
        *   在代码执行层监控 `llm_query` 调用次数，超过阈值强制终止并返回部分结果。

4.  **上下文变量污染**
    *   **风险**：子模型输出的长文本若直接拼接到 `stdout`，可能污染父级上下文。
    *   **对策**：严格限制 `stdout` 的读取策略，只读取“摘要”或“前 N 个字符”，中间结果必须存储在**外部变量**中，严禁回写到 Prompt 历史。
