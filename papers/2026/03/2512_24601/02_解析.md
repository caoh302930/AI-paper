## TL;DR and contributions
这篇论文提出了一种名为**递归语言模型（Recursive Language Models, RLMs）**的新推理范式，旨在突破大语言模型（LLM）上下文窗口的硬性限制。其核心思想是将超长提示词（Prompt）视为“外部环境”中的变量，让模型通过编写代码在 REPL（交互式编程环境）中递归地调用自身，从而处理远超其原生上下文窗口（甚至达到千万级 Token）的输入。实验表明，RLM 在长上下文任务上显著优于直接调用、上下文压缩（Compaction）及现有 Agent 框架，且成本相当。

**Main contributions:**
- 提出 RLM 范式：将 Prompt 作为外部变量，通过代码递归调用模型自身，实现无限上下文扩展。
- 设计了基于 Python REPL 的具体实现，支持模型编写代码来切片、分析和聚合超长文本。
- 在四个不同复杂度的长上下文基准（S-NIAH, BrowseComp+, OOLONG, OOLONG-Pairs）上验证了有效性，GPT-5 构建的 RLM 在 OOLONG-Pairs 任务上从 0.1% 提升至 58.0%。
- 展示了小模型（Qwen3-8B）通过少量轨迹蒸馏即可学会 RLM 行为，性能提升 28%。

**Compared against:** Base LLM (GPT-5, Qwen3-Coder), CodeAct agents, Compaction agents, Retrieval agents, Claude Code.
**On datasets:** S-NIAH (信息检索), BrowseComp-Plus (多跳推理), OOLONG (线性聚合), OOLONG-Pairs (二次方聚合), LongCoT-mini (长推理).
**Headline improvements:** 在 OOLONG-Pairs 任务上，RLM(GPT-5) 将 F1 分数从基线的 0.1% 提升至 58.0%；在 BrowseComp+ 上，相比压缩基线提升 29%；小模型蒸馏后性能提升 28.3%。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 将 Prompt 视为外部变量（Variable in Environment）而非输入 Token 流；利用 REPL 环境让模型编写代码来递归调用自身（`llm_query` 或 `rlm_query`），从而绕过上下文窗口限制。
- **🔧 Useful in practice:** Algorithm 1 的伪代码逻辑；System Prompt 的设计（如何引导模型使用 REPL 和递归）；训练小模型作为 RLM 的蒸馏策略（Rejection Fine-tuning on trajectories）。
- **📎 Nice to know:** 不同递归深度（Depth=0, 1, 2, 3）对性能的影响；OOLONG-Pairs 任务中二次方复杂度的具体表现；不同模型（GPT-5 vs Qwen）在 RLM 框架下的行为差异。
- **⚠️ Deprecated / superseded:** 传统的“上下文压缩/摘要”（Context Compaction）在处理需要密集访问所有细节的任务时表现不佳，已被 RLM 的“程序化切片”策略超越。
- **🔕 Skippable:** 详细的基准数据集构建细节（Appendix D）；部分负结果的具体失败案例（Appendix B，除非你正在调试类似系统）；冗长的参考文献列表。

## Context and prerequisites

要理解 RLM，首先需要理解当前 LLM 处理长上下文的**“上下文腐烂”（Context Rot）**现象。传统的 Transformer 架构在处理超长序列时，注意力机制的效能会随长度增加而急剧下降，导致模型“遗忘”关键信息或产生幻觉。现有的解决方案主要有两类：一是**架构层面**（如线性注意力、稀疏注意力），但这需要重新训练模型且扩展有限；二是**系统层面**的**上下文压缩（Compaction）**，即当上下文过长时，将旧内容摘要成短文本。然而，压缩是有损的，对于需要精细检索或聚合所有细节的任务（如“在百万字文档中统计所有特定模式的组合”），压缩会导致关键信息丢失。

其次，需要理解**REPL（Read-Eval-Print Loop）**的概念。REPL 是一个交互式编程环境，用户输入代码，系统执行并返回结果，且状态（变量）会持久保存。RLM 的创新在于将 LLM 置于 REPL 中，让 LLM 不再直接“阅读”整个 Prompt，而是通过编写 Python 代码来操作代表 Prompt 的变量。这就像给 LLM 装上了一个“文件系统”和“计算器”，它可以通过代码切片（Slicing）、循环（Looping）和递归（Recursion）来按需读取和处理数据，而不是被动地一次性吞下所有 Token。

最后，理解**推理时扩展（Inference-time Scaling）**至关重要。RLM 不依赖模型参数的增加，而是通过增加推理时的计算步骤（即更多的递归调用和代码执行）来换取性能提升。这与“思维链”（Chain-of-Thought）类似，但 RLM 将这种推理过程显式地转化为对超长上下文的程序化操作，从而在计算资源允许的情况下，理论上可以处理任意长度的输入。

## Method

### The big picture (layman version)
想象你要阅读一本几百万字的百科全书并回答一个复杂问题，但你的记忆（上下文窗口）只能容纳几万字。传统的做法是让你快速浏览并记住大概（压缩），或者让你只读相关章节（检索），但这往往会漏掉细节。RLM 的做法完全不同：它不让你直接“读”整本书，而是把书放在一个特殊的“工作台”（REPL 环境）上。你（模型）手里有一把刀（代码能力），你可以写一段代码，把书切成小块，然后叫一个“分身”（子模型）去读每一小块，把分身的回答记在笔记本（变量）上。最后，你再根据笔记本上的记录，写出最终答案。如果某个小块太复杂，你甚至可以再叫一个分身去处理那个小块。通过这种“切分 - 递归调用 - 聚合”的方式，你实际上处理了整本书，而你的记忆里只保留了当前正在处理的那一小块和笔记本上的摘要。这就是 RLM 的核心：用代码和递归代替了死记硬背。

### The walkthrough

RLM 的实现基于一个核心循环，我们称之为 **RLM Loop**。让我们从最简单的版本开始，逐步构建出完整的系统。

**1. 环境初始化：Prompt 即变量**
传统的 LLM 调用是将 Prompt $P$ 直接拼接到输入序列中：$Input = [System, P]$。一旦 $|P| > K$（上下文窗口限制），系统就会崩溃或截断。
RLM 首先初始化一个持久的 REPL 环境 $\mathcal{E}$。在这个环境中，用户 Prompt $P$ 被存储为一个字符串变量 `context`，而不是输入 Token。
$$ \mathcal{E} \leftarrow \text{InitREPL}(\text{prompt}=P) $$
同时，环境被赋予一个函数 `llm_query`（或 `rlm_query`），用于调用子模型。此时，模型 $\mathcal{M}$ 的输入不再是 $P$，而是关于 $\mathcal{E}$ 的元数据（如 `context` 的长度、前缀等），这保证了输入长度是常数 $O(1)$，与 $P$ 的长度无关。

**2. 迭代推理循环**
模型进入一个 `while True` 循环。在每一步，模型 $\mathcal{M}$ 根据当前的历史（History）和 REPL 的状态（State），生成一段 Python 代码。
$$ \text{code} \leftarrow \mathcal{M}(\text{History}, \text{State}) $$
这段代码的目的不是直接输出答案，而是**操作 `context` 变量**。例如，模型可能会写：
```python
# 将长文本切分为 10 个片段
chunks = [context[i:i+chunk_size] for i in range(0, len(context), chunk_size)]
# 对每个片段调用子模型
answers = [llm_query(f"Analyze: {c}") for c in chunks]
# 聚合答案
final_answer = llm_query(f"Summarize: {answers}")
```
代码在 REPL 中执行，产生的中间结果（如 `answers` 列表）被保存在环境变量中。模型只能看到代码执行后的输出（stdout）的摘要（如长度、前缀），这防止了输出内容污染上下文窗口。

**3. 递归调用机制**
这是 RLM 区别于普通 CodeAct Agent 的关键。普通 Agent 只能调用外部工具，而 RLM 可以调用**自身**。
- **浅层递归（Depth=1）：** 调用 `llm_query`，这相当于调用一个标准的 LLM 实例，处理切片后的文本。
- **深层递归（Depth>1）：** 调用 `rlm_query`。当子任务本身也很复杂（例如，一个切片内部还需要再次切分）时，`rlm_query` 会启动一个新的 RLM 循环（新的 REPL 环境），递归地处理该子任务。
$$ \text{sub\_result} \leftarrow \text{rlm\_query}(\text{sub\_context}, \text{query}) $$
这种机制允许模型构建一个**递归树**，处理复杂度高达 $O(|P|^2)$ 的任务（如 OOLONG-Pairs 中的成对聚合）。

**4. 终止条件**
循环持续进行，直到模型在 REPL 中设置了一个名为 `Final` 的变量，或者显式调用 `FINAL(answer)` 标记。
$$ \text{if } \mathcal{E}[\text{Final}] \text{ is set: return } \mathcal{E}[\text{Final}] $$
此时，系统返回最终结果。

**设计选择对比：**
论文通过 Algorithm 2 展示了一个“错误”的设计：将 Prompt 直接放入历史（History），导致上下文窗口迅速耗尽，被迫使用有损压缩。RLM 通过**将 Prompt 移出上下文窗口**（作为外部变量）并**通过代码递归调用**，彻底解决了这一问题。

## Challenges in the field — and what this work addresses

**挑战 1：上下文窗口的硬限制与“上下文腐烂”**
*为什么难：* 无论模型架构如何优化，Transformer 的注意力机制在超长序列下都会出现性能衰减（Context Rot），且显存限制使得直接处理百万级 Token 极其昂贵。现有的压缩方法（Summarization）会丢失细节，检索方法（RAG）难以处理需要全局聚合的任务。
*RLM 的解决：* RLM 不试图“塞入”所有 Token，而是通过**程序化切片**将长文本分解为模型能处理的小块。通过递归调用，模型可以按需访问任意深度的细节，同时保持核心上下文（History）的恒定大小，从而在理论上实现了无限上下文。

**挑战 2：复杂任务的聚合难度（线性/二次方复杂度）**
*为什么难：* 许多长文本任务（如统计所有文档对的相似性）的计算复杂度随输入长度呈线性甚至二次方增长。普通模型无法在单次前向传播中完成这种聚合，而简单的分块处理又难以跨块交互。
*RLM 的解决：* RLM 利用代码的**循环（Loop）**和**递归（Recursion）**能力。模型可以编写代码遍历所有切片，将中间结果存储在变量中，最后进行聚合。对于二次方任务，RLM 可以通过嵌套递归调用，让子模型处理成对数据，从而在推理时动态构建计算图，完成 $O(|P|^2)$ 的语义工作。

**挑战 3：小模型处理长任务的泛化能力**
*为什么难：* 通常只有超大模型（如 480B）才具备足够的推理能力来规划复杂的长文本处理策略。小模型（如 8B）往往无法理解如何切分或递归。
*RLM 的解决：* 论文发现，RLM 的行为模式（切分、调用、聚合）具有通用性。通过**轨迹蒸馏（Trajectory Distillation）**，仅用 1000 个来自大模型的 RLM 轨迹微调小模型，就能让小模型学会这种“递归思维”，性能提升显著（+28%），且推理成本更低。

**本工作未解决的问题：**
RLM 目前主要依赖**同步（Blocking）**调用，导致推理延迟较高。虽然论文提到异步调用可以优化，但这增加了系统实现的复杂性。此外，RLM 对模型的**代码生成能力**有较高要求，如果模型生成的代码有语法错误，整个递归链可能中断。

## Experiments and results

论文在四个主要基准上进行了评估，涵盖了从简单检索到复杂聚合的不同难度：

1.  **S-NIAH (Needle In A Haystack):** 单点检索任务。
    *   结果：RLM 与基线模型表现相当，证明在简单任务上 RLM 不会引入过多开销。
2.  **BrowseComp-Plus (1K docs):** 多跳推理，需从 1000 个文档中聚合信息。
    *   结果：RLM(GPT-5, depth=1) 得分为 **91.3%**，显著高于 Compaction Agent (70.5%) 和 CodeAct (51.0%)。成本仅为 $0.99，优于基线。
3.  **OOLONG:** 线性复杂度任务，需对所有文档进行语义标签聚合。
    *   结果：基线 GPT-5 得分为 44.0%，RLM 提升至 **56.0%**。Qwen3-Coder 基线 36.0%，RLM 提升至 **48.0%**。
4.  **OOLONG-Pairs:** 二次方复杂度任务，需处理文档对。这是最难的基准。
    *   结果：基线 GPT-5 几乎完全失败（F1 **0.1%**），因为无法处理成对交互。RLM(GPT-5, depth=1) 成功将 F1 提升至 **58.0%**。Qwen3-Coder 从 0.1% 提升至 **23.1%**。
    *   **深度影响：** 增加递归深度（Depth=2, 3）进一步提升了 OOLONG-Pairs 的性能（Depth=3 时 GPT-5 达到 **76.0%**），证明了深层递归对复杂聚合的必要性。

**小模型实验 (RLM-Qwen3-8B):**
*   通过蒸馏 1000 个轨迹，Qwen3-8B 作为 RLM 的性能比其基线提升了 **28.3%**（中位数），甚至在某些任务上接近 GPT-5 基线。
*   在 MRCRv2 任务上，RLM 展现了**长度泛化**能力：在 64k 数据上训练，能成功泛化到 1M 长度的测试集。

**成本与效率：**
*   RLM 的平均成本与基线 LLM 调用相当，甚至在某些任务上更低（因为避免了无效的长上下文计算）。
*   但在 OOLONG-Pairs 等复杂任务中，由于递归调用次数多，单次推理时间较长（同步调用导致）。

**关键实现细节（推测）：**
- **截断策略：** 论文提到 `stdout` 会被截断以防止溢出，代码中应有逻辑只保留输出前缀和长度。
- **递归深度控制：** 系统应有一个全局计数器或环境变量来跟踪当前递归深度，防止无限递归。
- **错误处理：** 针对 Qwen3-Coder 容易出现的语法错误，代码中可能包含重试机制或语法检查器。

## Open questions and limitations

1.  **同步调用的延迟瓶颈：** 当前实现是阻塞式的，导致长任务推理时间极长。未来工作需探索**异步递归**，但这会显著增加系统复杂度（如状态管理、并发控制）。
2.  **代码生成的鲁棒性：** RLM 高度依赖模型生成正确的 Python 代码。如果模型频繁产生语法错误或逻辑错误，递归链会断裂。如何训练模型生成“零错误”的递归代码是一个挑战。
3.  **成本爆炸风险：** 虽然平均成本可控，但在极端情况下（如模型陷入死循环或过度调用），成本可能失控。需要更智能的**早停机制**或**预算约束**。
4.  **训练数据的稀缺性：** 目前小模型的训练依赖于大模型的轨迹蒸馏。如果缺乏大模型生成的“完美”轨迹，小模型能否通过强化学习（RL）直接从零学会 RLM 行为？
