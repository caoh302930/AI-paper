## TL;DR and contributions
SkVM 提出了一种将大模型（LLM）智能体中的"Skill（技能）”从非结构化的提示词（Prompt）转化为可编译、可优化的系统组件的新范式。它通过类似传统编译器的“提前编译（AOT）”和“即时编译（JIT）”机制，解决了技能在不同模型和运行环境间移植性差、执行效率低的问题。实验显示，SkVM 能将任务完成率平均提升 15.3%，Token 消耗降低高达 40%，并在特定场景下实现 3.2 倍至 50 倍的加速。

**Main contributions:**
- 定义了 26 种“原语能力（Primitive Capabilities）”，将模糊的技能需求量化为可测量的指标。
- 设计了 SkVM 系统，包含基于能力的 AOT 编译（适配模型/环境）和运行时 JIT 优化（代码固化/自适应重编译）。
- 在 8 个不同规模的 LLM 和 3 种 Agent Harness 上验证，显著提升了弱模型的执行成功率并降低了强模型的 Token 成本。

**Compared against:** No Skill (无技能), Original Skill (原始技能), Skill-Creator (Anthropic 官方优化工具).
**On datasets:** SkillsBench, PinchBench, 以及从 clawhub.ai 和 skills.sh 收集的 118,000+ 真实技能。
**Headline improvements:** 任务完成率平均 +15.3%；Token 消耗降低 up to 40%；延迟降低 19–50 倍（通过代码固化）；端到端速度提升 3.2 倍（通过并行提取）。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 将 Skill 视为代码，LLM 视为异构处理器。核心在于“能力感知编译（Capability-Based Compilation）”：先量化模型能做什么（原语能力），再根据技能需求与模型能力的差距，动态调整技能指令（补偿或替换），而非简单地把技能塞进 Prompt。
- **🔧 Useful in practice:** 环境绑定（Environment Binding）机制，将依赖安装从 LLM 推理中剥离，转为预执行脚本；代码固化（Code Solidification）技术，将高频重复的 LLM 生成逻辑直接转为可执行函数，绕过推理。
- **📎 Nice to know:** 26 种原语能力的具体分类（如 gen.code.shell, reason.arithmetic 等）及其分级标准；并发提取（Concurrency Extraction）的三种粒度（DLP, ILP, TLP）。
- **⚠️ Deprecated / superseded:** 传统的“纯 Prompt 工程”处理技能的方式被证明在异构环境下脆弱且低效，SkVM 提供了一种系统级的替代方案。
- **🔕 Skippable:** 详细的微基准测试（Microbenchmarks）构建过程细节；部分具体的失败案例复现（除非关注具体错误模式）。

## Context and prerequisites

要理解 SkVM，首先需要打破"Skill 只是提示词”的直觉。在当前的 Agent 生态中，Skill 通常是一段包含自然语言指令、脚本片段和元数据的 Markdown 文件。开发者期望它能像函数库一样被复用，但实际执行时，它只是作为额外的上下文（Context）被“解释执行”（Interpreted Execution）。这就好比在汇编语言时代，我们试图用自然语言描述机器指令，然后指望不同的 CPU（模型）都能完美理解并执行，而没有任何中间层（编译器）来适配。

其次，必须理解“异构性”带来的挑战。不同的 LLM（如 Claude Opus vs. Qwen 30B）在理解复杂指令、执行代码或处理工具调用时的能力差异巨大。同一个 Skill，在强模型上可能完美运行，在弱模型上却可能因为无法理解某个隐式假设（如“使用绝对路径”）而失败。此外，Agent 的运行框架（Harness，如 LangGraph, OpenCode）提供的工具集和并发能力也不同。这种“技能需求”与“模型/环境能力”之间的不匹配，是导致当前技能系统脆弱、Token 浪费和延迟高的根本原因。

最后，需要回顾传统编译器的思想。编译器（如 GCC, JVM）的核心价值在于将高级语言（如 C++, Java）转换为特定硬件（CPU）能高效执行的机器码。它通过静态分析（AOT）优化代码结构，通过即时编译（JIT）利用运行时信息进一步优化。SkVM 正是将这一思想迁移到了 Agent 领域：Skill 是高级语言，LLM 是异构硬件，而 SkVM 就是那个编译器，负责在技能运行前和运行中，将其“编译”成最适合当前 LLM 和环境的形式。

## Method

### The big picture (layman version)
想象你有一个复杂的烹饪食谱（Skill），你想让不同的厨师（LLM）在不同的厨房（Harness/Environment）里做这道菜。
1. **现状问题**：现在的做法是把食谱直接读给厨师听。如果厨师没学过某种高级刀法（能力不足），或者厨房没某种调料（环境缺失），菜就做坏了，或者厨师得花大量时间问“这个怎么切？”（Token 浪费）。
2. **SkVM 的做法**：
   - **编译前（AOT）**：SkVM 先测试厨师的能力（比如“切丝”是 L1 还是 L3 水平），检查厨房有什么工具。然后，它重写食谱：如果厨师不会切丝，就改成“切块”（能力补偿）；如果厨房没盐，就提前把盐准备好（环境绑定）；如果有些步骤互不干扰，就安排两个厨师同时做（并发提取）。
   - **运行时（JIT）**：菜开始做了。如果厨师反复在同一个步骤出错，SkVM 就动态修改食谱（自适应重编译）。如果某个步骤（比如“切葱花”）每次都是完全一样的动作，SkVM 就直接派一个机器人（固化代码）去切，不再让厨师思考，从而极快完成。
3. **结果**：无论厨师水平如何，厨房条件怎样，SkVM 都能保证菜做出来，而且更快、更省料。

### The walkthrough

SkVM 的工作流分为两个主要阶段：**Skill 编译（AOT）**和 **Skill 运行时（JIT）**。

#### 1. Skill 编译 (AOT Compilation)
这是离线阶段，发生在技能安装时。编译器针对特定的 `(Model, Harness)` 对生成优化后的技能变体。它包含三个核心 Pass：

**Pass 1: 基于能力的编译 (Capability-Based Compilation)**
这是解决“模型不匹配”的核心。
- **原语能力定义**：SkVM 首先定义了 26 种“原语能力”（Primitive Capabilities），如 `gen.code.shell`（生成 Shell 代码）、`reason.arithmetic`（算术推理）等。每种能力被划分为不同等级（L1-L3），代表从基础到复杂的熟练度。
- **能力画像（Profiling）**：在编译前，系统会对目标模型进行微基准测试，生成其能力画像。例如，模型 A 在 `gen.code.shell` 上只有 L1 水平（只会基础命令），而模型 B 有 L3 水平（能写复杂管道）。
- **差距分析与转换**：编译器分析技能需求（例如：需要 L2 的 `tool.exec` 来处理相对路径）。
  - **补偿（Compensation）**：如果差距不大（如需求 L2，模型 L1），编译器会修改技能指令，使其更明确。例如，将“使用相对路径”改为“使用绝对路径”，降低对模型推理能力的要求。
  - **替换（Substitution）**：如果差距太大或模型完全不支持，编译器会寻找替代方案。例如，如果模型无法用 Python 处理 PDF（L3 需求），但能用 JavaScript（L2 支持），则自动切换实现路径。

**Pass 2: 环境绑定 (Environment Binding)**
这是解决“环境不匹配”的关键。
- 编译器从技能描述中提取依赖项（如 `pip install pandas`）。
- 它生成一个**幂等的环境绑定脚本（Env-binding Script）**。在技能正式运行前，先执行这个脚本检查并安装缺失的依赖。
- **优势**：将环境诊断从 LLM 的推理循环中剥离。原本 LLM 需要花费大量 Token 去发现“缺包”并尝试安装，现在由脚本直接完成，LLM 只需关注逻辑。

**Pass 3: 并发提取 (Concurrency Extraction)**
这是解决“效率”问题的。
- 编译器分析技能的工作流，构建有向无环图（DAG），识别无依赖的步骤。
- 它提取三种并行机会：
  - **数据级并行 (DLP)**：对同一操作处理多个数据（如并行处理 15 个 CSV）。
  - **指令级并行 (ILP)**：多个独立工具调用并发执行（需 Harness 支持批量调用）。
  - **线程级并行 (TLP)**：将子任务分发给子 Agent（Sub-agent）并行处理。
- 编译器将这些并行结构显式地标注在技能中，供运行时调度。

#### 2. Skill 运行时 (Runtime with JIT Optimization)
这是在线阶段，处理动态不确定性。

**JIT 优化机制**：
- **自适应重编译 (Adaptive Recompilation)**：运行时监控技能执行。如果同一技能多次失败，系统分析失败日志，判断是否为系统性能力缺口。如果是，则触发重编译，应用新的补偿策略，并保留回滚机制以防恶化。
- **代码固化 (Code Solidification)**：针对 75% 的技能中包含的“参数化模板”（如固定的 API 调用结构）。
  - **检测**：AOT 阶段识别出可固化的代码模板。
  - **验证**：运行时监控 LLM 输出，如果连续多次输出结构一致，则判定为“固化候选”。
  - **执行**：将模板实例化为可执行函数。后续调用直接运行函数，**完全绕过 LLM 推理**。这能带来 19-50 倍的延迟降低。
  - **安全回退**：如果固化代码执行失败，自动回退到 LLM 生成模式。

**资源感知调度 (Resource-Aware Parallel Scheduling)**：
- 运行时监控 CPU、内存和 API 限流信号。
- 当资源紧张时，动态限制子 Agent 的启动或暂停部分任务，避免系统过载。

## Challenges in the field — and what this work addresses

1. **挑战：技能移植性的“黑盒”困境**
   - **难点**：技能通常以自然语言编写，隐含了对模型能力和环境的假设。不同模型对这些假设的理解能力差异巨大（例如，弱模型可能无法区分 CLI 和 API 库）。传统的 Prompt 工程无法量化这种差异，导致技能在 A 模型上好用，在 B 模型上完全失效。
   - **SkVM 的解法**：引入“原语能力”作为中间抽象层。通过将模糊的自然语言需求拆解为 26 种可量化的能力指标，SkVM 能够精确测量“技能需求”与“模型能力”之间的差距，并据此进行针对性的指令重写（补偿）或路径替换（替代），从而实现了真正的跨模型移植。

2. **挑战：执行效率的“推理税”**
   - **难点**：当前 Agent 执行技能时，每一步都需要 LLM 进行推理。对于重复性高、结构固定的任务（如调用 API、解析固定格式），LLM 每次都要重新“思考”，消耗大量 Token 和时间。此外，环境依赖的缺失会导致 LLM 陷入“发现 - 尝试 - 失败”的死循环，进一步浪费资源。
   - **SkVM 的解法**：采用“代码固化”技术，将高频重复的推理逻辑转化为直接执行的代码，彻底绕过 LLM；同时通过“环境绑定”将依赖检查前置，避免 LLM 在运行时处理环境错误。这两者结合，显著降低了 Token 消耗和延迟。

3. **挑战：异构环境的动态适配**
   - **难点**：Agent 运行在多样的 Harness 中，有的支持并发，有的不支持；有的工具丰富，有的简陋。静态的技能无法适应这种动态变化。
   - **SkVM 的解法**：通过 AOT 编译时的“并发提取”和运行时的“资源感知调度”，SkVM 能够根据当前 Harness 的能力动态调整执行策略（如将串行改为并行），并在资源受限时自动降级，保证了系统的鲁棒性。

**本工作未解决的问题**：SkVM 目前主要解决结构化技能（如工具调用、流程控制）的优化。对于完全依赖模型创造性生成（如开放式写作、艺术创作）且无固定结构的技能，其优化空间有限，因为这类任务难以被“固化”或“能力量化”。

## Experiments and results

实验在 8 个 LLM（涵盖 SOTA、Mid-tier、Small 三个梯队）和 3 种 Harness（BareAgent, OpenCode, OpenClaw）上进行，覆盖 SkillsBench 和 PinchBench 等基准。

- **任务完成率**：SkVM 优化的技能在所有模型和 Harness 组合中均取得最高分数。平均任务完成率提升 **15.3%**。对于弱模型（如 Qwen3-30B），提升尤为显著（在 BareAgent 上比 Skill-Creator 高 25%）。
- **Token 效率**：在强模型与弱 Harness 组合下，Token 消耗降低高达 **40%**。这是因为减少了因环境错误和工具调用失败导致的重试循环。
- **延迟与速度**：
  - 通过**代码固化**，特定任务（如 PDF 提取）的延迟从 10s+ 降至 200ms+，实现 **19–50 倍** 的加速。
  - 通过**并发提取**（特别是 TLP），端到端执行速度提升 **3.2 倍**。
- **消融实验**：
  - AOT 编译本身就能将平均分数提升 88%（相比原始技能）。
  - JIT 优化进一步修复了 AOT 未覆盖的缺陷，经过 3 轮 JIT 后，14 类任务中有 10 类达到满分。
  - 环境绑定机制使弱模型在缺失依赖环境下的成功率从 33-67% 恢复到接近 100%。

## Open questions and limitations
1. **非确定性编译**：由于输入是自然语言，编译过程本身可能引入非确定性。虽然论文提到有回滚机制，但在极端情况下，编译后的技能是否总是优于原始技能仍需长期观察。
2. **原语能力的覆盖度**：目前 26 种原语覆盖了 95% 的技能，但随着技能生态发展，新的能力需求可能出现，需要不断扩展能力库。
3. **编译成本**：AOT 编译需要调用 LLM 进行微基准测试和代码生成，虽然是一次性成本，但对于大量小型技能，累积成本可能较高。
4. **创造性任务**：如前所述，对于高度依赖模型“灵感”而非“流程”的任务，SkVM 的优化效果可能有限。
