# 可以做什么：SkillGraph 落地实战指南

基于 SkillGraph 论文的核心逻辑（**有向依赖图 + 动态演化 + 共同进化**），以下是去理论化、可直接执行的落地方案。

## 可迁移到的场景（≥4）

1.  **复杂 SOP 自动化执行（企业 RPA 2.0）**
    *   **痛点**：传统 RPA 只能执行固定流程，一旦业务规则微调（如“审批流程从 3 人变 4 人”），脚本需重写。
    *   **SkillGraph 解法**：将“提交单据”、“财务审核”、“法务审核”、“归档”定义为节点。
        *   构建 `Prerequisite` 边：法务审核必须在财务审核之后。
        *   构建 `Enhance` 边：“自动填单”技能能提升“提交单据”的成功率。
        *   **演化**：当某类单据频繁在“法务审核”环节失败，系统自动将该节点拆分为“法务初审”和“法务复审”，无需人工重写代码。

2.  **多步代码生成与调试（DevAgent）**
    *   **痛点**：Agent 写长代码时，容易忘记前文依赖，或调用顺序错误（如先 `import` 后 `define`，或先 `connect DB` 后 `query`）。
    *   **SkillGraph 解法**：
        *   节点：`环境初始化 `、` 依赖安装 `、` 数据库连接 `、` 核心逻辑 `、` 单元测试`。
        *   边：`环境初始化` $\xrightarrow{prereq}$ `依赖安装`。
        *   **检索**：任务“写一个爬虫” $\to$ 检索出 `环境初始化` $\to$ `依赖安装` $\to$ `核心逻辑` 的有序序列。
        *   **演化**：若 Agent 多次在 `核心逻辑` 后直接报错，系统自动插入 `异常处理` 节点并建立连接。

3.  **个性化教育/游戏技能树（自适应学习系统）**
    *   **痛点**：现有推荐系统只能推荐“类似内容”，无法规划“学习路径”。学生学了“微积分”却不会“求导”，因为系统没建立强依赖。
    *   **SkillGraph 解法**：
        *   构建学科技能图，`Prerequisite` 边严格定义学习顺序。
        *   **渐进式解锁**：只有当 `基础代数` 节点的成功率（做题正确率）> 90%，才解锁 `微积分` 节点。
        *   **动态调整**：若大量学生在 `求导` 节点失败，系统自动将该节点拆分为 `定义求导` 和 `公式求导` 两个子节点，降低难度。

4.  **智能客服的长程任务处理（售后/理赔）**
    *   **痛点**：处理“退货退款”涉及：确认订单 $\to$ 检查物流 $\to$ 生成单号 $\to$ 通知仓库。传统 Agent 容易漏步骤或顺序错乱。
    *   **SkillGraph 解法**：
        *   将客服动作技能化。
        *   **边演化**：发现“检查物流”和“生成单号”经常同时成功，建立 `Co-occurs` 边，加速检索。
        *   **废弃机制**：若某类商品（如虚拟卡）不再需要“检查物流”，系统自动剪除该边，减少上下文干扰。

## 可立刻试的小实验（≥3）

### 实验 1：构建“厨房任务”技能依赖图（验证拓扑排序）
*   **目标**：验证图结构能否解决“顺序错误”导致的任务失败。
*   **输入**：
    *   任务：“做一杯热牛奶”。
    *   初始技能库（扁平）：`[倒牛奶，加热牛奶，清洗杯子，打开微波炉]`。
    *   初始关系：无（或仅语义相似）。
*   **步骤**：
    1.  定义三种边：`Prerequisite` (前置), `Enhance` (增强), `Co-occurs` (共现)。
    2.  人工或 Prompt 让 LLM 生成初始图：
        *   `清洗杯子` $\xrightarrow{prereq}$ `倒牛奶`
        *   `倒牛奶` $\xrightarrow{prereq}$ `加热牛奶`
        *   `打开微波炉` $\xrightarrow{prereq}$ `加热牛奶`
    3.  模拟检索：输入任务，执行 BFS/拓扑排序。
    4.  **对比**：分别用“无序列表 Prompt"和“有序序列 Prompt"让 LLM 执行任务。
*   **期望输出**：
    *   无序列表：LLM 可能输出“先加热再倒牛奶”（失败）。
    *   有序序列：LLM 输出“清洗 -> 倒 -> 开微波炉 -> 加热”（成功）。
    *   **结论**：图结构显式约束了顺序，显著提升复杂任务成功率。

### 实验 2：模拟“技能拆分”演化机制（验证自适应粒度）
*   **目标**：验证当技能太粗导致失败时，系统能否自动拆分。
*   **输入**：
    *   任务：“处理用户投诉”。
    *   初始技能：`[安抚用户]` (成功率设定为 30%，因为太笼统)。
    *   失败轨迹：用户因“语气生硬”或“未理解问题”而投诉升级。
*   **步骤**：
    1.  设定阈值：若技能成功率 $< 40\%$，触发 `Split` 操作。
    2.  调用 Teacher Model（或模拟）分析失败原因，生成子技能：`[共情倾听]`, `[确认问题]`, `[提供方案]`。
    3.  更新图：删除 `安抚用户`，添加三个子节点，并建立 `Prerequisite` 链。
    4.  重新检索并执行。
*   **期望输出**：
    *   旧策略：直接调用 `安抚用户`，失败。
    *   新策略：按顺序调用 `共情倾听` $\to$ `确认问题` $\to$ `提供方案`，成功率提升至 80%+。
    *   **结论**：动态拆分机制解决了“一刀切”技能导致的低效。

### 实验 3：渐进式解锁验证（防止“新手学大招”）
*   **目标**：验证是否能在低层级技能未掌握时，自动屏蔽高阶技能。
*   **输入**：
    *   任务：“编写并部署一个 Web 服务”。
    *   技能层级：
        *   Level 0: `写 Hello World`, `运行本地`
        *   Level 1: `配置 Docker`, `编写 Dockerfile`
        *   Level 2: `K8s 部署`, `负载均衡配置`
*   **步骤**：
    1.  初始化：仅解锁 Level 0。
    2.  模拟训练：Agent 在 Level 0 任务上连续失败 5 次。
    3.  检查解锁条件：Level 0 成功率 < 阈值 (如 0.8)。
    4.  **操作**：系统**禁止**检索 Level 1 和 Level 2 技能，强制 Agent 在 Level 0 范围内优化策略。
    5.  模拟训练：Agent 在 Level 0 成功率达到 0.9。
    6.  **操作**：解锁 Level 1。
*   **期望输出**：
    *   无解锁机制：Agent 直接尝试 `K8s 部署`，因基础不牢导致崩溃。
    *   有解锁机制：Agent 先学会 `运行本地`，再逐步学习 `Docker`，最终成功部署。
    *   **结论**：渐进式解锁避免了策略在复杂空间中的“灾难性遗忘”或“盲目探索”。

## 产品 / Agent 灵感

1.  **“技能地图”可视化调试台**
    *   **功能**：为 Agent 开发者提供一个可视化的 Graph UI。
    *   **价值**：实时显示技能节点的“热度”（使用次数）和“健康度”（成功率）。红色节点代表需要拆分或废弃，绿色粗边代表强依赖。
    *   **场景**：运维人员发现 Agent 在“退款”环节卡住，直接在图上看到“退款”节点成功率骤降，一键触发“拆分”操作。

2.  **动态 SOP 生成器（SOP-as-Code）**
    *   **功能**：输入“我想做一个电商大促活动”，Agent 自动生成并维护一个技能图。
    *   **价值**：随着活动进行，自动发现“预热”和“秒杀”之间的新依赖关系，动态调整执行脚本，无需人工干预流程。

3.  **跨域技能迁移引擎**
    *   **功能**：提取 ALFWorld 中的“加热”技能图结构（抽象逻辑），映射到 WebShop 的“搜索加热商品”任务。
    *   **价值**：解决大模型“举一反三”难的问题，将物理世界的逻辑结构迁移到数字世界。

## 跟现有系统怎么接

1.  **替换 RAG 检索层**
    *   **现状**：现有 Agent 使用 Vector DB (FAISS/Milvus) 做 Top-K 语义检索。
    *   **接入**：保留 Vector DB 做“种子节点”的初始匹配，但**必须**引入图数据库（Neo4j / NebulaGraph）存储技能关系。
    *   **流程**：Vector Search (找种子) $\to$ Graph Traversal (找路径) $\to$ Topological Sort (定顺序) $\to$ Prompt。

2.  **RL 训练循环改造**
    *   **现状**：RL 训练通常只更新 Policy 参数，记忆库是静态的。
    *   **接入**：在 RL 的 `Validation` 阶段插入 `Graph Evolution` 模块。
    *   **逻辑**：
        ```python
        # 伪代码
        for epoch in range(EPOCHS):
            trajectories = policy.run(env)
            rewards = evaluate(trajectories)
            
            # 1. 更新策略 (GRPO/PPO)
            policy.update(trajectories, rewards)
            
            # 2. 更新图 (SkillGraph Evolution)
            if epoch % EVOLUTION_INTERVAL == 0:
                graph.update_nodes(trajectories, rewards) # 增/合/分/弃
                graph.update_edges(trajectories, rewards) # 强化/剪枝
                graph.unlock_skills() # 渐进解锁
            
            # 3. 更新 Prompt 模板
            prompt_template = build_prompt(graph, current_task)
        ```

3.  **Teacher Model 接口封装**
    *   **现状**：通常直接调用 LLM 生成回答。
    *   **接入**：封装一个 `SkillCritic` 服务。
    *   **职责**：专门负责分析失败轨迹，输出“技能拆分建议”或“新边建议”，作为图演化的输入，与主 Agent 解耦。

## 风险与坑

1.  **Teacher Model 成本与延迟**
    *   **风险**：每次演化都需要调用强模型（如 o3/GPT-4）来生成新技能或合并建议，推理成本极高，训练速度变慢。
    *   **对策**：
        *   仅在验证集（Validation Set）上触发演化，训练时冻结图。
        *   使用小模型（7B/14B）作为“初筛 Critic”，仅对高置信度的变更调用大模型。
        *   设置演化频率阈值（如每 1000 步一次）。

2.  **图污染与错误固化**
    *   **风险**：如果 Teacher Model 生成了一个错误的依赖（如“先灭火再关气”），RL 可能会强化这个错误路径，导致图结构“中毒”。
    *   **对策**：
        *   **人类反馈回路 (HITL)**：关键节点变更需人工确认。
        *   **置信度熔断**：新边的权重初始值设低，必须经过多次成功验证（如 5 次）才能提升权重。
        *   **对抗样本检测**：定期用“错误轨迹”测试图，若发现图能生成错误路径，触发回滚。

3.  **计算复杂度爆炸**
    *   **风险**：随着技能数量增加，图遍历（BFS/Beam Search）和拓扑排序的开销可能成为瓶颈，尤其是实时推理场景。
    *   **对策**：
        *   限制图深度（Depth Limit）。
        *   使用近似算法（如局部搜索）代替全局拓扑排序。
        *   将图结构预计算并缓存，仅在演化时更新。

4.  **冷启动困难**
    *   **风险**：初始图如果没有好的种子，Agent 可能陷入局部最优，无法发现新技能。
    *   **对策**：
        *   利用现有开源数据集（如 ALFWorld 的官方技能）进行冷启动。
        *   引入“随机探索”机制，强制 Agent 尝试未连接的技能，以发现新边。
