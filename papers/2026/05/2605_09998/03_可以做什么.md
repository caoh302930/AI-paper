# 可以做什么

基于 **Continual Harness** 的核心逻辑（无重置、在线 CRUD 优化、模型-Harness 协同），以下是可立即落地的执行方案。核心思想是：**让 Agent 在“带伤”运行中，实时修改自己的“操作手册”和“工具箱”，而不是等死机重来。**

## 可迁移到的场景（≥4）

1.  **长周期自动化运维 (AIOps) 故障自愈**
    *   **痛点**：服务器故障往往需要数小时排查，传统 Agent 一旦陷入死循环（如重启服务导致数据锁死），重置环境意味着丢失现场，无法定位根因。
    *   **应用**：Agent 在执行修复脚本时，若检测到日志报错或进度停滞（失败签名），**不重启服务**，而是实时修改自己的执行策略（如：增加“先备份再重启”的步骤，或调用新的诊断脚本），直接在当前故障现场进行“手术式”修复。

2.  **复杂 SaaS 流程自动化 (RPA 2.0)**
    *   **痛点**：企业软件（如 Salesforce, SAP）界面经常微调，传统 RPA 脚本极易因 UI 变化而断裂，且重新录制成本极高。
    *   **应用**：构建一个“自适应 RPA Agent"。当它发现某个按钮点击失败或弹窗未响应时，立即分析当前 DOM 树，**动态重写**其“点击策略”（如：从“按坐标点击”改为“按 XPath 搜索并点击”），并将新策略固化为技能库，无需人工干预即可适应界面变更。

3.  **多轮客服/销售谈判 Agent**
    *   **痛点**：在长达数天的客户沟通中，Agent 容易遗忘之前的承诺或陷入话术死循环，重置对话历史会破坏客户信任。
    *   **应用**：Agent 在对话过程中，若检测到客户情绪下降或重复拒绝（失败模式），**在线更新**其系统提示词（如：“该客户对价格敏感，需先强调价值”）或调用新的“情感安抚技能”，直接在当前对话流中调整策略，实现“边聊边进化”。

4.  **科研/数据分析探索助手**
    *   **痛点**：数据清洗和特征工程往往需要多次试错，传统工作流是“运行 -> 报错 -> 停止 -> 改代码 -> 重跑”，效率极低。
    *   **应用**：Agent 在运行数据管道时，若发现某步特征提取导致模型过拟合（失败信号），**不中断流程**，直接修改代码块（技能库），插入正则清洗或异常值处理逻辑，并继续运行后续步骤，实现“流式代码优化”。

## 可立刻试的小实验（≥3）

### 实验 1：死循环检测与策略热修复（Python + 简单环境）
*   **输入**：一个模拟的“迷宫搜索”脚本，初始策略包含一个导致死循环的 Bug（如：在特定坐标反复左右移动）。
*   **步骤**：
    1.  构建一个轻量级 Refiner 模块（可用 LLM API 实现），监控 Agent 最近 50 步的状态序列。
    2.  设定规则：若检测到状态 $(x, y, action)$ 重复出现 3 次，触发 Refiner。
    3.  Refiner 读取轨迹，生成一段新的 Python 代码片段（Skill），强制在检测到该坐标时执行“随机转向”或“跳过”。
    4.  将新代码动态注入到 Agent 的执行循环中，**不重启**模拟环境。
*   **期望输出**：Agent 在运行中途自动跳出死循环，并记录“已修复死循环逻辑”的日志，最终到达终点。

### 实验 2：动态记忆库的 CRUD 操作（RAG 场景）
*   **输入**：一个基于文档问答的 Agent，初始知识库缺失关键信息（如：用户问“退款政策”，文档里没写，Agent 瞎编）。
*   **步骤**：
    1.  让 Agent 回答用户问题，并记录其“幻觉”回答和用户随后的纠正（如：“不对，其实是 7 天”）。
    2.  触发 Refiner：检测到“用户纠正”模式。
    3.  Refiner 调用 `process_memory` 工具，将“退款政策=7 天”作为新事实写入向量数据库，并更新系统提示词：“在回答退款问题时，必须优先检索‘退款政策=7 天’这一记忆”。
    4.  用户再次提问。
*   **期望输出**：第二次提问时，Agent 能直接利用刚写入的记忆给出正确回答，无需重新检索原始文档。

### 实验 3：弱模型的能力增强（Co-Learning 简化版）
*   **输入**：一个能力较弱的开源模型（如 Qwen-1.5-7B）和一个强模型（如 GPT-4o）。
*   **步骤**：
    1.  让弱模型执行一个复杂任务（如：写一个带异常处理的爬虫），初始 Harness 极简。
    2.  当弱模型代码报错时，截取错误片段，发送给强模型（Teacher）进行“重标注”（生成正确代码）。
    3.  Refiner 将“错误片段 + 正确代码”封装为一个新的“异常处理技能”加入弱模型的技能库。
    4.  弱模型继续运行后续步骤，调用新技能。
*   **期望输出**：弱模型在单次运行中，通过调用动态生成的技能，完成了原本无法独立完成的复杂任务，且代码质量随运行步数提升。

## 产品 / Agent 灵感

1.  **“自进化”运维 Copilot**
    *   **核心卖点**：宣称“永不重启”。当系统故障时，Copilot 不是建议重启，而是现场修改运维脚本，像打补丁一样修复流程。
    *   **差异化**：传统 AIOps 是“事后复盘”，此产品是“事中自愈”。

2.  **游戏/模拟训练陪练平台**
    *   **核心卖点**：为游戏 AI 或机器人训练提供“在线教练”。玩家/机器人每走一步，教练就实时修改其“操作手册”，记录最佳路径，最终生成一套专属的“通关攻略”（即优化后的 Harness）。
    *   **变现**：出售针对特定高难度关卡的“自动进化攻略包”。

3.  **自适应客服中台**
    *   **核心卖点**：客服 Agent 具备“记忆生长”能力。遇到难缠客户，Agent 现场学习话术并更新策略，第二天遇到类似客户直接调用新策略。
    *   **价值**：大幅降低人工客服介入率，提升长尾问题的解决率。

## 跟现有系统怎么接

*   **架构层**：在现有 Agent 框架（如 LangChain, AutoGen）中插入 **Refiner 中间件**。
    *   *Hook 点*：在 `agent.run()` 的循环中，每 $N$ 步插入一次 `check_failure()`。
    *   *数据流*：`Trajectory Window` -> `Refiner (LLM)` -> `CRUD Operations` -> `Update Agent State`。
*   **工具层**：
    *   必须定义 **Meta-Tools**：`update_prompt`, `add_skill`, `delete_skill`, `write_memory`。现有 Agent 通常只调用业务工具，需扩展其权限以调用这些元工具。
*   **存储层**：
    *   需要支持 **动态结构存储**。传统的 KV 存储不够，需要支持代码片段（Skill）和结构化记忆（Memory）的增删改查接口。
*   **评估层**：
    *   引入 **过程奖励模型 (PRM)** 或简单的规则引擎（如：检测死循环、检测报错），作为 Refiner 的触发信号，替代传统的“回合结束奖励”。

## 风险与坑

1.  **能力下限陷阱（Capability Floor）**
    *   **风险**：如果基础模型太弱（如 Flash-Lite），Refiner 生成的修改可能是错误的，导致 Agent“越改越错”，陷入更深的死循环。
    *   **对策**：设置“熔断机制”。如果连续 3 次优化后性能未提升或下降，强制回滚到上一版本 Harness，或切换为人工干预模式。

2.  **记忆爆炸与检索噪音**
    *   **风险**：Refiner 可能会生成大量无用记忆（如“今天天气不错”），导致上下文窗口被占满，检索效率下降。
    *   **对策**：在 Refiner 中加入“记忆价值评估”步骤，仅保留高置信度、高复用性的记忆；设置记忆过期机制。

3.  **收敛性未知**
    *   **风险**：Harness 可能无限膨胀，策略变得极其复杂且难以解释（黑盒化）。
    *   **对策**：限制 Harness 组件的数量上限（如：最多 5 个子智能体，10 条核心记忆），并定期运行“剪枝”操作，删除长期未调用的技能。

4.  **安全与合规**
    *   **风险**：Agent 自动修改代码或系统提示词可能引入安全漏洞（如：注入恶意代码）。
    *   **对策**：Refiner 生成的代码/提示词必须经过沙箱运行或静态代码分析（SAST）验证通过后，才能注入到主流程。

- [ ] **构建 Refiner 原型**：编写一个简单的 Refiner 脚本，能识别“死循环”并生成修复策略。
- [ ] **能力阈值测试**：选取 3 个不同参数量的模型（小、中、大），在相同任务下测试“无重置优化”的效果，确定能力下限。
- [ ] **设计熔断机制**：制定具体的回滚策略（Rollback Policy），防止优化导致系统崩溃。
- [ ] **寻找非游戏场景**：选择一个真实的长程任务（如：数据清洗、代码调试）进行小规模 PoC 验证。
