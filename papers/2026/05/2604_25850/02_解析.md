## TL;DR and contributions
这篇论文提出了一种名为 **AHE (Agentic Harness Engineering)** 的闭环系统，旨在解决编码智能体（Coding Agent）的“外围工程”（Harness）难以自动优化的问题。传统上，智能体的提示词、工具、中间件和记忆机制依赖人工经验迭代，而 AHE 通过构建“组件、经验、决策”三大可观测支柱，让另一个智能体（Evolve Agent）能够自动修改这些工程组件，实现自我进化。

**Main contributions:**
*   提出了 **AHE** 框架，将 Harness 优化转化为一个基于可观测性的闭环进化过程，而非单纯的提示词微调。
*   设计了 **NexAU** 解耦底座，将 Harness 拆分为 7 种可独立编辑的文件级组件（如工具、中间件、记忆），使动作空间显式化。
*   引入了 **Agent Debugger** 和 **Change Manifest**，将海量轨迹蒸馏为分层证据，并将每次修改绑定为“可证伪的预测合同”，实现自动回滚。
*   在 Terminal-Bench 2 上，10 轮进化将 Pass@1 从 69.7% 提升至 **77.0%**，超越了人工设计的 Codex (71.9%) 和现有的自进化基线。

**Compared against:** Human-designed harnesses (OpenCode, Terminus-2, Codex), Self-evolving baselines (ACE, Training-Free GRPO).
**On datasets:** Terminal-Bench 2 (89 tasks), SWE-bench-verified (500 tasks).
**Headline improvements:** Terminal-Bench 2 Pass@1 **+7.3 pp** (69.7% → 77.0%); SWE-bench-verified 在保持最高成功率的同时，Token 消耗比种子模型减少 **12%**。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** **可观测性（Observability）是自动进化的瓶颈**。AHE 的核心不在于进化智能体有多强，而在于如何把“黑盒”的修改过程变成“白盒”的、文件级的、可验证的契约。重点阅读 3.1 (NexAU 解耦)、3.2 (证据蒸馏) 和 3.3 (决策可观测/Manifest)。
- **🔧 Useful in practice:** 对于希望构建自进化 Agent 的工程师，**Change Manifest** 的设计（预测修复 vs 预测回归）和 **文件级回滚** 机制是极具参考价值的工程实践。
- **📎 Nice to know:** 4.4.1 的消融实验揭示了组件间的**非加和性（Non-additive）**，即简单堆叠有效组件反而可能因冗余检查导致性能下降，这对理解 Agent 组件交互至关重要。
- **⚠️ Deprecated / superseded:** 论文指出单纯优化 Prompt（如 ACE）已不足以应对复杂任务，因为瓶颈在于工具链和中间件等结构化组件，这部分内容在 AHE 中被超越。

## Context and prerequisites

要理解 AHE，首先需要建立对 **Coding Agent Harness（编码智能体外围工程）** 的直观认知。在当前的 LLM 应用范式中，模型本身（Base Model）只是“大脑”，而 Harness 则是它的“手脚”和“感官系统”。它包含了系统提示词（System Prompt，决定行为风格）、工具（Tools，如 Shell、文件读写）、中间件（Middleware，控制上下文管理、错误恢复）以及记忆机制（Memory）。在长周期任务中，Harness 的设计往往比模型本身更能决定成败。然而，现有的 Harness 设计高度依赖人工试错：开发者看到 Agent 失败，手动修改 Prompt 或增加工具，这种“人工循环”跟不上模型能力的快速迭代。

其次，需要理解 **自动优化（Automated Optimization）** 在 Agent 领域的困境。早期的尝试（如 Prompt 进化）通常只修改文本指令，或者将 Agent 的输出作为反馈信号。但问题在于，Harness 的修改空间是**异构且耦合**的：修改一个工具的实现可能影响中间件的逻辑，而海量的执行轨迹（Trajectories）中充满了噪音，难以定位是哪个组件导致了失败。如果进化智能体无法清晰地看到“修改了什么”、“为什么修改”以及“修改后的真实效果”，它就会陷入盲目的随机搜索（Trial-and-Error）。AHE 正是为了解决这个“不可观测”的瓶颈，通过结构化手段将模糊的优化问题转化为清晰的工程迭代问题。

## Method

### The big picture (layman version)
想象你在训练一个新手程序员（Base Model）去修复杂的服务器故障。以前，你只能靠口头指导（Prompt）他，或者手动给他换工具。现在，AHE 引入了一个“资深导师”（Evolve Agent）。这个导师不直接写代码，而是负责**修改新手的工作台（Harness）**。

为了让导师能高效工作，AHE 做了三件事：
1.  **把工作台拆成积木**：不再是一团乱麻的代码，而是把提示词、工具、中间件等拆成独立的文件。导师想改工具，就只改工具文件，互不干扰。
2.  **把失败变成病历本**：新手修不好时，会产生大量日志。AHE 有一个“诊断员”（Agent Debugger），它把几百万字的日志读一遍，提炼出“哪里坏了、为什么坏”的简明报告，而不是让导师去读原始日志。
3.  **立下军令状**：导师每次修改工作台，必须写下“我改这个是为了修好 A 任务，但可能会搞坏 B 任务”。下一轮测试后，系统自动核对：如果 A 修好了，B 没坏，修改保留；如果 B 坏了，立刻回滚。

通过这种“拆积木、看病历、立军令状”的循环，工作台的配置会自动进化，越来越适应各种任务，而无需人类插手。

### The walkthrough

AHE 的运作流程是一个严格的闭环（Algorithm 1），其核心在于将模糊的“优化”转化为可执行的“文件编辑”和“契约验证”。

**第一步：构建解耦的底座（Component Observability）**
传统的 Agent 框架往往将 Prompt、工具逻辑和中间件耦合在一起，修改一处可能牵一发而动全身。AHE 基于 **NexAU** 框架，将 Harness $H$ 定义为 7 种正交组件类型的集合：系统提示词、工具描述、工具实现、中间件、技能（Skills）、子代理配置、长期记忆。
关键在于，这些组件被映射为工作空间中的**独立文件**。
$$ H = \{ \text{prompt}, \text{tools}, \text{middleware}, \dots \} $$
这种设计实现了**组件可观测性**：每一个失败模式（Failure Pattern）都可以被映射到单一组件类别。例如，如果 Agent 总是超时，问题可能出在“中间件”的超时设置，而不是“提示词”写得不够好。这使得进化智能体（Evolve Agent）的动作空间变得清晰且可回滚（Revertible），每一次修改都是 Git 中的一个 Commit。

**第二步：从噪音中提取证据（Experience Observability）**
进化需要反馈，但原始的执行轨迹（Trajectories）包含数百万个 Token，充满了无关信息。AHE 引入了 **Agent Debugger** 模块。
它的工作流是：
1.  **生成轨迹**：对基准测试中的每个任务运行 $k$ 次（$k \ge 2$），收集成功或失败的轨迹。
2.  **分层蒸馏**：Debugger 作为一个独立的 Agent，在轨迹文件系统中导航，分析失败的根本原因（Root Cause）。它不直接输出原始日志，而是生成**分层证据库**（Layered Evidence Corpus）：
    *   **任务级报告**：针对每个失败任务，指出具体错误。
    *   **基准级概览**：聚合所有报告，识别共性的失败模式。
    *   **原始轨迹索引**：保留原始数据供深度核查。
这种“渐进式披露”（Progressive Disclosure）机制让 Evolve Agent 能够以极低的 Token 成本获取高价值的诊断信息，而不是被海量数据淹没。

**第三步：基于证据的受控进化（Decision Observability）**
这是 AHE 最创新的部分。Evolve Agent 读取证据库后，决定修改哪些文件。为了防止“盲目修改”，AHE 强制要求**决策可观测性**：
1.  **变更清单（Change Manifest）**：每次修改必须附带一个 JSON 清单，包含：
    *   `failure_pattern`: 针对的失败模式。
    *   `predicted_fixes`: 预测能修复哪些任务。
    *   `risk_tasks`: 预测可能导致回归（Regression）的任务。
2.  **可证伪的契约**：这个清单不是自我辩解，而是一个**可证伪的预测**。在下一轮迭代（$t+1$）中，系统会将预测的修复集和回归集与实际的测试结果进行比对。
    *   如果预测正确（修复了任务且无回归），修改被保留。
    *   如果预测失败（未修复或引发回归），系统自动执行**文件级回滚**（Rollback）。

这种机制将进化过程从“黑盒试错”变成了“白盒实验”，确保了每一次性能提升都是可归因的（Attributable）。

## Challenges in the field — and what this work addresses

**挑战 1：动作空间的异构性与耦合性**
*   **难点**：在自动优化中，修改 Prompt 和修改底层工具代码是完全不同的操作空间。如果将它们混在一起优化，智能体很难判断哪个修改是有效的。且组件间高度耦合，修改一个工具可能导致中间件失效。
*   **AHE 的解法**：通过 **NexAU 解耦底座**，将动作空间离散化为文件级操作。每个组件类型（如 Middleware）对应独立的文件，使得“修改”这一动作变得原子化。这解决了“改哪里”的模糊性问题。

**挑战 2：轨迹信号的信噪比极低**
*   **难点**：Agent 执行长任务时，轨迹包含大量成功的中间步骤和无关的调试信息。直接从原始日志中提炼“为什么失败”需要极强的推理能力，且 Token 成本极高。
*   **AHE 的解法**：引入 **Agent Debugger** 作为中间层。它专门负责“阅读”轨迹并生成结构化的诊断报告。这相当于在“原始数据”和“进化决策”之间加了一个**特征工程层**，将非结构化的文本转化为结构化的“根因分析”，大幅降低了进化智能体的认知负荷。

**挑战 3：自我进化的不可控与不可归因**
*   **难点**：现有的自进化方法（如 Prompt 进化）往往缺乏对修改效果的严格验证。智能体可能“感觉”自己改好了，但实际上只是过拟合了测试集，或者引入了隐蔽的回归（Regression）。
*   **AHE 的解法**：通过 **Change Manifest** 和**预测 - 验证机制**。强制智能体在修改前声明预期结果，并在修改后通过实测数据验证。这种“预测即契约”的设计，使得无效修改能被自动识别并回滚，解决了“改得对不对”的归因问题。

**AHE 未解决的问题**：
*   **组件间的非线性交互**：论文发现，单独优化某个组件（如只加记忆）可能有效，但多个组件叠加时，由于交互作用（如重复检查），总收益反而下降。AHE 目前主要优化单一组件或简单组合，尚未完全解决复杂的组件协同优化问题。
*   **回归预测的盲区**：实验显示，Evolve Agent 能较好地预测“修复”，但很难预测“回归”（Regression Blindness）。这意味着系统仍可能引入一些未被预见的副作用。

## Experiments and results

**RQ1: 主结果（Terminal-Bench 2）**
*   **设置**：在 Terminal-Bench 2 (89 个任务) 上，从最小化的种子 Harness (NexAU 0, 仅 Shell 工具) 开始，进行 10 轮进化。
*   **结果**：
    *   **Pass@1**: 从 **69.7%** (Seed) 提升至 **77.0%**。
    *   **对比**：超越了人工设计的 Codex (71.9%)，以及自进化基线 ACE (68.9%) 和 TF-GRPO (72.3%)。
    *   **难度分布**：在 Easy 和 Medium 任务上提升显著（Medium 从 78.2% 升至 88.2%），Hard 任务略低于 Codex (53.3% vs 56.7%)，原因是组件间的冗余检查消耗了长任务的步数预算。

**RQ2: 泛化能力（Transfer）**
*   **跨基准测试 (SWE-bench-verified)**：
    *   AHE 进化后的 Harness 直接用于 SWE-bench-verified (500 任务)，无需重新进化。
    *   **成功率**：达到 **75.6%**，高于所有基线（包括 Seed 的 75.2%）。
    *   **效率**：Token 消耗比 Seed 减少 **12%**，比 ACE 减少 **32%**。这证明了 AHE 将策略编码在了工具/中间件中，而非依赖昂贵的 Prompt 重述。
*   **跨模型 (Cross-Model)**：
    *   在 5 种不同基座模型（GPT-5.4, Qwen, Gemini, DeepSeek）上测试。
    *   **结果**：所有模型均获得正向收益（+2.3 pp 到 +10.1 pp）。
    *   **洞察**：模型能力越弱（越未饱和），从 AHE 的组件优化中获益越大（如 DeepSeek 提升 10.1 pp），说明 AHE 编码的是通用的工程协调模式。

**RQ3: 消融与分析**
*   **组件贡献**：
    *   **Tools, Middleware, Memory** 单独替换进种子均能提升性能。
    *   **System Prompt** 单独替换反而导致性能下降（-2.3 pp），说明纯文本策略不如结构化组件有效。
    *   **非加和性**：三个有效组件单独提升之和（+11.1 pp）大于 AHE 整体提升（+7.3 pp），证明组件间存在复杂的相互抑制（如重复验证）。
*   **自我归因可靠性**：
    *   **修复预测**：Precision 33.7%, Recall 51.4%（远高于随机基线）。
    *   **回归预测**：Precision 11.8%, Recall 11.1%（仅略高于随机）。这证实了“回归盲区”的存在，是未来改进的关键方向。

## Open questions and limitations

1.  **组件交互的复杂性**：目前 AHE 主要采用贪心或局部搜索策略，未能完全解决组件间的非线性交互（Non-additive interaction）。未来可能需要引入更复杂的组合优化算法来寻找全局最优的组件配置。
2.  **回归预测的盲区**：Evolve Agent 难以预测修改带来的负面影响（Regression Blindness）。这导致进化曲线可能出现非单调波动。如何增强模型对“副作用”的推理能力是核心挑战。
3.  **基准依赖风险**：虽然跨基准测试表现良好，但进化过程仍是在 Terminal-Bench 2 上进行的。对于更广泛的编程语言、真实世界的复杂仓库（Human-in-the-loop workflows），其有效性尚未经过充分验证。
4.  **安全治理**：AHE 虽然限制了编辑范围，但作为一个自修改系统，其长期运行的安全性（如防止恶意代码注入、死循环）仍需更完善的治理机制。
