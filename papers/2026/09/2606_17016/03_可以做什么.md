# 可以做什么

基于 TokenPilot 的核心洞察（**缓存连续性 > 文本稀疏性**），我们可以将“长上下文管理”从单纯的“文本压缩”转变为“推理加速工程”。以下是具体的落地方案：

## 可迁移到的场景

1.  **企业级代码 Copilot / IDE 插件**
    *   **痛点**：开发者在长文件编辑中，IDE 插件频繁读取文件头、导入语句和工具定义，导致每次推理前缀变动，KV Cache 失效。
    *   **应用**：将文件头、Import 列表、工具 Schema 固定为静态占位符（Prefix Stabilization）。无论中间代码如何修改，Prompt 前缀 100% 命中缓存，推理延迟降低 40%+。

2.  **7x24 小时无人值守运维 Agent (SRE)**
    *   **痛点**：运维 Agent 处理连续告警流，历史日志（HTML/JSON）堆积，直接截断会丢失关键报错上下文；全量保留导致显存爆炸。
    *   **应用**：利用“外部存储 + 恢复机制”。将原始日志哈希存入对象存储，Prompt 中仅保留压缩版（去标签、截断）。当 Agent 需要追溯时，触发“恢复工具”拉取原始片段，而非一直保留在 Context 中。

3.  **多轮客服/销售对话机器人**
    *   **痛点**：客服机器人需要记住用户画像和之前的订单，但每次回复都重复加载这些静态信息，导致 Token 费用高企。
    *   **应用**：将用户画像、历史订单摘要、系统指令作为“全局稳定前缀”。仅动态部分（用户最新输入、当前轮次回复）参与压缩和淘汰，确保前缀缓存命中率接近 100%。

4.  **RAG（检索增强生成）系统**
    *   **痛点**：RAG 检索到的文档片段格式不统一，导致 Prompt 前缀混乱，无法复用缓存。
    *   **应用**：在检索层增加“格式标准化”模块，将不同来源的文档统一转换为标准模板（如 `### Document [ID] ###`），并移除动态元数据（如检索时间戳），使 RAG 的输入前缀在多次查询中保持一致。

## 可立刻试的小实验

### 实验 1：验证“前缀稳定化”对缓存命中的影响
*   **输入**：准备两个 Prompt，内容逻辑相同，但将“当前时间”从 `2023-10-27` 改为 `2023-10-28`，其他部分（系统指令、工具定义）完全一致。
*   **步骤**：
    1.  部署一个支持 Prefix Caching 的推理引擎（如 vLLM, TGI）。
    2.  开启详细日志，记录两次推理的 `cache_hit` 状态。
    3.  修改 Prompt 生成逻辑，将时间替换为 `{CURRENT_TIME}` 占位符，再次运行两次不同时间的请求。
*   **期望输出**：
    *   未优化前：第二次推理 `cache_hit = False`（需重新计算 Pre-fill）。
    *   优化后：第二次推理 `cache_hit = True`（直接复用缓存，首字延迟显著降低）。

### 实验 2：模拟“残差效用”淘汰策略
*   **输入**：构建一个包含 10 个历史任务片段的上下文（Task 1-10），其中 Task 5 包含一个文件路径，Task 10 需要引用该路径。
*   **步骤**：
    1.  实现一个简单的状态机：`Active` -> `Completed` -> `Evictable`。
    2.  设置规则：Task 5 完成后标记为 `Completed`，但检测到后续有依赖标记为“保留”。
    3.  模拟第 11 轮对话，触发批量清理（每 3 轮一次）。
    4.  对比两种策略：(A) 传统 LRU（直接删最旧的 Task 1）；(B) TokenPilot 策略（保留 Task 5，删除无依赖的 Task 1）。
*   **期望输出**：
    *   策略 A：Task 10 执行失败（找不到文件路径）。
    *   策略 B：Task 10 成功执行，且上下文长度比 A 更短（因为删除了更多无用中间态）。

### 实验 3：测试“安全阀”恢复机制
*   **输入**：一段包含 5000 字符的 HTML 网页内容。
*   **步骤**：
    1.  使用规则引擎（如 BeautifulSoup 去除标签）将其压缩为 500 字符的纯文本，存入 Prompt。
    2.  将原始 5000 字符存入本地 JSON 文件（模拟 Artifact Registry）。
    3.  构造一个需要精确 HTML 标签（如 `<table>` 结构）才能回答的问题。
    4.  让 Agent 先尝试回答，若失败或置信度低，调用“恢复工具”从 JSON 读取原始内容重试。
*   **期望输出**：
    *   直接回答：失败或幻觉（信息丢失）。
    *   恢复机制：成功获取完整信息，且平均 Token 消耗远低于“始终保留 5000 字符”的方案。

## 产品 / Agent 灵感

1.  **“缓存感知”的 Agent 中间件 (Middleware)**
    *   开发一个独立于 LLM 框架的中间件层（类似 Nginx），拦截所有 Agent 的 Prompt。
    *   功能：自动识别动态字段（时间、ID、路径）并替换为哈希占位符；自动管理上下文的生命周期状态；自动对接对象存储。
    *   卖点：对现有 Agent 代码“零侵入”，直接提升 50%+ 的推理吞吐。

2.  **长会话成本优化 SaaS 插件**
    *   针对使用 LangChain/LlamaIndex 的开发者，提供一键插件。
    *   功能：自动分析 Prompt 结构，生成“稳定前缀模板”；自动计算残差效用，建议哪些历史消息可以归档。
    *   价值：直接帮企业降低 LLM API 账单（尤其是长上下文场景）。

3.  **智能日志分析 Agent 平台**
    *   专为运维场景设计。
    *   核心逻辑：默认只加载“压缩版日志”进行推理，只有当 Agent 判定“信息不足”时，才异步拉取“原始日志”。
    *   优势：解决运维日志量巨大导致的 Token 爆炸问题，同时保证排查精度。

## 跟现有系统怎么接

1.  **推理引擎层 (vLLM / TGI / SGLang)**
    *   **必须开启**：`--enable-prefix-caching` (vLLM) 或对应参数。
    *   **配置**：调整 `max_num_batched_tokens` 以适配更长的稳定前缀。
    *   **对接点**：TokenPilot 的“前缀稳定化”模块必须在 Prompt 发送给推理引擎**之前**完成。

2.  **Agent 框架层 (LangChain / AutoGen)**
    *   **修改 Prompt 构建器**：在 `ChatPromptTemplate` 中引入“占位符替换”逻辑。
    *   **扩展 Memory 组件**：不要使用标准的 `ConversationBufferMemory`，而是实现一个 `TokenPilotMemory`，包含 `ArtifactRegistry`（外部存储）和 `LifecycleManager`（状态机）。
    *   **工具注册**：注册一个 `restore_artifact` 工具，供 Agent 在需要时调用。

3.  **数据存储层**
    *   **Artifact Registry**：使用 Redis (Hash) 或 S3/OSS (Object Storage) 存储原始大片段。Key 为内容哈希值，Value 为原始文本。
    *   **元数据存储**：使用轻量级数据库（SQLite/PostgreSQL）存储上下文片段的状态（Active/Completed/Evictable）和依赖关系图。

## 风险与坑

1.  **后端不支持 Prefix Caching**
    *   **风险**：如果推理引擎未开启或配置错误，TokenPilot 的“前缀稳定化”将毫无收益，甚至因为额外的替换逻辑增加延迟。
    *   **对策**：部署前必须通过实验验证 `cache_hit_rate`。

2.  **过度压缩导致“语义断裂”**
    *   **风险**：规则式压缩（如去 HTML 标签）可能破坏某些依赖特定格式的推理逻辑（如表格结构、代码缩进）。
    *   **对策**：必须保留“恢复机制”作为兜底；在压缩规则中加入白名单（如 `<code>`, `<pre>` 标签保留）。

3.  **残差效用评估模型误判**
    *   **风险**：轻量级评估模型（Estimator）可能错误判断某个已完成任务“无用”，导致后续任务失败。
    *   **对策**：设置保守阈值（如论文中的 $B=3$），不要每步都清理；对于关键任务（如代码生成），强制保留 `Completed` 状态直到任务链结束。

4.  **任务流高度混杂**
    *   **风险**：如果 Agent 频繁在不同类型的任务间切换（如从“写代码”跳到“查天气”），前缀复用率会大幅下降，收益降低。
    *   **对策**：在任务切换点（Task Switch）强制刷新缓存，或动态调整前缀模板。
