## TL;DR and contributions
TokenPilot 是一个专为长会话 LLM Agent 设计的上下文管理框架，其核心洞察在于：单纯压缩文本（减少 Token 数量）往往会破坏 Prompt 的前缀连续性，导致后端 KV Cache 失效，反而增加了计算成本。该框架通过“全局稳定前缀”和“局部生命周期感知”双重机制，在大幅减少输入 Token 的同时，维持了缓存的高命中率。

**Main contributions:**
- 提出了 **Ingestion-Aware Compaction**（摄入感知压缩），通过稳定占位符和工具定义重排，确保跨任务的前缀字节级一致。
- 设计了 **Lifecycle-Aware Eviction**（生命周期感知淘汰），基于残差效用（Residual Utility）而非简单的最近使用原则，保守地批量清理上下文。
- 在 PinchBench 和 Claw-Eval 上实现了连续模式下成本降低 **87%**（Claw-Eval 从 \$81.52 降至 \$10.58），同时保持任务性能不降。

**Compared against:** Vanilla (无管理), LLMLingua-2, SelectiveContext, LCM, Pichay, Summary, MemoBrain, AgentSwing, Keep-Last-N, MemOS.
**On datasets:** PinchBench (123 个真实世界任务，11 类), Claw-Eval (161 个通用任务，沙盒环境).
**Headline improvements:** 连续模式下，PinchBench 成本降 61%，Claw-Eval 成本降 87%；缓存命中率从 38.7% 提升至 79.2% (PinchBench)。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 理解“文本稀疏性”与“缓存连续性”之间的权衡（Trade-off）。核心在于**前缀稳定化（Prefix Stabilization）**：将动态变化的字段（如时间戳、路径）替换为静态占位符，使 Prompt 前缀在多次推理中保持字节级一致，从而复用 KV Cache。
- **🔧 Useful in practice:** **残差效用（Residual Utility）** 的评估机制。它不是简单地丢弃旧任务，而是判断旧任务对当前任务是否还有“剩余价值”（如文件引用、依赖关系），这比传统的 LRU（最近最少使用）更适合 Agent 场景。
- **📎 Nice to know:** 具体的规则式压缩策略（如 HTML 精简、日志截断）以及外部 Artifact Registry 的恢复机制（Fallback Loop）。
- **⚠️ Deprecated / superseded:** 传统的“每步清理”或“硬截断”策略在长会话中已被证明会导致缓存失效，TokenPilot 的“批量保守清理”是更优解。
- **🔕 Skippable:** 详细的基线模型超参数配置表（Appendix A.3），除非你要复现；标准的 Related Work 综述部分。

## Context and prerequisites

要真正理解 TokenPilot，必须先建立对 **KV Cache（键值缓存）** 和 **Prefix Caching（前缀缓存）** 的直观认知。在 LLM 推理中，计算量最大的部分不是生成新词，而是处理输入 Prompt 中的每一个 Token（即 Pre-fill 阶段）。为了加速，系统会将计算好的 Key 和 Value 矩阵存入显存（KV Cache）。如果下一次推理的 Prompt 开头和上一次完全一样，系统就可以直接复用这部分缓存，跳过昂贵的计算，这被称为“缓存命中”。然而，现有的 Agent 上下文管理方法（如摘要、截断）往往会改变 Prompt 的结构或内容，导致前缀“错位”，迫使系统重新计算所有 Token（缓存未命中），这种重复计算的开销往往远超节省下来的 Token 费用。

此外，需要理解 **Agent 的长会话特性**。与单次对话不同，Agent 在执行复杂任务（如写代码、分析日志）时，会不断累积工具调用记录、执行输出和中间状态。这些内容通常包含大量冗余信息（如 HTML 标签、重复的日志行），直接截断会导致信息丢失，而全部保留则会导致上下文窗口爆炸。TokenPilot 的突破点在于它不再单纯关注“删掉多少字”，而是关注“如何排列这些字才能让 GPU 的缓存机制发挥最大效能”。

## Method

### The big picture (layman version)
想象你在一个图书馆里整理书架（上下文管理）。以前的做法是：每来一本书（新任务），就把旧书里不重要的页撕掉，或者把书的位置挪来挪去。结果虽然书架空了，但每次找书时，因为书的位置变了，管理员（GPU）必须重新跑遍整个书架，效率极低。

TokenPilot 的做法完全不同：
1. **全局层面（整理书架规则）：** 它规定所有书的封面和目录页（Prompt 前缀）必须长得一模一样。比如，把“2023 年 10 月 1 日”这种每天变的时间，统一写成“日期占位符”。这样，无论任务怎么变，书架的最前面几层永远不变，管理员可以直接复用之前的记忆（缓存命中）。
2. **局部层面（决定留哪本书）：** 它不会每读一页就扔一本书。它会判断这本书虽然读完了，但后面可能还会用到（比如后面要查同一个文件）。只有当这本书彻底没用了，它才会在一个固定的时间点（比如每 3 轮对话）批量清理，避免频繁变动书架位置。

简而言之，TokenPilot 通过“固定前缀”让缓存能复用，通过“保守清理”避免频繁变动，从而在减少 Token 数量的同时，大幅降低了计算成本。

### The walkthrough

#### 1. 全局模块：摄入感知压缩 (Ingestion-Aware Compaction)
这是 TokenPilot 的“第一道防线”，在内容进入上下文之前进行处理。

**动机：** 传统的压缩是在 Prompt 生成后进行的，容易破坏前缀。TokenPilot 选择在“摄入门（Ingestion Gate）”就介入。
**步骤：**
- **前缀稳定化 (Prefix Stabilization)：** 系统识别出 Prompt 中的动态字段（如工作目录路径、时间戳、Session ID）。它定义了一个规范化算子 $\phi$，将这些动态内容替换为静态占位符。
  $$ \phi(m^{(t)}) = \phi(m^{(t+1)}) \implies \mathcal{C}'_{\text{prefix}} \subseteq \mathcal{C}'_{\text{hit}} $$
  这意味着，只要 $t$ 和 $t+1$ 时刻的输入经过 $\phi$ 处理后前缀一致，就能保证缓存命中。同时，它将工具定义（Tool Definitions）从 Prompt 中间移到末尾，避免不同任务的工具定义差异破坏前缀。
- **观察缩减 (Observation Reduction)：** 对于环境反馈（如 HTML 网页、日志），使用规则式方法（如去除标签、截断长日志）进行压缩。
  $$ m_{\text{ingest}} = \kappa(m), \quad \mathcal{A}[h(m)] \leftarrow m $$
  这里 $\kappa(m)$ 是压缩后的预览，$h(m)$ 是内容的哈希值。关键点在于，原始完整内容被存入外部存储 $\mathcal{A}$（Artifact Registry）。如果压缩版导致任务失败，Agent 可以调用“恢复工具”从 $\mathcal{A}$ 中拉取完整内容。这形成了一个**安全阀（Fallback Loop）**，既节省了 Token，又保证了信息不丢失。

#### 2. 局部模块：生命周期感知淘汰 (Lifecycle-Aware Eviction)
这是 TokenPilot 的“第二道防线”，负责在长会话中动态管理历史片段。

**动机：** 传统的 LRU 或固定窗口策略会过早丢弃可能仍有价值的上下文，或者保留无用的垃圾。
**步骤：**
- **状态标记：** 每个上下文片段 $c_j$ 被标记为三种状态：`active`（进行中）、`completed`（已完成但可能有残差价值）、`evictable`（可淘汰）。
  $$ \hat{U}(c_j) = \begin{cases} 1 & s_j = \textit{active} \\ \mathds{1}[\Psi_j \neq \emptyset] & s_j = \textit{completed} \\ 0 & s_j = \textit{evictable} \end{cases} $$
  其中 $\Psi_j$ 代表残差效用（Residual Utility）。即使任务完成，如果 $\Psi_j \neq \emptyset$（例如后续任务需要引用该文件），片段仍保留在 `completed` 状态，不立即删除。
- **保守批量触发：** 为了避免频繁的状态切换破坏缓存布局，系统不每一步都清理，而是每 $B$ 轮（实验设为 3 轮）触发一次。
  $$ \Delta\mathcal{R}_i^{(j)} = \langle E_j, \Psi_j \rangle = \mathcal{E}(\mathcal{V}_i, \mathcal{R}_{i-1}) $$
  这里 $\mathcal{E}$ 是一个轻量级模型（Qwen3.5-35B-A3B），它分析压缩后的历史视图 $\mathcal{V}_i$，判断哪些片段可以进入 `evictable` 状态。
- **执行清理：** 只有当状态确认为 `evictable` 时，才执行物理删除。
  $$ \mathcal{C}' = \{ m \in \mathcal{C} \mid s_{j(m)} \neq \textit{evictable} \} $$

这种设计确保了缓存布局的稳定性，同时通过残差效用判断避免了“误删”导致的信息缺失。

## Challenges in the field — and what this work addresses

1.  **缓存失效与文本压缩的矛盾：**
    *   **难点：** 现有的压缩方法（如摘要、截断）虽然减少了 Token 数，但改变了 Prompt 的字节序列，导致后端 KV Cache 失效。重新计算 Pre-fill 的成本往往远高于节省的 Token 费用。
    *   **TokenPilot 的解法：** 将“压缩”和“缓存”解耦。通过**前缀稳定化**，强制让 Prompt 的前缀部分保持字节级一致，使得压缩主要发生在不影响缓存命中的后部或内部，从而在不牺牲缓存效率的前提下减少 Token。

2.  **长会话中的上下文冗余与关键信息丢失：**
    *   **难点：** Agent 在长任务中会积累大量工具输出（如 HTML、日志）。直接截断会丢失关键细节，导致任务失败；全部保留则成本爆炸。
    *   **TokenPilot 的解法：** 引入**外部存储 + 恢复机制**。压缩版用于日常推理，原始数据存于外部。只有当 Agent 发现信息不足时，才按需恢复。这解决了“压缩导致信息丢失”的痛点。

3.  **动态上下文管理的过度频繁：**
    *   **难点：** 每一步都判断是否清理上下文，不仅计算开销大，而且频繁的删除/插入操作会打乱缓存的物理布局，降低命中率。
    *   **TokenPilot 的解法：** **批量保守清理**。通过每 3 轮触发一次，并引入“残差效用”作为缓冲，让已完成的上下文在 `completed` 状态停留一段时间，避免过早淘汰，同时减少状态切换频率。

**本工作未解决的问题：** 如果任务流高度混杂（不同类别的任务频繁切换），前缀复用率会自然下降，此时 TokenPilot 的收益会减弱。此外，该方法强依赖后端支持 Prefix Caching，对于不支持该特性的推理引擎无效。

## Experiments and results

实验在 **PinchBench** 和 **Claw-Eval** 两个基准上进行，分为 **Isolated Mode**（单任务独立）和 **Continuous Mode**（连续任务流）。

*   **成本降低（核心指标）：**
    *   **Claw-Eval (Continuous):** 成本从 Vanilla 的 **\$81.52** 降至 TokenPilot 的 **\$10.58**，降幅达 **87%**。
    *   **PinchBench (Continuous):** 成本从 **\$7.24** 降至 **\$2.79**，降幅 **61%**。
    *   **Isolated Mode:** 同样实现了 56%-61% 的成本降低。
*   **性能保持：**
    *   在成本大幅下降的同时，任务得分（Score）与 Vanilla 持平甚至略高（PinchBench: 81.3 vs 79.2; Claw-Eval: 60.8 vs 63.4，差异在统计误差范围内）。
*   **缓存命中率提升：**
    *   PinchBench 上，缓存命中率从 38.7% 提升至 **79.2%**。
    *   消融实验显示，仅使用“前缀稳定化”就能将成本从 \$8.31 降至 \$4.35，证明了缓存优化的巨大价值。
*   **关键发现：**
    *   **恢复工具的重要性：** 如果去掉恢复工具（Fallback），任务得分从 80.9 降至 77.1，且成本回升，证明“安全阀”机制不可或缺。
    *   **批量触发频率：** 实验表明 $B=3$（每 3 轮清理一次）是最佳平衡点，$B=1$ 会导致缓存命中率下降，$B=\infty$ 会导致上下文爆炸。

## Open questions and limitations

1.  **对后端架构的强依赖：** TokenPilot 的收益完全建立在后端支持 **Prefix Caching** 的基础上。如果推理引擎（如某些开源框架的默认配置）不支持或配置不当，该方法的优势将大打折扣。
2.  **高度混杂任务流的挑战：** 论文承认，在任务类别频繁切换（Mixed-category streams）的场景下，前缀复用率会下降，导致成本节省幅度减小。如何动态适应这种高熵任务流是一个开放问题。
3.  **Estimator 的误判风险：** 虽然轻量模型成本很低，但在信号模糊时仍可能误判“残差效用”，导致过早清理或保留无用信息。
4.  **参数调优：** 批量大小 $B$ 和频率阈值 $\tau$ 需要根据具体的部署环境和任务分布进行调整，缺乏自适应机制。
