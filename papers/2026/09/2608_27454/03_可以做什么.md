# 可以做什么

基于 WikiSkill 的核心逻辑（**持久化经验库 + 执行者隔离 + 结构化知识提炼**），以下是可直接落地的行动指南。核心思路是：**不要只存日志，要存“教训”和“模式”；不要让执行者看答案，要让它“盲跑”产生真实数据。**

## 可迁移到的场景（≥4）

1.  **企业级 RAG 知识库的“错题集”系统**
    *   **痛点**：传统 RAG 只检索文档，不检索“检索失败的原因”。用户问错、模型答错后，系统没有记忆，下次还错。
    *   **WikiSkill 方案**：建立 `wiki/failed_queries.md`。当 RAG 检索失败或回答被用户点踩时，由维护者 Agent 分析原因（是关键词不匹配？还是文档缺失？），提炼为 `pattern`（如：“涉及财务数据时，必须优先检索 Q3 财报而非新闻稿”）。
    *   **价值**：RAG 系统越用越聪明，自动积累“避坑指南”。

2.  **自动化测试/CI/CD 的“防御性脚本库”**
    *   **痛点**：测试脚本经常因为环境波动、特定边界条件失败，修复脚本往往是一次性的，下次类似错误依然发生。
    *   **WikiSkill 方案**：将测试失败轨迹存入 `raw/`，由 Wiki Maintainer 分析失败模式（如：“数据库连接超时通常发生在高并发前 30 秒”），生成通用的 `retry_pattern` 或 `mock_strategy` 存入 Wiki。
    *   **价值**：测试框架具备“自愈”和“防御”能力，自动规避历史已知的环境噪声。

3.  **低代码/无代码平台的“最佳实践”生成器**
    *   **痛点**：用户搭建工作流时，常犯逻辑错误（如循环死锁、变量作用域错误），平台缺乏实时指导。
    *   **WikiSkill 方案**：记录用户构建工作流的“失败尝试”，提炼出 `anti-patterns`（反模式）。当新用户构建类似流程时，Skill Proposer 基于 Wiki 中的教训，动态注入“防错提示”或“推荐模板”。
    *   **价值**：将用户的试错成本转化为平台的通用资产，降低上手门槛。

4.  **具身智能（Robotics）的“安全操作手册”**
    *   **痛点**：机器人在新环境中容易重复撞墙、抓取失败，且难以将一次失败的经验泛化到类似物体。
    *   **WikiSkill 方案**：机器人执行任务时（禁止看 Wiki），记录碰撞/抓取失败轨迹。Wiki 层将“抓取圆柱体时角度需>30 度”等物理规律结构化。
    *   **价值**：机器人通过积累“物理常识”而非单纯微调参数，快速适应新物体，且历史安全教训永久保留。

## 可立刻试的小实验（≥3）

### 实验 1：构建“失败模式提取器” (Wiki Maintainer 原型)
*   **目标**：验证能否从杂乱日志中自动提炼结构化知识。
*   **输入**：
    *   一段包含 3-5 次失败尝试的 Agent 对话日志（JSON 格式，包含 `thought`, `action`, `observation`, `error`）。
    *   现有的 Wiki 文件（Markdown，包含少量已知模式）。
*   **步骤**：
    1.  编写 Prompt，让 LLM 扮演"Wiki Maintainer"。
    2.  指令：分析新日志，识别与现有 Wiki 中模式是否重复。
    3.  若不重复，提取“失败根因”和“建议策略”，生成一个新的 Markdown 片段（包含 `title`, `symptoms`, `root_cause`, `solution`）。
    4.  若重复，更新现有条目的 `occurrence_count`。
*   **期望输出**：
    *   一个更新后的 Markdown 文件。
    *   新增或更新了一条清晰的 `pattern`（例如：“当 API 返回 429 时，不应立即重试，需检查 Rate Limit 头”）。

### 实验 2：验证“执行者隔离”效应
*   **目标**：证明执行者不看 Wiki 能产生更高质量的探索数据。
*   **输入**：
    *   一个简单任务（如：用 Python 代码解决一个复杂的数学题，或操作一个模拟 Excel）。
    *   两个版本的 System Prompt：
        *   A 版：包含 Wiki 中的“解题技巧”。
        *   B 版：不包含 Wiki，仅包含基础指令。
*   **步骤**：
    1.  让模型 A 运行 10 次，记录轨迹。
    2.  让模型 B 运行 10 次，记录轨迹。
    3.  计算两条轨迹的“信息熵”或“尝试多样性”（统计不同的 `action` 序列数量）。
*   **期望输出**：
    *   数据对比：模型 B（隔离版）的尝试序列多样性显著高于模型 A。
    *   结论：模型 A 倾向于“走捷径”或“照搬”，模型 B 进行了真正的推理和试错，产生的数据更适合用于后续进化。

### 实验 3：小模型 + 经验库 vs 大模型
*   **目标**：复现“小模型带技能超越大模型”的现象。
*   **输入**：
    *   一个中等难度的任务集（如 5 道逻辑推理题）。
    *   模型 A：小参数模型（如 Qwen-7B 或 Llama-3-8B）。
    *   模型 B：大参数模型（如 Qwen-72B 或 GPT-4o-mini）。
    *   一个预制的 Wiki 文件（包含 3-5 条针对该任务类型的成功策略）。
*   **步骤**：
    1.  模型 A + Wiki（将 Wiki 内容注入 System Prompt）运行任务。
    2.  模型 B（无 Wiki，纯基线）运行任务。
    3.  对比准确率。
*   **期望输出**：
    *   在特定垂直领域（如特定格式的表格处理、特定逻辑陷阱），模型 A + Wiki 的准确率接近或超过模型 B。
    *   验证 Wiki 中的“规则”比“参数知识”在特定任务上更有效。

## 产品 / Agent 灵感

1.  **“记忆增强型”客服 Agent**
    *   **功能**：客服 Agent 每次解决完一个复杂投诉，自动将“用户情绪转折点”和“成功安抚话术”存入 Wiki。
    *   **创新**：新客服 Agent 上岗时，不是读 SOP 文档，而是直接加载“历史成功/失败案例库”，瞬间具备资深客服的经验。

2.  **代码审查（Code Review）的“模式识别器”**
    *   **功能**：不只看当前代码，而是对比 Wiki 中的“历史 Bug 模式”。
    *   **创新**：如果 Wiki 记录过“某类并发锁会导致死锁”，当新代码出现类似结构时，Agent 直接报警并给出基于历史教训的修复建议，而非通用的代码规范。

3.  **个人知识管理（PKM）的“进化助手”**
    *   **功能**：用户在做笔记时，Agent 自动分析笔记中的“决策失误”或“灵感来源”，将其转化为可复用的 `pattern`。
    *   **创新**：你的笔记库不仅是存储，而是一个不断进化的“决策操作系统”，下次遇到类似问题，它直接推送“上次你在这里踩了坑，这次试试 B 方案”。

## 跟现有系统怎么接

*   **接入 RAG 系统**：
    *   **位置**：在 RAG 的 `Retriever` 和 `Generator` 之间插入 `Wiki Layer`。
    *   **流程**：用户提问 -> 检索文档 -> **检索 Wiki 中的“失败模式”**（如：此问题常因缺少某参数失败） -> 将模式注入 Prompt -> 生成回答。
    *   **更新**：用户反馈（点赞/点踩） -> 触发 `Wiki Maintainer` -> 更新 Wiki。

*   **接入 LangChain / LlamaIndex**：
    *   **组件**：自定义一个 `WikiMemory` 类，继承自 `BaseChatMessageHistory`。
    *   **实现**：重写 `add_messages` 方法，不仅存消息，还调用一个 `analyze_and_patch` 函数，将失败消息转化为 Markdown 补丁写入本地文件系统或向量库。
    *   **隔离**：在 `AgentExecutor` 的 `system_prompt` 构建阶段，**故意不**包含 Wiki 内容给执行 Agent，仅在 `Tool` 调用或 `Skill` 注入阶段由外部控制注入。

*   **接入 CI/CD 流水线**：
    *   **位置**：在测试失败后的 `Post-Run` 脚本中。
    *   **逻辑**：解析测试报告 -> 调用 Wiki Maintainer API -> 更新 `wiki/patterns/` -> 触发 `Skill Proposer` 生成新的测试脚本补丁 -> 提交 PR。

## 风险与坑

1.  **Wiki 膨胀与噪声（Garbage Collection）**
    *   **风险**：Wiki 无限累积，包含大量过时或错误的模式，导致检索噪音，甚至误导技能提案者。
    *   **对策**：必须设计 `Wiki Pruner` Agent，定期扫描 Wiki，根据 `occurrence_count`（出现频率）和 `last_success_date`（最后成功日期）标记低价值条目，或自动归档到 `archive/`。

2.  **执行者“作弊”（Leakage）**
    *   **风险**：如果不小心在 System Prompt 中泄露了 Wiki 内容，执行者会直接“抄答案”，导致生成的轨迹失去探索价值，进化循环失效。
    *   **对策**：在工程实现上，严格物理隔离。执行者的上下文窗口（Context Window）构建代码中，**硬编码禁止**读取 `wiki/` 目录。

3.  **负迁移（Negative Transfer）**
    *   **风险**：小模型进化出的“特定技巧”（Workaround）可能在大模型上失效，甚至产生干扰（如论文中提到的 18.1% 案例）。
    *   **对策**：在 `Skill Proposer` 阶段增加“模型适配性检查”。如果目标模型能力更强，强制过滤掉过于底层的、针对弱模型缺陷的补丁，只保留通用逻辑。

4.  **回滚机制的复杂性**
    *   **风险**：技能回滚容易，但 Wiki 中的知识如果基于错误的技能生成，可能导致知识污染。
    *   **对策**：Wiki 条目应包含 `source_skill_version` 和 `validation_status`。当技能回滚时，相关 Wiki 条目自动标记为 `suspicious`，暂停使用，直到被新数据验证。
