## TL;DR and contributions
这篇论文提出了一种名为 **SKILL.state** 的运行时架构，旨在解决大语言模型（LLM）智能体在执行长周期任务时，因不断追加历史对话导致上下文爆炸、推理延迟增加以及“上下文中毒”（即旧信息干扰新判断）的问题。它不再依赖不断增长的对话历史，而是维护一个显式的、结构化的**执行状态（Execution State）**，每一步只向模型输入当前状态和最新观察，并在验证后丢弃中间推理过程。

**Main contributions:**
- 提出 SKILL.state 架构，将长程执行从“追加历史”重构为“状态转移”，实现提示词大小恒定（$\mathcal{O}(1)$）和累计 Token 消耗线性增长（$\mathcal{O}(T)$）。
- 构建了 **SkillExecBench** 诊断基准，并在 InterCode CTF 和 $\tau$-Bench 等公开基准上验证了该方法。
- 证明了结构化状态管理在抗噪性、状态恢复能力和长程执行效率上显著优于传统的 ReAct、摘要压缩及 LangGraph 等基线。

**Compared against:** Prompt (ReAct-style), Memory (Summarization-style), Stateful (LangGraph-style), Truncated (Sliding Window), Summary-capped, ReAct + LLMLingua.
**On datasets:** SkillExecBench (Warehouse Management, Software Repository), InterCode CTF, Sierra $\tau$-Bench (Retail, Airline).
**Headline improvements:** 在 200 步的 Warehouse 任务中，SKILL.state 将总 Token 消耗从基线的 617 万降至 12.2 万（约 50 倍减少），同时准确率从 0.84 提升至 0.94；在 InterCode CTF 中 Pass@1 达到 54.2%，比最强基线高出 7.8 个百分点。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 核心在于将“执行状态”作为一等公民（First-class abstraction），用结构化 Schema 替代自然语言历史。关键机制是：模型输出推理 + 状态补丁（State Patch），运行时验证补丁并合并，随后**永久丢弃**推理过程，只保留更新后的状态。
- **🔧 Useful in practice:** 状态模式（Schema）的设计方法（如 InterCode 中的 5 个字段）、运行时验证逻辑（防止模型破坏状态）、以及如何处理外部状态漂移（State Recovery）。
- **📎 Nice to know:** 复杂度分析（$\mathcal{O}(T^2)$ vs $\mathcal{O}(T)$）的数学推导、不同模型（Gemma, Qwen）在结构化输出上的错误分类（Error Taxonomy）。
- **⚠️ Deprecated / superseded:** 传统的“全量历史追加”（ReAct 标准模式）在长程任务中已被证明效率低下且易受干扰；简单的文本摘要（Summarization）在保留关键状态依赖上不如结构化状态。
- **🔕 Skippable:** 详细的附录 Prompt 模板（除非要复现）、具体的噪声生成代码细节、以及部分扩展实验的完整数据表（核心结论已在主表体现）。

## Context and prerequisites

要理解这篇论文，首先需要理解当前 LLM 智能体运行的一个根本矛盾：**记忆与推理的耦合**。传统的智能体（如 ReAct 范式）在执行每一步时，都会把之前的所有观察、动作和推理记录像“聊天记录”一样全部塞进 Prompt 里。这就像一个人做长任务时，必须把过去几千步的日记全部背在脑子里才能决定下一步。随着任务变长，这个“日记本”越来越厚，不仅消耗大量 Token（金钱和速度），更重要的是，旧日记里的细节会干扰模型对当前事实的判断，导致模型“记混”或“幻觉”。

其次，需要理解**结构化状态（Structured State）**与**自然语言历史**的本质区别。结构化状态类似于数据库中的表或程序中的变量，它只包含“当前世界是什么样”的精确信息（例如：库存里有什么、文件在哪个目录），而不包含“我是怎么知道的”或“我刚才想了什么”。这种状态是“充分统计量”（Sufficient Statistic），意味着只要有了当前状态，就不需要回溯历史也能做出正确的下一步决策。这与对话状态跟踪（DST）有相似之处，但 DST 通常用于静态对话，而 SKILL.state 用于动态、长程的自主执行。

最后，理解**上下文窗口（Context Window）的局限性**至关重要。虽然现在的模型支持超长上下文，但研究表明模型在长文本中存在“迷失中间”（Lost in the Middle）现象，且检索精度随长度增加而下降。SKILL.state 的核心洞察是：与其让模型去“压缩”或“检索”历史，不如直接不让历史进入 Prompt，只保留经过验证的当前状态。这从根本上改变了智能体的运行范式，从“基于历史的推理”转变为“基于状态的转移”。

## Method

### The big picture (layman version)
想象你在玩一个复杂的策略游戏，传统做法是每走一步，就把之前所有的游戏日志、你的内心独白、敌人的所有动作全部抄写在一张越来越长的纸上，然后带着这张纸去问 AI 下一步怎么走。纸太厚了，AI 看不过来，而且容易被几百年前的旧日志误导。

SKILL.state 的做法完全不同：它准备了一个**“当前局势面板”**（结构化状态），上面只写着现在的关键信息（比如：你在哪、背包里有什么、任务进度）。每走一步，AI 只看这个面板和最新的敌人动作，然后告诉系统：“我要移动，并且更新面板上的位置信息”。系统验证这个更新是否合法（比如不能穿墙），如果合法，就**只更新面板**，然后把 AI 刚才的“内心独白”（推理过程）直接扔进垃圾桶。下一轮开始时，AI 只面对更新后的面板。这样，无论游戏进行一万步，AI 每次看到的“纸”大小都是一样的，既快又准，完全不会被旧历史干扰。

### The walkthrough

**1. 动机：为什么历史是负担？**
在传统的运行时（如 ReAct），第 $t$ 步的输入 $C_t$ 包含了从 $0$ 到 $t-1$ 的所有交互历史。
$$ C_t = \{ (O_0, R_0, A_0), \dots, (O_{t-1}, R_{t-1}, A_{t-1}) \} $$
随着 $t$ 增加，$|C_t|$ 线性增长，导致累计 Token 消耗呈二次方增长 $\mathcal{O}(T^2)$。更严重的是，历史中包含大量过时的观察（Obsolete Observations）和错误的推理（Hallucinated Reasoning），模型必须不断在 Prompt 中区分“过去的事实”和“现在的状态”，这极大地增加了认知负荷。

**2. 核心设计：显式状态转移**
SKILL.state 将执行过程重新定义为状态转移。在第 $t$ 步，模型接收的输入 $A_t$ 仅包含三部分：
$$ A_t = (P, \Sigma_t, O_t) $$
- $P$：**程序规范（Procedural Specification）**，即任务的固定指令，不可变。
- $\Sigma_t$：**结构化执行状态（Structured Execution State）**，当前时刻的世界快照。
- $O_t$：**最新观察（Latest Observation）**，环境反馈。

**3. 执行循环（The Loop）**
算法流程如下（参考 Algorithm 1）：
1.  **构造 Prompt**：系统组装 $(P, \Sigma_t, O_t)$。注意，这里**没有**历史对话。
2.  **模型生成**：LLM 输出三元组 $(R_t, \Delta\Sigma_t, a_t)$。
    - $R_t$：思维链（Chain-of-Thought），用于内部推理。
    - $\Delta\Sigma_t$：**状态补丁（State Patch）**，一个 JSON 对象，描述如何修改 $\Sigma_t$（例如：`{"inventory": {"shelf_42": null}}` 表示移除物品）。
    - $a_t$：要执行的动作（Action）。
3.  **验证与合并**：运行时（Runtime）对 $\Delta\Sigma_t$ 进行确定性验证（检查字段类型、格式、逻辑合法性）。
    - 如果合法，执行状态更新：$\Sigma_{t+1} = \Sigma_t \oplus \Delta\Sigma_t$。这里的 $\oplus$ 是字典合并操作，支持覆盖和删除（null 语义）。
    - 执行动作 $a_t$，获取新观察 $O_{t+1}$。
4.  **丢弃推理**：**关键步骤**。$R_t$ 被永久丢弃，绝不进入下一轮 Prompt。

**4. 为什么这样设计？**
- **抗噪性**：因为历史观察不进入 Prompt，环境中的无关噪声（如系统日志、传感器数据）只要不改变当前状态，就不会干扰模型。
- **效率**：Prompt 大小被限制在 $|P| + |\Sigma| + |O|$，与步数 $t$ 无关，即 $\mathcal{O}(1)$。累计消耗变为 $\mathcal{O}(T)$。
- **状态恢复**：如果外部世界发生了模型不知道的变化（如库存被他人移动），新的观察 $O_{t+1}$ 会直接反映在状态更新中，模型无需“回忆”过去，直接根据新状态修正即可。

**5. 状态模式（Schema）的重要性**
状态不是自由文本，而是预定义的 Schema。例如在 InterCode CTF 中，Schema 固定为 5 个字段：`discovered_flags`, `tested_hypotheses`, `active_files`, `working_dir`, `cmd_summary`。这种约束迫使模型将非结构化的推理转化为结构化的事实，避免了信息在自然语言中的模糊传递。

## Challenges in the field — and what this work addresses

**挑战 1：长程执行中的上下文膨胀与成本失控**
- **难点**：随着任务步数增加，传统方法的 Prompt 长度呈线性增长，导致推理延迟和 Token 成本呈二次方爆炸。即使使用长上下文模型，检索关键信息的准确率也会下降。
- **本文方案**：通过**状态截断**（State Truncation）而非文本截断，将 Prompt 大小锁定为常数。无论执行 10 步还是 200 步，输入大小基本不变，彻底解决了成本随时间爆炸的问题。

**挑战 2：历史噪声与“上下文中毒”**
- **难点**：在长任务中，早期的错误推理或无关观察会残留在 Prompt 中，误导模型做出后续错误决策（例如：模型可能因为 10 步前的一个错误假设而坚持错误的路线）。
- **本文方案**：**丢弃中间推理**。模型只基于当前状态 $\Sigma_t$ 和最新观察 $O_t$ 决策。历史中的错误推理一旦转化为状态补丁并验证失败，就不会进入下一轮；即使成功，也只保留修正后的事实，彻底切断了错误推理的传递链条。

**挑战 3：外部状态漂移（State Drift）的恢复**
- **难点**：在真实环境中，状态可能由外部因素改变（如仓库管理员手动移动了货物），而模型的历史记录仍显示旧位置。传统方法需要模型“意识到”历史与观察冲突并自我修正，这通常需要多步恢复。
- **本文方案**：由于决策仅依赖当前状态，一旦新观察 $O_t$ 触发状态更新（如“物品已移动”），$\Sigma_t$ 立即修正。实验显示，SKILL.state 在状态漂移后**0 步**即可恢复，而基线方法需要 5-8 步。

**本文未解决的问题**：
- **动态 Schema 发现**：如果任务没有预定义的状态结构，或者状态结构随任务动态变化，SKILL.state 难以直接应用。
- **历史依赖型任务**：如果任务目标本身就是回顾历史（如审计、调试、解释“为什么当时这么做”），丢弃历史会导致无法完成任务。

## Experiments and results

实验在多个基准和模型上进行了验证，核心发现如下：

**1. 长程扩展性（Long-Horizon Scaling）**
在 Warehouse 任务中，随着步数 $T$ 从 10 增加到 200：
- **Token 消耗**：ReAct 基线在 $T=200$ 时消耗 **6,175,509** tokens，而 SKILL.state 仅消耗 **122,384** tokens（减少约 98%）。
- **准确率**：ReAct 在 $T=200$ 时准确率降至 **0.74**，而 SKILL.state 保持在 **0.94**。
- **结论**：SKILL.state 不仅大幅降低成本，还随着任务变长，相对优势越明显。

**2. 抗噪性（Noise Robustness）**
在注入 50 个无关事件（高噪声）的情况下：
- ReAct 准确率暴跌至 **0.53**。
- SKILL.state 保持在 **0.98**。
- **原因**：无关噪声被过滤在状态更新之外，未进入下一轮 Prompt。

**3. 状态恢复（State Recovery）**
当外部修改状态（如物品被移动）：
- 基线方法（Prompt/Memory/Stateful）平均需要 **5-8** 步才能纠正幻觉。
- SKILL.state 需要 **0** 步，立即响应新观察。

**4. 公开基准表现**
- **InterCode CTF**：Pass@1 达到 **54.2%**，比最强基线（Memory）高 7.8%，比 ReAct 高 11%。
- **$\tau$-Bench Retail**：通过率 **58.3%**，Token 消耗降低 60%。
- **$\tau$-Bench Airline**：通过率 **32.4%**，在复杂数据库响应下保持低 Token 消耗。

**5. 预算匹配控制（Budget-Matched Controls）**
当强制限制基线方法的 Token 预算与 SKILL.state 相同时：
- 滑动窗口（Truncated）准确率降至 **0.18**（丢失关键早期信息）。
- 统计压缩（LLMLingua）降至 **0.22**（误删关键语义）。
- SKILL.state 仍保持 **0.94**。
- **结论**：性能提升源于**结构化状态**，而非单纯的文本缩短。

## Open questions and limitations
1. **Schema 设计的门槛**：SKILL.state 高度依赖预先设计的状态模式。对于开放域、无固定结构的新任务，如何自动推导或动态调整 Schema 是一个未解之谜。
2. **多 Agent 并发冲突**：论文提到多 Agent 场景下，共享状态的并发写入需要确定性的冲突解决机制（Conflict Resolution），目前仅在单 Agent 下验证。
3. **历史审计需求**：对于需要解释“为什么”或“过程是什么”的任务（如法律审计、故障排查），丢弃推理过程 $R_t$ 可能导致无法追溯决策路径。
4. **小模型的格式化能力**：实验显示，小模型（如 Qwen-8B）在生成结构化 JSON 时容易出错（12% 的语法错误），这限制了其在低资源场景下的直接应用，需要结合语法约束解码（Grammar-constrained decoding）。

- **视频强调点**：视频（Agent 智能体深度研究院）准确抓住了“从追加消息到只保留状态”的核心转变，并重点展示了 Warehouse 任务中 Token 消耗的巨大差异（600 万 vs 12 万），这与论文 Table 1 的数据一致。
