# 可以做什么

基于 SKILL.state 的核心范式（**结构化状态转移 + 运行时验证 + 丢弃推理历史**），以下是可立即落地的执行方案。核心逻辑是：**将 Agent 从“聊天机器人”改造为“状态机控制器”**。

## 可迁移到的场景（≥4）

1.  **复杂工作流编排（Workflow Orchestration）**
    *   **场景**：电商订单处理、SaaS 客户 Onboarding、多步骤数据清洗。
    *   **痛点**：传统 Agent 在 10+ 步流程中容易“忘记”之前的参数（如订单 ID、用户偏好），导致重复查询或逻辑冲突。
    *   **应用**：定义 `OrderState` (status, items, payment_status, shipping_addr)。每步只更新状态字段，不保留对话。若中间某步失败，只需回滚状态字段，无需重放整个对话。

2.  **长周期代码/数据工程（Long-horizon Coding & ETL）**
    *   **场景**：自动化重构大型代码库、跨文件数据迁移、CI/CD 流水线调试。
    *   **痛点**：ReAct 模式在处理 50+ 个文件修改时，Context 被无关的 `ls` 输出和 `cat` 内容填满，导致模型迷失。
    *   **应用**：维护 `RepoState` (active_files, open_prs, test_failures, current_dir)。Agent 输出 `{"file_changes": {...}}` 补丁。运行时验证补丁语法，更新状态，丢弃 `思考过程`。

3.  **实时游戏/模拟仿真 NPC（Game Simulation）**
    *   **场景**：RPG 任务链、虚拟经济系统、物流仿真。
    *   **痛点**：NPC 随着对话轮数增加，记忆混乱（如把之前的 NPC 当成现在的敌人），且 Token 成本随时间爆炸。
    *   **应用**：状态即“游戏存档”（Inventory, Location, QuestProgress, NPC_Relations）。每帧/每步只读取当前存档，输出动作和状态变更。彻底解决“迷失中间”问题。

4.  **多 Agent 协作系统（Multi-Agent Collaboration）**
    *   **场景**：销售 Agent + 技术 Agent + 法务 Agent 共同完成合同谈判。
    *   **痛点**：多 Agent 共享长对话历史会导致“信息污染”，一个 Agent 的幻觉会被其他 Agent 当作事实引用。
    *   **应用**：建立**共享状态数据库**（Shared State DB）。每个 Agent 只读取 DB 当前快照，输出状态更新建议。由一个“验证器 Agent"或规则引擎合并状态，确保单一事实来源（Single Source of Truth）。

## 可立刻试的小实验（≥3，含输入/步骤/期望输出）

### 实验 1：构建“状态截断”对比测试
*   **目标**：验证在 20 步任务中，SKILL.state 是否比 ReAct 更抗噪且 Token 更少。
*   **输入**：
    *   任务：模拟一个“仓库找货”脚本（共 20 步，每步随机插入 3 个无关干扰项，如“系统日志：CPU 90%"）。
    *   基线 Prompt：`[System] 找货任务。[History] (前 19 步完整对话) [Current] 当前观察：干扰项...`
    *   实验 Prompt：`[System] 找货任务。[State] {current_item: null, shelf: A1} [Current] 干扰项...`
*   **步骤**：
    1.  编写一个简单的 Python 脚本模拟环境（返回干扰项）。
    2.  运行 ReAct 模式 20 步，记录 Token 消耗和最终准确率。
    3.  运行 SKILL.state 模式（定义 JSON Schema，强制输出 `state_patch`），记录 Token 消耗和准确率。
*   **期望输出**：
    *   ReAct：Token 消耗随步数线性剧增，准确率在 15 步后显著下降（受干扰项影响）。
    *   SKILL.state：Token 消耗恒定，准确率保持高位，干扰项被自动过滤。

### 实验 2：实现“状态补丁验证器”
*   **目标**：测试运行时验证机制如何防止模型破坏状态。
*   **输入**：
    *   Schema: `{"inventory": {"type": "object", "properties": {"item_id": {"type": "string"}}}}`
    *   模型错误输出：`{"state_patch": {"inventory": {"item_id": 123, "extra_field": "bad"}}}` (类型错误 + 多余字段)
*   **步骤**：
    1.  使用 `jsonschema` 库编写验证函数。
    2.  传入模型输出，捕获 `ValidationError`。
    3.  实现重试逻辑：捕获错误后，将错误信息（非历史对话）反馈给模型，要求修正 `state_patch`。
*   **期望输出**：
    *   第一次：验证失败，抛出异常。
    *   第二次：模型修正为 `{"inventory": {"item_id": "123"}}`，验证通过，状态更新成功。

### 实验 3：外部状态漂移恢复测试
*   **目标**：验证当环境状态被“外部”修改时，Agent 能否 0 步恢复。
*   **输入**：
    *   初始状态：`{location: "Room A"}`。
    *   环境干扰：在第 5 步，外部脚本强行将 Agent 移动到 `Room B`，但 Agent 认为还在 `Room A`。
*   **步骤**：
    1.  模拟环境：第 5 步返回观察 `Observation: You are in Room B`。
    2.  观察 ReAct：模型是否因为历史记录（Room A）而困惑，需要几步才能纠正？
    3.  观察 SKILL.state：模型直接读取 `Observation` 更新状态为 `Room B`，下一步直接基于 `Room B` 行动。
*   **期望输出**：
    *   ReAct：需要 2-3 步自我修正，期间可能产生幻觉。
    *   SKILL.state：第 5 步立即更新状态，第 6 步直接基于新位置行动，无延迟。

## 产品 / Agent 灵感

1.  **“无记忆”长任务助手**
    *   开发一款专门处理长文档分析、长代码重构的 Agent。用户只看到“当前进度条”和“当前文件树状态”，后台自动维护状态机。即使任务中断 24 小时，重启后直接加载 JSON 状态文件即可继续，无需重新读取 100 页历史。

2.  **企业级自动化流程引擎（Low-Code Agent）**
    *   将 SKILL.state 封装为低代码组件。业务人员定义“状态字段”（如：客户等级、订单金额、审批状态），AI 自动根据业务规则更新字段。系统天然具备“审计日志”（状态变更历史）和“防幻觉”特性。

3.  **实时游戏/虚拟人引擎插件**
    *   为 Unity/Unreal 开发插件，将 LLM 作为 NPC 的“决策核心”。NPC 不再维护对话历史，只维护 `Mood`, `Relationship`, `Inventory` 状态。大幅提升多 NPC 同屏时的响应速度和逻辑一致性。

4.  **个人知识库“快照”管理器**
    *   针对个人研究 Agent，不存储所有阅读笔记，而是维护一个 `KnowledgeGraph` 状态（实体、关系、置信度）。每次阅读新论文，只更新图谱状态。避免知识库变成“垃圾堆”，只保留高置信度的结构化知识。

## 跟现有系统怎么接

1.  **LangGraph / LangChain 改造**
    *   **现状**：LangGraph 默认倾向于维护 `messages` 列表。
    *   **改造**：
        *   定义一个 `State` 类（继承自 `TypedDict`），只包含业务状态字段，**不包含** `messages`。
        *   在 `Node` 中，将 `messages` 作为临时输入，生成 `state_patch`。
        *   使用 `StateGraph` 的 `update_state` 机制，**仅更新** `state_patch` 字段，并在节点结束时**清空** `messages` 变量（或将其移出 Graph State，仅存于本地日志）。
        *   引入 `validator` 节点，在状态更新前拦截非法 JSON。

2.  **现有 RAG 系统对接**
    *   **现状**：RAG 通常检索历史对话作为上下文。
    *   **改造**：
        *   将 RAG 检索结果转化为 `state_patch` 的一部分（如 `retrieved_facts` 字段）。
        *   不再将检索到的原文片段直接塞入 Prompt，而是让模型提取关键信息填入状态字段。
        *   历史对话仅作为“冷启动”或“异常回溯”的备份，不作为日常推理输入。

3.  **数据库/向量库集成**
    *   **架构**：`Agent Runtime` <-> `State DB (Redis/Postgres)`。
    *   **流程**：
        *   启动：从 DB 读取 `current_state` (JSON)。
        *   推理：LLM 输出 `patch`。
        *   验证：代码层校验 `patch`。
        *   持久化：`DB.update(state, patch)`。
        *   日志：将 `reasoning` (R_t) 写入单独的 `audit_log` 表（可选，用于事后审计，不进入推理循环）。

## 风险与坑

1.  **Schema 设计僵化（Schema Rigidity）**
    *   **风险**：如果任务需要动态增加字段（如突发情况），预定义 Schema 会报错，导致 Agent 卡死。
    *   **对策**：设计“扩展字段”（`extra_info` 或 `metadata`），允许模型自由填充非结构化数据，但核心逻辑字段必须严格校验。或者引入“动态 Schema 生成器”前置步骤。

2.  **状态丢失与不可逆（State Corruption）**
    *   **风险**：模型输出错误的 `state_patch`（如误删了关键数据），且验证器未拦截（如类型匹配但逻辑错误），导致状态永久损坏。
    *   **对策**：实现“状态快照”机制（Snapshot）。每 N 步保存一次完整状态副本。一旦检测到逻辑异常（如库存为负），自动回滚到上一个快照。

3.  **小模型结构化能力不足**
    *   **风险**：7B/8B 模型容易输出格式错误的 JSON，导致验证循环无限重试，增加延迟。
    *   **对策**：使用 **Grammar-constrained Decoding**（如 `outlines` 或 `guidance` 库），强制模型输出符合 Schema 的 JSON，从生成源头杜绝格式错误。

4.  **审计与解释性缺失**
    *   **风险**：丢弃推理过程（R_t）后，无法回答“为什么当时决定这么做？”（如合规审计需求）。
    *   **对策**：建立**双通道日志系统**。推理过程实时写入“临时日志”，仅在确认状态更新成功后，将关键决策点（Decision Point）提取并持久化到“审计日志”中，而非全量存储。

- [ ] **验证器开发**：编写 Python 脚本，实现基于 `jsonschema` 的状态补丁验证与重试逻辑。
- [ ] **基线复现**：在本地部署一个 20 步的简单任务，对比 ReAct 与 SKILL.state 的 Token 消耗和准确率。
