# 可以做什么

基于 SMetric 的核心洞察（**首轮负载均衡 + 后续轮缓存亲和 + 无状态推断**），以下是针对工程落地、系统优化及新场景探索的务实行动指南。

## 可迁移到的场景

1.  **多轮对话客服/销售机器人（高并发场景）**
    *   **痛点**：传统调度器容易让某些 GPU 被“长会话”（如复杂咨询）占满，导致新客进不来（TTFT 高）。
    *   **应用**：利用 SMetric 策略，将新会话均匀打散。一旦会话建立，后续多轮对话自动粘滞。
    *   **价值**：在不增加硬件的情况下，提升新客接入速度，同时保持老客对话流畅。

2.  **代码生成/调试 Agent（长上下文场景）**
    *   **痛点**：Agent 在调试代码时，往往需要连续多轮交互，上下文极长。若调度不均，单卡显存极易 OOM 或成为瓶颈。
    *   **应用**：通过“首轮负载均衡”防止单卡堆积过多长上下文会话；通过“后续轮亲和”利用本地 KV Cache 加速代码补全。
    *   **价值**：显著降低长代码生成的 P99 延迟，提升集群整体吞吐量。

3.  **RAG（检索增强生成）系统中的多轮问答**
    *   **痛点**：用户基于检索结果进行多轮追问，检索结果（Context）在 KV Cache 中复用率极高。
    *   **应用**：首轮请求（检索 + 初始生成）负载均衡，后续追问（仅复用 Context）缓存亲和。
    *   **价值**：减少重复的检索上下文计算，提升 RAG 系统的响应速度。

4.  **PD 分离架构（Prefill-Decode Disaggregation）的推理服务**
    *   **痛点**：在 Prefill 节点和 Decode 节点分离的架构中，Prefill 节点容易因负载不均而成为瓶颈。
    *   **应用**：在 Prefill 层应用 SMetric 策略。首轮请求均匀分配给 Prefill 节点，后续轮次若缓存命中则直接 Decode，若过载则动态迁移。
    *   **价值**：论文数据显示，此场景下 Prefill TPS 提升可达 34%，是架构升级的关键优化点。

## 可立刻试的小实验

### 实验 1：基于消息长度的“轮次”推断器
*   **目标**：验证无需维护会话表，仅凭请求体即可准确区分“首轮”与“后续轮”。
*   **输入**：构造一组模拟请求 JSON，包含不同长度的 `messages` 列表（0 条历史、1 条历史、10 条历史）。
*   **步骤**：
    1.  编写一个 Python 脚本，解析 `messages` 列表长度。
    2.  设定阈值（如 `len(messages) < 2` 视为首轮，否则后续）。
    3.  对比该推断结果与真实会话 ID 的匹配率（使用真实 Trace 数据或模拟数据）。
*   **期望输出**：推断准确率 > 95%。若存在误判（如用户刷新页面导致历史丢失），记录误判率，评估是否需引入 `session_id` 作为兜底。

### 实验 2：负载倾斜模拟与“过载回退”机制验证
*   **目标**：验证在单点过载时，SMetric 的 `not_overloaded` 机制能否成功将请求迁移。
*   **输入**：模拟一个 4 节点集群，人为将 Node 1 的负载设为 90%，其他节点 20%。构造一批“后续轮”请求，目标指向 Node 1。
*   **步骤**：
    1.  实现一个简单的调度器逻辑：若 `target_node.load > threshold` (如 80%)，则选择 `min_load_node`。
    2.  运行 1000 次请求模拟。
    3.  统计最终落在 Node 1 的请求比例 vs 其他节点。
*   **期望输出**：Node 1 的负载被限制在阈值附近，大量后续请求被成功“踢”到其他空闲节点，集群整体负载标准差下降。

### 实验 3：全局 KV Store 的“回退”延迟测试
*   **目标**：量化当缓存失效（Cache Miss）时，从全局 KV Store 拉取数据的延迟成本，评估是否值得。
*   **输入**：配置一个本地 KV Cache（模拟显存）和一个全局 KV Store（模拟 CPU 内存/网络存储）。
*   **步骤**：
    1.  模拟一个“后续轮”请求，目标实例无缓存。
    2.  测量从全局存储拉取 KV Cache 并注入显存的时间（Latency）。
    3.  对比“拉取后生成”的总耗时 vs “重新计算（无缓存）”的耗时。
*   **期望输出**：验证 `拉取延迟 + 生成时间` < `重新计算时间`。如果拉取延迟过高（如 > 500ms），则说明该场景下 SMetric 的“回退策略”可能失效，需调整阈值。

## 产品 / Agent 灵感

1.  **“弹性会话”Agent 网关**
    *   **概念**：开发一个位于 LLM 服务前的智能网关，内置 SMetric 逻辑。
    *   **功能**：自动识别新会话并“撒网”负载均衡；识别长会话并“粘滞”优化。
    *   **卖点**：向客户宣称“无需扩容即可提升 15% 并发能力”，特别适合 SaaS 型 Agent 平台。

2.  **动态会话迁移工具（Session Migrator）**
    *   **概念**：针对长尾负载，开发一个后台服务，监控 GPU 负载。
    *   **功能**：当检测到某节点上的长会话导致过载时，主动触发“缓存迁移”（将 KV Cache 从过载节点拷贝到空闲节点），并通知调度器将后续请求路由过去。
    *   **价值**：解决 SMetric 论文中未深入探讨的“极端长会话”导致的硬过载问题。

3.  **Agent 成本优化仪表盘**
    *   **概念**：为云厂商或企业用户提供可视化工具。
    *   **功能**：展示“因负载均衡不均导致的资源浪费” vs “因缓存复用节省的计算成本”。
    *   **价值**：用数据证明采用 SMetric 策略后，单位 Token 成本的下降幅度。

## 跟现有系统怎么接

1.  **基于 vLLM 的修改（最推荐）**
    *   **切入点**：修改 `vllm/worker/model_runner.py` 或 `scheduler.py`。
    *   **具体操作**：
        *   在 `schedule()` 函数中，增加 `turn` 判断逻辑（解析 `request.messages`）。
        *   实现 `select_node()` 的分支逻辑：`if turn == 0: return min_load_node()`; `else: return cache_aware_node()`。
        *   集成 `LMCache` 或 `vLLM` 自带的 KV Cache 管理接口，实现过载检测逻辑。

2.  **基于 Ray Serve 的自定义调度器**
    *   **切入点**：利用 Ray Serve 的 `Deployment` 和 `Router` 机制。
    *   **具体操作**：
        *   编写一个自定义的 `Router` 类，继承自 `Ray Serve` 的路由逻辑。
        *   在路由层实现 SMetric 算法，直接决定请求转发给哪个 Replica。
        *   利用 Ray 的 Actor 机制维护轻量级的“过载状态”（无需维护全量会话表）。

3.  **作为 Sidecar 代理（无侵入式）**
    *   **切入点**：在应用层和 LLM 服务层之间部署一个 Sidecar（如 Envoy 插件或 Python 微服务）。
    *   **具体操作**：
        *   Sidecar 解析 HTTP 请求体，计算 `turn`。
        *   Sidecar 维护一个简单的“实例负载计数器”（基于心跳或主动探测）。
        *   Sidecar 根据 SMetric 规则重写 `Host` 头或负载均衡策略，将请求转发给正确的后端实例。
    *   **优势**：无需修改 LLM 推理引擎代码，兼容性强。

## 风险与坑

1.  **全局 KV Store 成为新瓶颈**
    *   **风险**：SMetric 依赖全局存储来支持“回退”机制。如果网络带宽（RDMA）或存储 IO 不足，大量缓存失效请求会导致全局存储拥塞，反而拖慢整个集群。
    *   **对策**：必须对全局存储进行压力测试；设置合理的 `HIT_RATIO` 阈值，避免在存储拥塞时频繁回退。

2.  **“伪首轮”误判**
    *   **风险**：如果用户刷新页面、断开重连，或者 Agent 工具调用导致上下文丢失，请求可能携带空历史，被误判为“首轮”。此时调度器将其负载均衡到无缓存节点，导致性能骤降。
    *   **对策**：结合 `session_id`（如果 API 支持）作为辅助判断；或设置一个“缓冲期”，对疑似新会话的请求进行小范围试探。

3.  **长尾会话的“粘性”陷阱**
    *   **风险**：如果某个会话异常长（如陷入死循环），即使有 `not_overloaded` 机制，也可能因为阈值设置不当而无法及时迁移，导致单卡 OOM。
    *   **对策**：引入“会话超时”和“最大轮次”限制；监控单会话的 Token 消耗速率，异常时强制熔断或迁移。

4.  **多模态场景的不确定性**
    *   **风险**：论文主要针对文本 Agent。如果 Agent 输入包含图片/视频，KV Cache 的复用模式可能不同（图片编码可能不复用），导致调度策略失效。
    *   **对策**：在多模态场景下，需重新校准 `turn` 推断逻辑和缓存命中率阈值。

- [ ] **原型开发**：在 vLLM 或 Ray Serve 上实现一个最小化的 SMetric 调度器 Demo（仅包含 `turn` 判断和基础负载均衡）。
- [ ] **存储评估**：评估现有基础设施的全局 KV Store（如 Redis, S3, 或专用 KV Store）的读写延迟和带宽，计算是否满足“回退”机制的延迟要求。
- [ ] **阈值调优**：设计实验，寻找最佳的 `OVERLOAD` 阈值（如 1.5x, 2.0x）和 `HIT_RATIO` 阈值，以适应不同的业务负载。
- [ ] **监控埋点**：在调度器中埋点，记录“首轮负载均衡次数”、“后续轮缓存命中次数”、“过载回退次数”，以便上线后持续优化。
