# SMetric: Rethink LLM Scheduling for Serving Agents with Balanced Session-centric Scheduling

**Authors:** Jiahao Wang, Kaizhan Lin, Kaixi Zhang, et al. (Shanghai Jiao Tong University, Alibaba Group)
**Venue:** arXiv preprint (2026)
**Organization(s):** Institute of Parallel and Distributed Systems (IPADS), SJTU; Alibaba Group
**arXiv:** [2607.08565](https://arxiv.org/abs/2607.08565)
**Code:** [Not released yet (paper states open-source upon publication)](https://arxiv.org/abs/2607.08565)
**Project page:** None

## TL;DR and contributions
这篇论文针对大语言模型（LLM）在"Agent 服务”场景下的调度难题，提出了一种名为 **SMetric** 的新调度策略。核心发现是：Agent 的会话（Session）具有极强的局部性，后续请求几乎总是复用同一实例上的 KV Cache，导致现有“缓存优先”策略造成严重的负载不均。SMetric 通过“首轮负载均衡、后续轮缓存亲和”的差异化路由，在不牺牲缓存命中率的前提下，将集群吞吐量（TPS）提升了 10%–16%。

**Main contributions:**
- 首次系统分析了真实 Agent 工作负载的 KV Cache 复用模式与会话执行特征。
- 揭示了现有调度器在 Agent 场景下因过度追求缓存命中而牺牲负载均衡的痛点。
- 提出了基于会话轮次（Session Turn）的无状态差异化调度算法 SMetric。
- 在 PD 共置（Colocation）和 PD 分离（Disaggregation）两种架构下，均验证了显著的性能提升。

**Compared against:** Bailian (阿里生产环境调度器), LMetric (SOTA 学术调度器), Load-balance-only (纯负载均衡), Dynamo (分离架构下的 SOTA)。
**On datasets:** 两个来自阿里百炼（Bailian）编码 Agent 的真实生产轨迹（Trace 1: TB 级模型，Trace 2: 280B 参数模型）。
**Headline improvements:**
- PD 共置架构下，有效集群 TPS 提升 **10%–16%**。
- PD 分离架构下，Prefill TPS 提升 **2%–34%**。
- 中位首字延迟（TTFT）在分离架构下从 1.8 秒降至 **1.1 秒**（降低 37%）。
- 负载不均衡度（Max/Mean）从 3.0 倍降至 **2.6 倍**。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 核心洞察是"Agent 会话的粘性”：一旦首轮请求落在某实例，后续请求因 KV Cache 复用会自然“粘”在该实例。因此，**只需对首轮请求做负载均衡**，即可保证整个会话的负载平衡，同时保留后续请求的本地缓存优势。
- **🔧 Useful in practice:** 实现细节：如何无状态地推断“轮次”（通过历史消息数）；两个关键保护机制（过载检测 `not_overloaded` 和缓存失效检测 `session_not_evicted`）；全局 KV Store 在其中的角色。
- **📎 Nice to know:** 对全局 KV Store 容量敏感度的分析（Sensitivity Analysis）；与 CacheRoute 等工作的对比细节；不同模型规模（30B vs 235B）下的表现差异。
- **⚠️ Deprecated / superseded:** 传统的“纯缓存亲和”策略（如 Bailian 的默认配置）在 Agent 场景下已被证明会导致严重的负载倾斜，不再是最佳实践。
- **🔕 Skippable:** 详细的硬件配置列表（除非你要复现）；标准的 Related Work 综述部分；过于基础的 LLM 推理两阶段（Prefill/Decode）介绍。

## Context and prerequisites

要理解 SMetric，首先需要建立对 **LLM 推理中的 KV Cache 复用** 和 **多轮会话（Session）** 的直观认识。在 LLM 生成文本时，模型需要计算 Key 和 Value 矩阵（KV Cache）来记录上下文。如果两个请求的前缀相同，后续请求就可以直接复用之前计算好的 KV Cache，跳过昂贵的计算过程，这被称为“缓存命中”。在传统的聊天机器人场景中，这种复用率通常在 50%-60% 左右。然而，在 Agent 场景中，Agent 为了完成任务，会连续发起多轮请求，每一轮都携带完整的对话历史。这意味着后续请求的前缀几乎完全覆盖了上一轮的内容，导致 **KV Cache 复用率飙升至 80% 以上**。

其次，必须理解 **集群调度的两难困境**。现有的调度器通常会在“负载均衡”（把请求分给空闲的 GPU）和“缓存亲和”（把请求分给有缓存的 GPU）之间做权衡。在 Agent 场景下，如果调度器过度追求缓存亲和，它会把同一个会话的所有请求都路由到同一个 GPU 实例上。由于 Agent 会话往往很长且计算量大，这会导致少数 GPU 被“撑爆”，而其他 GPU 却闲置，最终限制了整个集群的吞吐量（TPS）。反之，如果为了负载均衡而强行把请求打散，虽然 GPU 利用率高了，但失去了缓存复用，计算量剧增，同样拖慢速度。SMetric 正是为了解决这个特定的“非此即彼”的矛盾而设计的。

## Method

### The big picture (layman version)
想象一个繁忙的图书馆（GPU 集群），读者（Agent 请求）需要查阅书籍（计算 KV Cache）。以前的管理员（调度器）发现，如果读者能直接找到上次放书的书架（本地缓存），速度就快。于是，管理员把所有来自同一个读者的后续请求都派往同一个书架。结果，几个热门书架被挤得水泄不通，而冷门书架空无一人，整体效率反而下降。

SMetric 的管理员换了一种策略：他不再关心读者后续会去哪里，而是**只关注读者第一次进门时（首轮请求）把书放在哪个书架**。对于第一次进门的读者，他严格执行“哪里空闲放哪里”的负载均衡策略，确保所有书架的初始压力均匀。一旦读者第一次被分配到了某个书架，后续的所有请求（因为书就在那里，不用搬）都会自然地回到这个书架。这样，既保证了每个书架的初始负载是平衡的，又让后续请求享受了“书就在手边”的高速缓存红利。如果某个书架后来因为读者突然变多而太挤了，管理员会介入，把部分读者的后续请求“迁移”到空闲书架，但这只是例外情况。

### The walkthrough

SMetric 的核心逻辑建立在两个关键洞察之上：
1.  **会话粘性（Session Stickiness）：** 在 Agent 工作负载中，后续请求（Follow-up requests）极大概率复用同一会话中前序请求的 KV Cache。由于这些 Cache 通常驻留在处理前序请求的 GPU 本地显存中，现有的“缓存优先”调度器会将后续请求自动路由回同一实例。
2.  **首轮决定论：** 既然后续请求会“粘”在首轮请求所在的实例上，那么**只要首轮请求的分布是均匀的，整个会话的负载分布就是均匀的**。

基于此，SMetric 将调度过程分为两个阶段，并引入一个无状态的判断指标：**轮次（Turn）**。

#### 1. 无状态轮次推断
调度器不需要维护庞大的“会话 ID 到实例 ID"的映射表（这在高并发下是巨大的开销）。SMetric 利用 LLM API 的无状态特性：每个请求都携带了完整的对话历史。调度器只需统计请求中历史消息的数量，即可推断出这是第几轮（Turn）。
- 如果历史消息数为 0（或特定阈值），判定为 **首轮请求（Turn 0）**。
- 否则，判定为 **后续请求（Turn > 0）**。

#### 2. 差异化路由策略
SMetric 的伪代码逻辑（参考论文 Figure 13）如下：

**步骤 A：判断请求类型**
- 若 `req.turn == 0`（首轮）：
  - **策略：** 纯负载均衡（Load Balance Only）。
  - **动作：** 选择当前负载（如 In-flight tokens 数）最小的实例。
  - **目的：** 将新会话均匀地“撒”到整个集群，避免热点。

- 若 `req.turn > 0`（后续轮）：
  - **策略：** 缓存亲和（Cache-Aware），但带有保护机制。
  - **动作：** 优先选择本地 KV Cache 命中率最高的实例（通常是处理过上一轮的实例）。
  - **保护机制 1（过载检测 `not_overloaded`）：** 检查目标实例的负载是否超过集群平均负载的某个阈值（如 2 倍）。如果过载，说明该实例可能积累了太多长会话，此时**放弃缓存亲和**，回退到负载均衡策略，将请求迁移到空闲实例。
  - **保护机制 2（缓存失效检测 `session_not_evicted`）：** 检查目标实例的本地 Cache 是否还保留着该会话的历史。由于显存有限，长时间未活动的会话 Cache 可能被淘汰。如果实际命中率远低于预期（`c < HIT_RATIO * est_hit`），说明 Cache 已失效，此时**放弃缓存亲和**，回退到负载均衡策略（此时请求可视为新会话，利用全局 KV Store 获取数据）。

#### 3. 全局 KV Store 的协同
SMetric 的设计依赖于现代 LLM 服务的 **两级 KV Store 架构**：
- **本地层（Local Tier）：** GPU 显存，速度快，容量小。
- **全局层（Global Tier）：** CPU 内存或远程存储，容量大，速度稍慢（通过 RDMA 连接）。
当 SMetric 因保护机制将请求路由到非缓存实例时，该实例可以通过全局层快速获取 KV Cache，虽然会增加一点延迟（TTFT），但保证了负载均衡，且 Agent 对这种延迟的容忍度较高。

## Challenges in the field — and what this work addresses

**挑战 1：缓存局部性与负载均衡的零和博弈**
- **难点：** 在 Agent 场景下，KV Cache 复用率极高（>80%）。如果调度器为了负载均衡而忽略缓存，会导致大量重复计算，TPS 暴跌；如果为了缓存而忽略负载均衡，会导致严重的“长尾”实例过载，其他实例闲置，同样限制 TPS。这是一个典型的“非此即彼”困境。
- **SMetric 的解法：** 利用 Agent 工作负载的**时间局部性**（后续请求紧跟前序请求）和**空间局部性**（同一会话的 KV Cache 集中在同一实例）。通过打破“所有请求都需缓存亲和”的假设，仅对首轮请求做负载均衡，SMetric 成功解耦了这两个目标：首轮负责平衡，后续负责复用。

**挑战 2：调度器的状态膨胀与扩展性**
- **难点：** 要实现“会话感知”的调度，传统思路是维护一个全局的 `Session_ID -> Instance_ID` 表。但在大规模集群中，活跃会话数可能高达数万甚至数十万，维护、同步和清理这个表会消耗大量 CPU 资源，成为调度器本身的瓶颈。
- **SMetric 的解法：** 采用**无状态设计**。不维护会话表，而是通过请求本身携带的历史消息数（Turn）来推断会话阶段。这使得调度器可以像无状态函数一样处理请求，极大地提升了扩展性和响应速度。

**挑战 3：长尾负载与动态变化**
- **难点：** 即使首轮负载均衡，如果某些会话突然变得极长（例如 Agent 陷入死循环或处理复杂任务），仍会导致实例过载。
- **SMetric 的解法：** 引入**动态保护机制**（`not_overloaded` 和 `session_not_evicted`）。当检测到异常负载或缓存失效时，动态打破“粘性”，将请求迁移，防止单点故障。

**本工作未解决的问题：**
- 论文未深入探讨当全局 KV Store 带宽或容量严重不足时的极端情况（虽然做了敏感性分析，但未提出新的存储架构优化）。
- 未涉及跨集群（Inter-cluster）的调度问题。

## Experiments and results

论文在真实的硬件集群（4 台服务器，每台 8 张 H20 GPU）上进行了详尽的评估，对比了 Bailian（生产基线）、LMetric（学术 SOTA）和纯负载均衡策略。

**1. PD 共置架构（Prefill-Decode Colocation）**
- **吞吐量（TPS）：** 在配备全局 KV Store 的情况下，SMetric 的集群有效 TPS 比最强基线（Bailian）高出 **10%–16%**。
- **负载均衡度：** 实例间的最大负载与平均负载之比（Max/Mean）从 Bailian 的 **3.0** 降至 **2.6**，显著减少了资源浪费。
- **延迟：** 中位首字延迟（TTFT）从 1.8 秒降至 **1.1 秒**（降低 37%）；P50 和 P90 的 TPOT 也分别降低了 10% 和 20%。
- **无全局存储时：** 若没有全局 KV Store，SMetric 与 Bailian 的性能差距缩小至 **1%**，证明了其核心优势依赖于两级存储架构的协同。

**2. PD 分离架构（Prefill-Decode Disaggregation）**
- **Prefill TPS：** 提升幅度更大，范围在 **2%–34%** 之间。这是因为 Prefill 阶段对计算负载的均衡更为敏感。
- **延迟：** 中位 TTFT 从 1.8 秒降至 **1.1 秒**。
- **大模型测试：** 在 Qwen3-235B 模型上，SMetric 依然保持优势，TPS 提升 8%（对比 Bailian），且在高负载下表现更稳健。

**3. 消融实验与敏感性分析**
- **保护机制有效性：** 移除 `not_overloaded` 保护机制会导致长尾延迟显著增加（P99 TTFT 从 45.3s 升至 51.2s）。
- **参数鲁棒性：** 对 `OVERLOAD` 阈值和 `HIT_RATIO` 的敏感性分析显示，SMetric 在较宽的参数范围内性能稳定，无需精细调优。

## Open questions and limitations
1.  **全局存储的瓶颈：** SMetric 的性能提升高度依赖于全局 KV Store 的带宽和容量。如果全局存储成为瓶颈（例如在极端高并发或网络拥塞时），SMetric 的回退机制（Fallback to Load Balance）可能会导致性能下降，甚至不如纯缓存亲和策略。
2.  **会话结束检测：** 论文提到 Agent 会话没有明确的结束信号，调度器依靠超时或历史消息推断。如果 Agent 长时间挂起后突然发起请求，SMetric 可能错误地将其视为新会话（导致负载均衡而非缓存亲和），或者错误地视为旧会话（导致缓存失效）。
3.  **多模态与复杂工具调用：** 实验主要基于编码 Agent（文本输入输出）。对于涉及图像、音频等多模态输入，或者工具调用结果极其复杂的场景，KV Cache 的复用模式和会话长度分布可能不同，SMetric 的适用性需进一步验证。

## 与 B 站讲解的对照
- **视频强调点：** 视频重点突出了“首轮负载均衡，后续轮缓存亲和”这一核心策略，以及 **16%** 的 TPS 提升这一亮眼数字。视频还直观地解释了“为什么缓存优先会导致负载不均”（少数实例被长会话占满）。
- **可能简化/遗漏：**
  - 视频可能简化了 **全局 KV Store** 的关键作用。论文明确指出，如果没有全局存储，SMetric 的优势几乎消失（仅 1% 提升）。视频未深入解释为什么需要全局存储来支撑“首轮负载均衡”（因为首轮请求可能落在没有缓存的实例上，必须靠全局存储拉取数据）。
  - 视频未详细展开 **两个保护机制**（过载检测和缓存失效检测）的细节，而这在实际部署中是防止系统崩溃的关键。
  - 视频未提及 **无状态设计** 的工程价值（避免维护巨大的会话表），这是 SMetric 能落地的关键工程创新。
