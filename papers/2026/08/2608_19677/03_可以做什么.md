# 可以做什么

基于 CacheRoute 的核心逻辑（**周期性离线规划 + 负载感知放置 + 影子验证**），以下是可直接落地的工程动作与产品方向。核心原则：**不要试图实时计算路由，利用业务流量的统计稳定性，用“时间换空间”解决缓存与负载的矛盾。**

## 可迁移到的场景（≥4）

1.  **企业级 RAG 知识库服务**
    *   **痛点**：不同部门（HR、法务、IT）的文档前缀（System Prompt + 知识库索引）高度固定，但流量分布不均。随机路由导致热门部门文档无法复用 KV Cache，首字延迟（TTFT）高。
    *   **应用**：将“部门/文档 ID"作为 Key，周期性计算路由表。将高频部门文档的 KV Cache 强制驻留在负载较轻的节点，实现部门级缓存共享，同时避免单点过载。

2.  **多租户 SaaS 客服机器人**
    *   **痛点**：大型 SaaS 客户（如银行、电商）的客服场景前缀（Prompt + 历史对话）复用率极高，但小客户流量分散。传统负载均衡打散了大客户的缓存上下文。
    *   **应用**：识别“大客户 Key"，将其路由策略从“随机”改为“亲和性 + 负载均衡”。在控制周期内，将大客户的请求稳定分发到 2-3 台特定机器，确保上下文连续性，提升并发处理能力。

3.  **代码生成/IDE 插件服务**
    *   **痛点**：开发者在编写同一项目代码时，文件头（Imports, Class Definitions）作为前缀高度重复。但不同项目流量波动大，容易导致热点机器排队。
    *   **应用**：以“项目 ID + 文件路径”为 Key。利用 LPT 算法将热门项目的代码前缀缓存分散到集群中当前空闲的节点，既保证代码补全的上下文命中率，又防止某个热门项目拖垮单台机器。

4.  **游戏 NPC 对话/剧情生成服务**
    *   **痛点**：游戏内特定剧情节点或 NPC 的固定开场白（前缀）被海量玩家重复触发，但玩家分布随机。
    *   **应用**：将“剧情节点 ID"作为 Key。周期性规划将热门剧情节点的缓存预加载到特定节点组。当玩家请求该剧情时，直接命中缓存，大幅降低生成延迟，提升玩家体验。

## 可立刻试的小实验（≥3，含输入/步骤/期望输出）

### 实验 1：影子回放验证（Shadow Replay）
*   **输入**：过去 24 小时的真实请求日志（包含 `Request_ID`, `Key`, `Timestamp`, `Latency`），当前生产环境的负载均衡配置。
*   **步骤**：
    1.  离线解析日志，统计每个 `Key` 的到达速率 $\lambda_b$。
    2.  模拟 CacheRoute 规划器：基于当前集群机器数 $R$ 和预估负载上限 $q_{cap}$，生成一张“假设的路由表”。
    3.  在离线环境中“重放”日志：根据新路由表，将请求映射到模拟的机器上，计算理论上的负载分布（Imbalance）和潜在的缓存命中率（假设缓存无限大）。
    4.  对比：新路由表 vs 当前随机/一致性哈希策略的负载标准差。
*   **期望输出**：一份报告，显示如果上线新策略，负载不均衡度预计降低多少（例如从 3.5 降至 1.3），以及理论吞吐量提升比例。

### 实验 2：LPT 放置策略的贪心效果验证
*   **输入**：一组模拟的 Key 列表（Key A: 100 QPS, Key B: 80 QPS, Key C: 20 QPS...），3 台目标机器。
*   **步骤**：
    1.  初始化 3 台机器负载为 0。
    2.  按速率降序遍历 Key。
    3.  对每个 Key，将其任务分配给当前负载最小的 $k$ 台机器（$k=1$ 或根据流量计算）。
    4.  记录每步分配后的最大负载（Makespan）。
    5.  对比：随机分配策略下的最大负载。
*   **期望输出**：数据图表显示，LPT 策略下的最大机器负载比随机策略低 20%-40%，证明其能有效防止热点。

### 实验 3：重规划周期敏感性测试
*   **输入**：模拟流量数据，包含一个“突发热点”事件（例如某 Key 流量在 5 分钟内激增 10 倍，随后回落）。
*   **步骤**：
    1.  设置不同的规划周期 $T$（例如：1 分钟、10 分钟、1 小时）。
    2.  模拟在突发发生时，新路由表生效的时间点。
    3.  计算：从流量突变到新表生效期间的“性能损失窗口期”（缓存未命中 + 负载不均导致的延迟）。
    4.  计算：频繁重规划带来的“预热开销”（假设每次重规划需要 30 秒预热）。
*   **期望输出**：一个“最佳周期曲线”，找出在特定业务波动率下，收益最大化的重规划频率（例如：每 15 分钟一次）。

## 产品 / Agent 灵感

1.  **“智能路由编排器”插件**
    *   **定位**：作为 LLM 推理平台（如 vLLM, TGI）的独立控制平面插件。
    *   **功能**：自动监控集群 Key 分布，每 10 分钟生成并下发一次路由表。提供“影子模式”开关，允许运维人员先观察新策略效果，确认无误后一键切换。
    *   **卖点**：无需修改推理引擎代码，即插即用，宣称能提升 2 倍吞吐量。

2.  **SaaS 租户 SLA 保障 Agent**
    *   **定位**：面向多租户 SaaS 的运维 Agent。
    *   **功能**：识别 VIP 租户（高频 Key），自动将其前缀缓存“锁定”在专属资源池，并动态调整其他租户的流量以填补空闲资源。
    *   **卖点**：将“缓存命中率”转化为可售卖的"VIP 低延迟服务”，直接提升客户付费意愿。

3.  **边缘推理缓存同步器**
    *   **定位**：针对边缘计算场景（多节点、弱网）。
    *   **功能**：在边缘节点间同步“热门前缀”的路由规划。当中心节点检测到某区域热点时，提前规划并将路由表下发至该区域边缘节点，避免跨区请求导致的延迟。

## 跟现有系统怎么接

1.  **架构位置**：
    *   部署在 **Inference Gateway**（推理网关）与 **Model Cluster**（模型集群）之间。
    *   作为 **Sidecar** 或 **独立微服务** 运行，不侵入推理引擎内部。

2.  **接口对接**：
    *   **输入**：从网关获取 `Request Header` 中的 `X-Business-Key`（或从 Prompt 提取特征）。
    *   **输出**：返回 `Target-Node-ID` 或 `Node-List`（用于内部负载均衡）。
    *   **控制面**：提供一个 gRPC/HTTP 接口供“规划器”定期推送新的路由表（JSON 格式：`{ "key": "xxx", "nodes": [1, 3, 5] }`）。

3.  **数据流**：
    *   **监控层**：Prometheus 采集各机器的 `Queue-Depth` 和 `KV-Cache-Usage`。
    *   **规划层**：定时拉取监控数据 -> 运行 LPT 算法 -> 生成新路由表。
    *   **执行层**：网关读取最新路由表（内存缓存），请求到达时查表转发。

## 风险与坑

1.  **冷启动/预热失效**：
    *   **风险**：新路由表生效瞬间，目标机器的缓存是空的（Cold），前几个请求必须重新计算，导致延迟尖峰。
    *   **对策**：在切换路由表前，先向目标机器发送“预热请求”（Warm-up Request），强制加载前缀；或采用“灰度切换”，先切 5% 流量。

2.  **业务分布剧烈漂移**：
    *   **风险**：如论文所述，如果业务 Key 分布变化极快（如突发新闻），周期性规划会滞后，导致缓存失效。
    *   **对策**：设置“熔断机制”。如果检测到某 Key 的命中率连续下降或负载倾斜超过阈值，自动回退到“随机负载均衡”模式。

3.  **异构前缀大小**：
    *   **风险**：论文假设前缀大小一致。实际中，长文档前缀占用显存多，短 Prompt 占用少。简单的“数量准入”会导致显存碎片化。
    *   **对策**：升级规划算法，引入“字节感知（Byte-aware）”的背包问题解法，按显存占用量而非 Key 数量进行准入控制。

4.  **元数据开销**：
    *   **风险**：如果 Key 数量极大（百万级），路由表过大，查表延迟增加。
    *   **对策**：对 Key 进行分层（Top-K 热 Key 走查表，其余走随机）；或使用布隆过滤器（Bloom Filter）加速查表。

## 跟进清单

- [ ] **数据收集**：从现有生产环境导出最近 1 周的请求日志，提取 `Key` 和 `Latency` 分布。
- [ ] **基线构建**：在测试集群部署一套“随机负载均衡”和一套“一致性哈希”作为对照组。
- [ ] **原型开发**：编写一个简单的 Python 脚本，实现 LPT 调度算法，输入日志统计，输出路由表。
- [ ] **影子测试**：在测试环境开启影子模式，对比新策略与基线的 p99 延迟和吞吐量。
- [ ] **阈值定义**：根据业务 SLO，定义“重规划触发条件”（如：负载不均衡度 > 1.5 或 命中率下降 > 5%）。
- [ ] **异常演练**：模拟单台机器故障或流量突增，观察路由表切换后的恢复时间。
