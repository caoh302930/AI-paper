# CacheRoute: Planned Prefix-Affinity Routing for Large-Scale LLM Serving

**Authors:** Huang Cheng (Meta)  
**Venue:** arXiv preprint (2026)  
**Organization(s):** Meta, Menlo Park  
**arXiv:** [2608.19677](https://arxiv.org/abs/2608.19677)  
**Code:** not released (per paper text)  
**Project page:** none

## TL;DR and contributions
CacheRoute 解决了一个看似矛盾的问题：在大模型推理服务中，为了利用“前缀缓存（Prefix KV Cache）”加速，我们需要把相同业务前缀的请求路由到同一台机器；但为了负载均衡，我们又希望请求分散到所有机器。传统的“随机负载均衡”会打散缓存，而“固定亲和性路由”又会导致热点机器队列拥堵。CacheRoute 提出了一种**周期性规划式路由**：它不实时计算，而是根据历史请求速率，预先计算一张路由表，把高频业务（Warm Set）稳定地分配给负载较轻的机器，同时利用 LPT（最长处理时间优先）算法平衡负载。

**Main contributions:**
- 提出了一种将“缓存局部性”与“负载平衡”统一在周期性路由表中的新范式。
- 在 Llama-3.3-70B (fp8) 的 60 张 H100 集群上，实现了 93.2% 的 KV 缓存命中率，吞吐量达到 176 QPS，是当时最强基线（Preble）的 2.3 倍。
- 通过消融实验和负样本（32B 模型下的失败案例）明确界定了该方法的适用边界：只有当可复用的前缀收益足以抵消负载倾斜时，才应启用。

**Compared against:** Flat-LB (Power-of-Two Choices), Sticky (Consistent Hashing), CHWBL, DualMap, Preble.
**On datasets:** 两个半合成聚合工作负载（基于去标识化的运营遥测数据，模拟多租户客服场景），以及受控的 8B/32B 合成负载。
**Headline improvements:** KV 命中率从 64.1% 提升至 93.2%；在 p99 延迟 $\le$ 3.5s 的 SLO 下，吞吐量提升 2.3 倍（176 vs 76 QPS）。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 周期性离线规划路由表（Periodic Offline Plan）。核心在于将“高频 Key 准入（Warm-set admission）”和“基于负载的放置（LPT Placement）”解耦。不要试图实时计算，而是利用业务速率的稳定性，每隔一段时间（Control Interval）生成一张表，期间请求只查表不重算。
- **🔧 Useful in practice:** “影子回放（Shadow Replay）”部署策略。论文强调不能仅凭统计估算就上线，必须先在影子模式下对比新路由表和旧负载均衡的 p99 延迟和容量，只有确认收益才切换。
- **📎 Nice to know:** 8B 模型上的消融实验，详细拆解了“亲和性（Affinity）”、“复制（Replication）”和“放置（Placement）”各自对命中率和负载不均衡度的贡献。
- **⚠️ Deprecated / superseded:** 文中未提及被后续工作完全取代，但明确指出在“前缀复用收益极低”或“业务分布变化极快”的场景下，该方法不如 Flat-LB。
- **🔕 Skippable:** 附录中关于具体种子（seeds）的统计细节、fp16 精度下的压力测试（因为未通过 SLO，仅作为辅助证据）、以及过于详细的数学推导（如 LPT 的近似界讨论，文中已承认不适用）。

## Context and prerequisites

要理解 CacheRoute，首先必须建立对 **LLM 推理中的前缀缓存（Prefix Caching）** 的直观认识。在大模型生成文本时，如果多个请求共享相同的前缀（例如客服机器人中相同的系统提示词或业务背景），推理引擎可以复用之前计算好的 KV Cache，跳过昂贵的预填充（Prefill）阶段。然而，这种复用有一个物理前提：第二次请求必须到达**第一次请求所在的那台服务器**，且该服务器上的缓存尚未被驱逐。如果请求被随机分发到另一台机器，缓存就“白算”了，必须重新计算。

其次，需要理解 **负载均衡与亲和性（Affinity）的固有矛盾**。传统的负载均衡器（如随机或一致性哈希）倾向于将流量均匀分散，这会导致高频前缀的请求被分散到不同机器，使得每台机器上的缓存都存不住完整的前缀，命中率极低。反之，如果使用“粘性路由”（Sticky Routing），将同一 Key 永远绑定到同一台机器，虽然缓存命中率高了，但如果该 Key 流量巨大，这台机器就会成为热点，队列积压，导致尾延迟（Tail Latency）飙升，拖累整个集群的 SLO。

最后，理解 **周期性规划（Periodic Planning）** 的必要性。实时路由（Online Routing）需要感知每台机器当前的缓存状态和负载，但这会带来巨大的控制平面开销，且缓存状态变化太快（Eviction），实时决策往往滞后。CacheRoute 假设业务请求速率（Rate）在一段时间内是相对稳定的，因此可以离线计算一个“最佳路由表”，在控制周期内保持稳定，牺牲了极短期的灵活性，换取了缓存的长期稳定性和计算开销的降低。

## Method

### The big picture (layman version)
想象一个大型图书馆（集群），有很多书架（服务器），读者（请求）来借书（生成文本）。如果很多读者都借同一套书的前几章（前缀），图书馆希望这些读者能去同一个书架，这样书架上留着那几章，后面的人就不用重新复印（复用缓存）。但是，如果所有借这套书的人都挤去同一个书架，那个书架就会排长队，而别的书架却空着。

CacheRoute 的做法是：图书馆管理员（路由规划器）不实时盯着每个读者，而是每隔一段时间（比如每小时）统计一次：哪些书（业务 Key）最火？然后，管理员画一张地图（路由表）：
1. 对于最火的几本书，指定它们必须去特定的几个书架（Warm Set）。
2. 在分配这些热门书时，故意把它们分散到当前最空闲的几个书架上，避免某个书架太累（LPT 算法）。
3. 对于不火的书，还是随机分配。
4. 在这张地图生效的一个小时内，所有读者只看地图，不去问书架忙不忙。

这样做的好处是：热门书的缓存能一直留在书架上（高命中率），同时因为管理员特意把它们分到了空闲书架，不会造成排队（负载均衡）。

### The walkthrough
CacheRoute 的核心流程分为**规划（Planning）**和**执行（Dispatch）**两个阶段，且规划是周期性的。

**1. 规划阶段（离线/周期性）：**
输入是各业务 Key 的估计请求速率 $\lambda_b$ 和集群总机器数 $R$。
*   **步骤一：确定每个 Key 需要的机器数（Load-based assignment count）。**
    系统首先设定一个单台机器的负载上限 $q_{\rm cap}$（通过实验测得，即机器开始变慢的拐点）。对于每个 Key $b$，计算它需要分配给多少台机器 $k_b$：
    $$ k_b = \max\left(1, \left\lceil \frac{\lambda_b}{q_{\rm cap}} \right\rceil \right) $$
    这意味着，如果某个 Key 的流量太大，单台机器扛不住，就把它复制（Replicate）到多台机器上；如果流量小，就只给一台（$k_b=1$）。在论文的主实验（70B 模型）中，所有 Key 的流量都小于 $q_{\rm cap}$，所以实际上 $k_b$ 恒为 1，即**单副本亲和性**。

*   **步骤二：准入控制（Warm-set admission）。**
    集群的缓存总容量是有限的。系统假设每个机器能存 $W$ 个前缀槽位，总槽位 $C = R \times W$。系统按速率 $\lambda_b$ 从高到低排序 Key，依次将其纳入“热集（Warm Set）”，直到总槽位 $C$ 被占满。未被纳入的 Key 将作为“冷尾（Cold Tail）”流量，走传统的负载均衡。

*   **步骤三：放置与调度（Placement and dispatch）。**
    这是最关键的一步。对于被准入的 Key，我们需要决定具体放在哪 $k_b$ 台机器上。
    这里使用了经典的 **LPT（Longest Processing Time first）** 调度算法的变体。
    *   初始化：所有机器的当前负载 $L[r]$ 设为预期的“冷尾流量”负载。
    *   迭代：按速率从高到低遍历每个 Key $b$。对于 Key $b$ 的 $k_b$ 个任务（每个任务负载为 $\lambda_b / k_b$），将其分配给当前负载 $L[r]$ 最小的 $k_b$ 台机器。
    *   更新：每分配一个任务，更新对应机器的负载 $L[r]$。
    这种贪心策略（LPT）能有效避免将大任务集中到同一台机器，从而最小化最大负载（Makespan），实现负载均衡。

**2. 执行阶段（在线）：**
*   路由表 $T(b)$ 在控制周期内固定不变。
*   当请求到达时，检查其 Key $b$ 是否在路由表中。
    *   如果在：从 $T(b)$ 指定的机器集合中，选择**当前负载最小**的那一台（Least-loaded member）。注意，这里只在小范围内选，不会跨机器乱跑。
    *   如果不在（冷尾）：使用 **Power-of-Two Choices**（随机选两台，去负载小的那台）进行负载均衡。

**为什么选择 LPT？**
LPT 是解决多机调度问题的经典启发式算法。虽然论文指出标准的 LPT 近似界不适用于这种“任务可拆分且目标机器不同”的场景，但实验证明它能有效将负载不均衡度（Imbalance）从 3.46 倍降低到 1.24 倍。

**为什么周期性？**
实时计算 LPT 开销太大，且缓存状态（Residency）难以精确预测。周期性规划牺牲了毫秒级的动态调整，换取了缓存的稳定性（Stability），避免了因频繁切换机器导致的缓存失效（Thrashing）。

## Challenges in the field — and what this work addresses

**挑战一：缓存局部性与负载均衡的零和博弈**
*   **难点：** 传统的负载均衡（如随机）破坏了缓存局部性，导致大量重复计算；而固定亲和性（Sticky）虽然保留了局部性，却将流量倾斜直接转化为队列倾斜，导致尾延迟爆炸。
*   **CacheRoute 的解法：** 它不是二选一，而是通过**离线规划**将两者解耦。它利用业务速率的统计规律，预先将高频 Key 分配给负载较轻的机器，既保证了这些 Key 的缓存能“住”在机器上（亲和性），又通过 LPT 算法防止了单点过载（负载均衡）。

**挑战二：缓存命中率的不可预测性**
*   **难点：** 许多系统试图用数学模型预测 KV Cache 的驻留时间（Residency），但实际中由于驱逐策略（Eviction Policy）、请求到达的突发性（Burstiness）以及前缀长度的差异，理论模型往往严重偏离实际（论文中模型预测误差高达 44.7%）。
*   **CacheRoute 的解法：** 放弃精确的解析预测，转而采用**影子回放（Shadow Replay）**。在正式部署前，先在影子模式下运行新路由表，直接测量真实的 KV 命中率和延迟。这是一种“用实测代替估算”的工程务实策略。

**挑战三：动态环境下的规划失效**
*   **难点：** 如果业务流量分布发生剧烈漂移，预先计算的路由表可能瞬间过时，导致缓存失效或负载不均。
*   **CacheRoute 的解法：** 论文承认了这一点，并给出了**重规划（Replanning）**的权衡建议：只有当“旧表带来的性能损失”超过“新表预热带来的性能损失”时，才更新路由表。这避免了因过度敏感而频繁重算。

**本工作未解决的问题：**
*   **异构前缀大小：** 当前规划假设所有 Key 的前缀大小相似（等槽位模型）。如果某些业务的前缀特别长（占用大量显存），当前的“按数量准入”策略可能不是最优的，需要引入“字节感知（Byte-aware）”的背包问题解法，但这在论文中尚未实现。

## Experiments and results

**主实验（70B 模型，60 张 H100）：**
*   **吞吐量：** 在 p99 延迟 $\le$ 3.5s 的 SLO 下，CacheRoute 达到 **176 $\pm$ 11 QPS**，是次优基线 Preble (76 QPS) 的 **2.3 倍**，是 Flat-LB (42 QPS) 的 4.2 倍。
*   **缓存命中率：** 服务端的 Token-weighted KV 命中率从 Flat-LB 的 **64.1%** 提升至 **93.2%**。
*   **尾延迟：** 在 100 QPS 负载下，p99 TTFT（首字延迟）仅为 **1.8s**，而基线方法在 3.8s - 8.5s 之间。

**消融实验（8B 模型，30 张 H100）：**
*   **亲和性（Affinity）：** 仅开启亲和性，命中率从 56% 升至 88%，但负载不均衡度飙升至 3.46 倍，容量无提升（仍为 240 QPS）。
*   **复制（Replication）：** 仅开启复制，不均衡度降至 2.60 倍，容量仍无提升。
*   **LPT 放置：** 加入 LPT 后，不均衡度降至 **1.24 倍**，容量突破至 **500 QPS**（达到测试上限）。这证明了**平衡放置**是将缓存收益转化为实际吞吐的关键。

**负样本（32B 模型）：**
*   在两个 32B 的半合成工作负载中，由于可复用的前缀收益极低（Flat-LB 命中率仅 0.8%-1.1%），开启亲和性后，虽然命中率提升至 8.5%-11.8%，但负载倾斜导致容量反而下降至 Flat-LB 的 **0.50-0.67 倍**。这验证了“并非所有场景都适用 CacheRoute"。

## Open questions and limitations
1.  **前缀大小异构性：** 论文假设所有 Key 的前缀大小相近。如果业务中存在大量超长上下文（如法律文档分析），当前的“等槽位”准入策略可能导致缓存碎片化或过早驱逐，需要更复杂的字节级优化。
2.  **冷启动与重规划延迟：** 新路由表生效时，目标机器的缓存是冷的，需要重新预热。在流量剧烈波动时，如何平衡“频繁重规划带来的预热开销”与“旧表失效带来的性能损失”仍是一个工程难题。
3.  **对突发流量的敏感性：** 虽然实验显示 Gamma 分布的突发流量影响不大，但在极端突发（如秒级流量激增 10 倍）下，周期性规划可能无法及时响应，导致短暂的 SLO 违规。

## 与 B 站讲解的对照
*   **视频强调点：** 视频标题和简介高度聚焦于“规划式路由让多机命中率升至 93.2%"和“请求发错机器，Prefix Cache 白算”这一痛点，这与论文的核心贡献完全一致。视频清晰地解释了“旧方法短板”（负载均衡打散缓存 vs 固定亲和性导致热点）。
*   **可能的简化/遗漏：**
    *   **LPT 算法的细节：** 视频可能未深入解释 LPT（最长处理时间优先）在其中的具体作用，即它是如何把“亲和性”和“负载均衡”结合起来的。论文中明确指出，仅有亲和性是不够的，必须配合 LPT 才能提升容量。
    *   **负样本的重要性：** 视频主要展示成功案例（70B），可能未充分强调 32B 模型下的失败案例。论文中这部分非常关键，它界定了方法的适用边界，提醒工程师不能盲目上线。
    *   **影子回放（Shadow Replay）：** 视频可能未详细展开部署前的“影子回放”验证步骤，而这是论文中反复强调的“部署检查清单”的核心，是工程落地的关键安全网。
    *   **复制（Replication）的角色：** 视频提到“复制只在受控 8B 热点实验中实际发挥作用”，这一点在论文主实验（70B）中确实未体现（所有 $k_b=1$），视频对此的表述是准确的，但需理解这是实验设计的特异性，而非算法的局限性。
