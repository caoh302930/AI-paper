# 可以做什么

基于 EPC-AW 论文的核心洞察——**“多智能体失败常源于规划者的认知误校准（高估可行性），而非执行错误”**，以下是可立即落地的工程化方案。核心逻辑是：**利用多视角信息不对称来检测隐性规划错误，并通过记忆约束防止复发。**

## 可迁移到的场景（≥4）

1.  **复杂数据检索与 RAG 增强问答**
    *   **痛点**：Agent 自信地规划了“搜索 A 网站 -> 提取 B 数据 -> 计算 C"的路径，但 A 网站实际上没有 B 数据。Agent 完美执行了搜索（返回空或无关信息），最终得出错误结论。
    *   **应用**：引入“执行者视角”（拥有历史搜索失败记录）和“诊断者视角”（拥有成功证据标准）对 Planner 的搜索计划进行一致性打分。若 Planner 认为“肯定有”，但执行者认为“大概率无”，则触发重规划。

2.  **自动化软件测试与调试（Auto-Debugging）**
    *   **痛点**：Agent 生成修复代码，语法正确且能通过静态检查，但逻辑上无法修复 Bug（认知误校准：认为修改变量 X 就能解决 Y 问题）。
    *   **应用**：Planner 生成修复方案，Executor（运行测试）和 Diagnoser（分析测试失败日志）分别评估。若 Planner 评分高但 Diagnoser 基于历史失败案例评分低，则标记该方案为“高风险”，强制引入约束（如“不要盲目修改全局变量”）。

3.  **供应链/物流路径规划**
    *   **痛点**：规划系统认为“路线 A 最快”，因为它忽略了某些隐性约束（如特定路段在特定时段禁行，或某仓库库存不足但未实时同步）。
    *   **应用**：构建多智能体架构。Planner 基于宏观地图规划；Executor 基于实时路况/库存日志；Diagnoser 基于历史延误数据。通过 IPS 机制，选择三方共识度最高的路线，避免 Planner 的“盲目乐观”。

4.  **金融合规与风控策略生成**
    *   **痛点**：风控 Agent 生成了一套看似完美的交易策略，认为符合所有规则，但忽略了某些“灰色地带”或最新监管解读（认知偏差）。
    *   **应用**：Planner 生成策略，合规专家 Agent（Diagnoser）和过往违规案例库 Agent（Executor）进行交叉评估。利用 CESR 将“被否决的策略特征”转化为记忆约束，防止 Agent 再次生成类似违规策略。

## 可立刻试的小实验（≥3）

### 实验 1：构建“认知隔离”的模拟环境
*   **目标**：验证“记忆隔离”是否能产生视角差异，从而暴露 Planner 的误判。
*   **输入**：一个包含陷阱的搜索任务（例如：查询一个不存在的历史事件，但 Planner 容易幻觉出“可能存在”）。
*   **步骤**：
    1.  实例化三个 LLM 角色：`Planner`（仅看到任务描述，记忆为空）、`Executor`（记忆包含“该关键词搜索历史返回 0 结果”）、`Diagnoser`（记忆包含“成功回答必须包含具体日期”）。
    2.  让 `Planner` 生成 3 个搜索计划。
    3.  让 `Executor` 和 `Diagnoser` 分别基于**自己的记忆**对这三个计划打分（1-5 分）。
    4.  计算一致性得分：$Score = Planner\_Score - \text{Avg}(Executor\_Score, Diagnoser\_Score)$。
*   **期望输出**：
    *   Planner 对“幻觉计划”打分高（4-5 分）。
    *   Executor/Diagnoser 打分低（1-2 分）。
    *   一致性得分显著为负，系统应自动**拒绝**该计划，而非直接执行。

### 实验 2：CESR 约束生成与复用
*   **目标**：验证“失败教训”能否转化为“通用约束”并防止复发。
*   **输入**：连续 3 轮相同的搜索任务（或变体），模拟 Planner 反复犯同样错误。
*   **步骤**：
    1.  **Round 1**：Planner 提出错误计划（如“直接假设数据存在”），被 IPS 拦截。记录 Planner 的原始理由。
    2.  **Round 1 后**：调用 Diagnoser 生成一条约束（例如：“禁止在未获得搜索证据前假设数据存在”），写入 Planner 的 System Prompt 或 Memory。
    3.  **Round 2 & 3**：观察 Planner 在生成新计划时，是否主动规避了该模式。
*   **期望输出**：
    *   Round 1：Planner 提出错误计划，被拦截。
    *   Round 2：Planner 生成的计划中，不再包含“假设数据存在”的步骤，或者在生成时主动增加了“先搜索验证”的步骤。
    *   验证：对比加入约束前后的 Plan 文本差异。

### 实验 3：IPS 在“搜索密集型”任务中的保守性测试
*   **目标**：验证论文中提到的“单独使用 IPS 可能导致过度保守”的结论。
*   **输入**：一个需要“大胆猜测并验证”的复杂推理任务（如 GAIA 基准中的某些任务）。
*   **步骤**：
    1.  **基线组**：仅使用 IPS 选择计划（只选大家意见一致的）。
    2.  **实验组**：IPS + CESR（引入约束后允许在安全范围内探索）。
    3.  对比两组在 10 个样本上的成功率。
*   **期望输出**：
    *   基线组：成功率较低，因为 Planner 不敢提出需要“先搜索再推理”的冒险计划，只选“平庸但安全”的计划。
    *   实验组：成功率显著提升，因为 CESR 排除了“错误方向”，释放了 Planner 在“正确方向”上的探索能力。

## 产品 / Agent 灵感

1.  **“反盲目自信”规划器插件**
    *   **功能**：作为一个中间件插件，嵌入现有的 Agent 工作流（如 LangGraph, AutoGen）。
    *   **机制**：在 Planner 输出 Plan 后，不直接执行，而是自动调用一个轻量级的“挑战者 Agent"（基于历史失败数据训练），对 Plan 进行“压力测试”。如果挑战者认为“不可行”，则强制 Planner 重写。
    *   **卖点**：解决“代码能跑，但结果不对”的顽疾，提升企业级 Agent 的可靠性。

2.  **动态认知校准仪表盘**
    *   **功能**：为开发者提供可视化的“认知一致性”监控。
    *   **机制**：实时展示 Planner、Executor、Diagnoser 对当前计划的评分差异。
    *   **价值**：当差异过大时，高亮显示“认知误校准”风险，帮助开发者快速定位是 Planner 太自信，还是 Executor 记忆太消极。

3.  **自适应约束记忆库（Self-Correction Memory）**
    *   **功能**：一个独立的知识库服务，专门存储“被 CESR 提炼出的约束规则”。
    *   **机制**：当某个 Agent 团队（如客服组、研发组）频繁出现同类规划错误时，系统自动提取约束规则，并广播给该组所有 Agent，实现“一人犯错，全员避坑”。

## 跟现有系统怎么接

1.  **架构层改造（引入角色隔离）**
    *   **现状**：现有系统通常是单 Agent 或简单的 Chain，所有 Agent 共享同一份 Context。
    *   **改造**：
        *   将 `Context` 拆分为 `Global_Context`（任务、工具定义）和 `Private_Memory`（各角色专属）。
        *   **Planner**：只读 `Global` + `Failed_Tries`。
        *   **Executor**：只读 `Global` + `Execution_Logs`。
        *   **Diagnoser**：只读 `Global` + `Success_Cases`。
        *   在 Prompt 中显式声明：“你只能看到 XX 信息，基于此评估计划”。

2.  **流程层改造（插入 IPS 检查点）**
    *   **现状**：`Plan -> Execute -> Loop`。
    *   **改造**：`Plan (K candidates) -> [IPS Check: Cross-Evaluation] -> Select Best -> Execute`。
    *   **代码逻辑**：
        ```python
        candidates = planner.generate(k=5)
        scores = {}
        for agent in [executor, diagnoser]:
            scores[agent] = agent.evaluate(candidates, memory=agent.private_memory)
        best_plan = select_by_consistency(candidates, planner_score, scores)
        ```

3.  **记忆层改造（实现 CESR 写入）**
    *   **现状**：记忆通常是简单的日志追加。
    *   **改造**：增加 `Constraint_Generator` 模块。
        *   当 `Planner_Preference != IPS_Selection` 时，触发 `Constraint_Generator`。
        *   输出格式：`[CONSTRAINT] 当遇到 X 情况时，禁止执行 Y 操作，必须优先验证 Z。`
        *   将该 Constraint 插入 Planner 的 System Prompt 或 RAG 检索库。

## 风险与坑

1.  **“一致的错误”盲区**
    *   **风险**：如果工具返回了完美的假数据（如搜索到了伪造网页），Planner、Executor、Diagnoser 可能基于此达成一致，IPS 无法识别。
    *   **对策**：必须保留一个独立的“事实核查层”或引入外部可信数据源作为 Ground Truth 校验，不能完全依赖内部一致性。

2.  **Token 成本与延迟爆炸**
    *   **风险**：每轮生成 K 个计划，每个计划被 3 个 Agent 评估，Token 消耗是基线的 3-5 倍。
    *   **对策**：
        *   仅在任务复杂度高（如多步推理）时开启 IPS。
        *   使用小模型（如 7B/14B）进行 IPS 评估，仅用大模型做最终生成。
        *   限制 K 值（如 K=3 而非 9）。

3.  **约束过拟合（Overfitting）**
    *   **风险**：CESR 生成的约束过于具体（如“不要搜索 2023 年 5 月 1 日的新闻”），导致 Agent 在类似但不同的场景（2023 年 5 月 2 日）也束手束脚。
    *   **对策**：在 Constraint Generator 中增加“抽象化”步骤，要求将具体案例转化为通用原则（如“不要假设特定日期的新闻存在，除非有明确来源”）。

4.  **角色定义模糊**
    *   **风险**：如果 Planner 和 Executor 的记忆隔离不彻底（例如 Planner 看到了 Executor 的失败日志），视角差异消失，IPS 失效。
    *   **对策**：在代码层面严格物理隔离 Prompt 上下文，不要共享 Memory 对象，而是通过 API 显式传递“经过过滤”的记忆片段。
