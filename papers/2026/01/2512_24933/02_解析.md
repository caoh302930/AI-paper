## TL;DR and contributions
ADOPT 提出了一种自适应依赖导向的联合提示优化框架，旨在解决多步大语言模型（LLM）工作流中“只有最终结果有标签，中间步骤无监督”的难题。它通过模拟微积分中的偏导数计算，将最终任务的错误信号分解为每个步骤的局部优化方向，并利用 Shapley 值动态分配优化资源，从而像训练神经网络一样高效地训练整个工作流的提示词。

**Main contributions:**
- 提出**依赖感知的文本梯度估计**机制，无需 LLM 进行反向推理即可将全局误差分解为步骤级信号。
- 设计**解耦的优化架构**，将信号生成与提示更新分离，兼容任意单步优化器。
- 引入**基于 Shapley 值的资源分配策略**，自适应地将计算预算倾斜给对最终结果贡献最大的步骤。
- 在 5 个真实数据集和多种工作流结构（含循环）上，性能显著超越 GEPA、TextGrad 等强基线。

**Compared against:** Chain-of-Thought (CoT), TextGrad, Trace, MIPRO, GEPA.  
**On datasets:** Amazon (推荐), HotPotQA (多跳问答), HoVer (事实核查), Emergency (紧急协助), Harmful (有害内容检测)。  
**Headline improvements:** 在 HotPotQA 上准确率从 GEPA 的 0.63 提升至 **0.69**；在 HoVer 上从 0.65 提升至 **0.71**；在 Amazon 上从 0.92 提升至 **0.94**。

## What matters, what doesn't

- **🎯 Core idea (read carefully):** 核心在于**“依赖感知的文本梯度分解”**。即如何在不依赖 LLM 反向推理的情况下，利用执行轨迹分析每个步骤对最终结果的贡献度，从而将全局错误信号精准地“分配”给具体的中间步骤。这是 ADOPT 区别于 TextGrad/Trace 的关键。
- **🔧 Useful in practice:** **Shapley 资源分配策略**。在实际工程中，优化所有步骤成本高昂，该策略能自动识别哪些步骤是瓶颈，从而节省 Token 和时间。
- **📎 Nice to know:** 具体的 Prompt 优化器实现细节（如 Instruction-only vs Joint），以及不同数据集的具体 Pipeline 代码结构（Appendix D）。
- **⚠️ Deprecated / superseded:** 文中指出 TextGrad 和 Trace 在处理**循环结构（Looping structures）**时存在天然缺陷，ADOPT 通过显式建模依赖关系解决了这一问题。
- **🔕 Skippable:** 详细的数学推导公式（如 Shapley 值的具体权重公式 $w(S)$），除非你需要复现算法细节，否则理解其“平均边际贡献”的直觉即可。

## Context and prerequisites

要真正理解 ADOPT，你需要建立两个核心概念模型：多步工作流的“黑盒”特性，以及文本梯度的“微积分”类比。

首先，多步 LLM 工作流（Multi-Step LLM Pipelines）通常由一系列 LLM 调用和非 LLM 逻辑（如代码控制流、工具调用）串联而成。在传统监督学习中，我们通常有输入 $x$ 和中间层输出 $h_i$ 的标签，但在 LLM 工作流中，我们往往只有最终输出 $y$ 的标签（Ground Truth），中间每一步的输出 $h_i$ 都是“黑盒”，没有直接的正确与否的标注。这就导致了一个经典的**信用分配问题（Credit Assignment Problem）**：当最终答案错了，我们不知道是第一步检索错了，还是第二步推理错了，还是第三步总结错了。现有的方法（如 TextGrad）试图让 LLM 自己“反思”错误来源，但这引入了 LLM 自身的推理偏差，且难以处理复杂的循环依赖。

其次，ADOPT 的核心灵感来自深度学习的**反向传播（Backpropagation）**。在神经网络中，我们通过链式法则计算损失函数对每个参数的偏导数 $\frac{\partial L}{\partial w_i}$，从而知道该参数该往哪个方向调整。在 LLM 提示词优化中，参数是自然语言字符串，无法直接求导。ADOPT 提出用**文本梯度（Textual Gradient）**来模拟这一过程：它不依赖 LLM 去“猜”哪里错了，而是通过**依赖分析（Dependency Analysis）**，量化每个步骤的输出变化对最终结果的影响程度。这就像在微积分中，如果我们知道函数 $y = f(x_1, x_2)$ 的结构，我们就能解析地计算出 $x_1$ 和 $x_2$ 各自的偏导数，而不需要让函数自己去“思考”它为什么错了。ADOPT 正是通过这种“解析式”的依赖建模，替代了传统的“推理式”错误归因。

## Method

### The big picture (layman version)
想象一个由 5 个人组成的团队（工作流），每个人负责一个环节，最后由第 5 个人提交最终报告。老板（优化器）只给最终报告打分，如果报告错了，老板不知道是谁的错。
以前的方法（如 TextGrad）是：老板把报告退给第 5 个人，让他去问第 4 个人，第 4 个人问第 3 个人……大家互相猜谁错了，最后第 1 个人可能收到一个模糊的指令“你写得不够好”。这既慢又容易出错，特别是如果团队里有循环讨论（比如第 2 个人和第 3 个人互相修改），这种“传话”机制就会崩溃。

ADOPT 的做法完全不同：
1.  **先画地图（依赖分析）：** 在优化开始前，ADOPT 先观察团队在**成功**案例中的表现，分析每个人的工作如何具体影响了最终结果。比如，它发现第 1 个人提供的“关键词”直接决定了第 5 个人能否找到正确答案。
2.  **算偏导数（梯度分解）：** 当报告错了，ADOPT 不让大家互相猜，而是直接根据之前的“地图”，计算出第 1 个人、第 2 个人各自应该承担多少“责任”，并给每个人写一张具体的“修改建议卡”（局部文本梯度）。这张卡片告诉第 1 个人：“你的关键词太宽泛了，导致后面找不到答案，请改为更具体的地理词汇”。
3.  **谁重要谁多练（资源分配）：** 优化过程中，ADOPT 发现第 1 个人和第 3 个人对提升分数贡献最大，于是把更多的“练习机会”（优化预算）分配给他们，而让贡献小的第 5 个人少练点，从而节省整体时间。

### The walkthrough

ADOPT 的优化过程分为三个紧密耦合的阶段：**依赖感知的文本梯度估计**、**解耦的提示优化**、**基于 Shapley 值的资源分配**。

#### 1. 依赖感知的文本梯度估计 (Dependency-aware Textual Gradient Estimation)
这是 ADOPT 的灵魂。它试图模拟 $\nabla_{p_i} \mathcal{L}$（损失函数对第 $i$ 个提示的梯度）。
- **步骤 A：分析最终输出依赖 (Analyzing Final Output Dependency)**
  ADOPT 首先利用优化器 $E_1$ 分析工作流代码和提示词，理解整体任务。然后，利用 $E_2$ 分析**成功案例（Good Cases）**的执行轨迹。$E_2$ 会回答：“在成功的情况下，步骤 $i$ 的输出是如何具体贡献给最终结果的？”这建立了一个从步骤到最终结果的**功能依赖图**。这步非常关键，它避免了让 LLM 在错误发生时去“推理”依赖关系，而是基于成功数据建立先验知识。
- **步骤 B：构建全局文本梯度 (Computing Global Textual Gradient)**
  对于**失败案例（Bad Cases）**，ADOPT 使用 $E_3$ 计算最终输出与真值之间的**文本损失（Textual Loss, $\mathcal{L}$）**，即具体的错误描述。接着，$E_4$ 分析这些错误，生成一个**全局文本梯度（Global Textual Gradient, $g^{\text{global}}$）**。这相当于在说：“最终结果错了，因为缺少了地理信息，且混淆了平台与地点”。
- **步骤 C：分解为局部文本梯度 (Computing Local Textal Gradient)**
  这是最精彩的一步。利用步骤 A 建立的依赖关系，$E_5$ 将全局梯度 $g^{\text{global}}$ 分解为每个步骤的**局部文本梯度（Local Textual Gradient, $g^{\text{local}}_i$）**。
  形式化地，这类似于计算偏导数：
  $$ g^{\text{local}}_i = \nabla_{p_i}^{\text{text}} \mathcal{L} $$
  $E_5$ 会结合“步骤 $i$ 的职责”和“全局错误”，生成针对步骤 $i$ 的具体修改方向。例如，对于 HotPotQA 中的检索步骤，它会指出：“你的查询太宽泛，没有包含‘国家’这一维度，导致后续检索失败”。

#### 2. 解耦的提示优化 (Prompt Optimization for Pipeline)
一旦有了局部梯度，ADOPT 将其转化为具体的优化任务。
- **生成修订输出 (Revised Step Output):** 利用 $E_6$，根据局部梯度 $g^{\text{local}}_i$，为每个失败案例生成一个**理想的步骤输出（Revised Output）**。这相当于为步骤 $i$ 构造了一个伪标签（Pseudo-label）。
- **构建步骤级数据集:** 收集所有失败案例的 $(x_i, \hat{y}_i)$ 对，形成步骤 $i$ 的专属数据集 $\mathcal{D}_i$。
- **单步优化:** 此时，ADOPT 将问题解耦。每个步骤 $i$ 可以独立使用任何现有的单步优化器（如 MIPRO、OPRO 等）在 $\mathcal{D}_i$ 上更新提示词 $p_i$。这产生了每个步骤的一组候选提示词 $\mathcal{P}_i$。
- **全局提示选择 (Global Prompt Selection):** 由于步骤间存在耦合，不能简单地把每个步骤最好的提示拼起来。ADOPT 使用**贝叶斯优化（Bayesian Optimization）**在组合空间 $\mathcal{P}_1 \times \dots \times \mathcal{P}_m$ 中搜索最佳的提示组合，以最大化端到端性能。

#### 3. 基于 Shapley 值的资源分配 (Shapley-based Resource Allocation)
为了节省成本，ADOPT 不平均分配优化预算。
- **贡献度评估:** 在每一轮优化后，ADOPT 计算每个步骤的**Shapley 值（$\phi_i$）**。Shapley 值衡量的是：当步骤 $i$ 从“弱提示”变为“强提示”时，对整体性能的平均边际贡献。
  $$ \phi_i = \sum_{S \subseteq [m] \setminus \{i\}} w(S) (v(S \cup \{i\}) - v(S)) $$
  其中 $v(S)$ 是步骤集合 $S$ 使用强提示时的性能。
- **动态调整:** 使用 **Kernel SHAP** 算法，利用已评估的组合来近似计算 $\phi_i$。贡献大的步骤，下一轮获得更多的候选提示生成预算（$b_i$）；贡献小的步骤，预算减少。这确保了计算资源集中在“瓶颈”步骤上。

## Challenges in the field — and what this work addresses

1.  **中间步骤无监督信号 (Lack of Intermediate Supervision):**
    *   **难点:** 多步工作流中，只有最终结果有标签。传统方法（如 TextGrad）依赖 LLM 进行反向推理（Backward Reasoning）来推断错误来源。但这引入了 LLM 自身的幻觉和解释偏差，且信号在传递过程中容易衰减或失真。
    *   **ADOPT 的解法:** 放弃让 LLM“推理”错误来源，转而通过**依赖分析**（基于成功案例）和**解析分解**（基于全局梯度）来显式计算每个步骤的“责任”。这更像是一种结构化的信号分解，而非模糊的推理。

2.  **复杂控制流与循环结构 (Complex Control Flow & Loops):**
    *   **难点:** 许多现有方法（如 TextGrad, Trace）假设工作流是 DAG（有向无环图）。一旦遇到循环（如 Agent 反复尝试直到成功），反向传播路径变得无限或难以定义，导致这些方法失效。
    *   **ADOPT 的解法:** ADOPT 的依赖分析是基于执行轨迹（Execution Traces）的，不依赖静态的图结构。它分析的是“实际运行中”步骤与结果的函数关系，因此天然支持包含循环、条件分支的复杂工作流。

3.  **优化效率与资源浪费 (Optimization Efficiency):**
    *   **难点:** 多步优化需要巨大的 Token 消耗。如果对所有步骤一视同仁地优化，会浪费大量资源在那些已经饱和或对结果影响微乎其微的步骤上。
    *   **ADOPT 的解法:** 引入 **Shapley 值资源分配**。通过量化每个步骤的边际贡献，动态调整优化预算，实现了“好钢用在刀刃上”，在减少 Token 消耗的同时保持甚至提升性能。

**What this work does NOT address:**
ADOPT 仍然需要大量的 LLM 调用来进行依赖分析和梯度估计，虽然比均匀优化更高效，但对于实时性要求极高（Real-time）或资源极度受限的场景，其开销依然是一个挑战。此外，它假设工作流代码 $C$ 是固定的，无法优化工作流本身的逻辑结构（如增加或减少步骤）。

## Experiments and results

ADOPT 在 5 个真实数据集和 5 种不同结构的工作流上进行了评估。
- **主要结果 (Table 2):**
    - **HotPotQA (多跳问答):** ADOPT 达到 **0.69** 准确率，优于 GEPA (0.63) 和 MIPRO (0.62)。
    - **HoVer (事实核查):** ADOPT 达到 **0.71**，优于 GEPA (0.65)。
    - **Amazon (推荐):** ADOPT 达到 **0.94** (1-MAE)，优于 GEPA (0.92)。
    - **Emergency & Harmful:** 在含循环结构的任务中，ADOPT 表现尤为突出，分别达到 0.89 和 0.75，而 TextGrad 和 Trace 因不支持循环结构无法在这些数据集上运行（标记为 `/`）。
- **收敛性分析 (Figure 3):** ADOPT 在早期迭代中性能提升迅速，且后期稳定，没有明显的性能震荡。引入资源分配（Resource Allocation）的变体收敛速度更快。
- **消融实验 (Table 4):**
    - 移除**依赖导向估计**：性能显著下降（HotPotQA 从 0.69 降至 0.64），证明依赖分解是核心。
    - 移除**全局提示选择**：性能下降（0.62），说明局部最优不等于全局最优，组合搜索必不可少。
    - 移除**资源分配**：最终精度影响不大（0.68 vs 0.69），但**效率**（Token 和时间）显著提升（Table 5），证明其主要用于加速而非提升上限。
- **效率对比 (Table 5):** 在 HotPotQA 上，ADOPT 的总 Token 消耗（5.52M）低于 MIPRO (11.79M) 和 GEPA (4.65M，但 GEPA 在循环任务上不可用)，且优化时间更短（2.20h vs 3.88h）。

## Open questions and limitations
1.  **依赖分析的准确性:** ADOPT 依赖 LLM 来分析步骤间的依赖关系。如果 LLM 对代码或任务的理解有误（例如错误判断了某个步骤的重要性），会导致梯度分解错误，进而误导优化方向。
2.  **计算开销:** 尽管有资源分配，但每一轮都需要运行多次 LLM 调用（依赖分析、梯度分解、候选生成、组合搜索）。对于超大规模工作流（如 20+ 步骤），开销可能依然难以接受。
3.  **对坏案例的敏感性:** 优化主要基于“坏案例”（Bad Cases）。如果训练集中坏案例太少，或者坏案例具有特殊性（Outliers），可能导致过拟合或优化方向偏差。
4.  **提示空间的离散性:** 文本梯度是自然语言，将其转化为具体的提示词修改（如增加一个词、改变句式）仍然是一个启发式的搜索过程，缺乏数学上的严格收敛保证。

- **视频强调:** 视频标题提到“像训练模型一样训练 Prompt"，这非常精准地抓住了 ADOPT 的核心类比（将 Prompt 视为参数，将文本梯度视为导数）。视频可能重点展示了 ADOPT 在循环结构（Loop）上的优势，这是 GEPA 等方法的痛点。
- **可能简化/遗漏:**
    - 视频可能未深入解释**Shapley 值**的具体计算过程，仅将其描述为“智能分配资源”。实际上，这是基于博弈论的精确贡献度度量，是 ADOPT 效率提升的关键。

    - 视频可能未提及**解耦设计**（Decoupling）的重要性，即 ADOPT 可以兼容任何单步优化器，这是一个很强的工程优势。
